# JCode 上下文治理完整链路

本文以当前代码为准，描述 JCode 从 run 启动、结构化上下文构建、DeepSeek Responses 原生工具调用，到工具结果回流、历史压缩、记忆维护和恢复校验的完整链路。

## 一、治理目标

上下文治理负责：

1. 将稳定规则、技能、会话历史、短期记忆和当前请求组织为 Provider 无关的结构化结果。
2. 在上下文压力增加时按四档策略压缩低优先级内容，同时保持工具调用与结果的结构完整。
3. 将工具执行结果、文件新鲜度、artifact 和失败信息回流到下一轮上下文。
4. 将构建、压缩、Provider 响应和运行状态写入 session、trace、checkpoint 和 report，供恢复与审计。

## 二、核心模块

| 模块 | 职责 |
| --- | --- |
| `src/runtime/agent.py` | 驱动 run 循环，按 Provider 原生 `tool_calls` 执行工具。 |
| `src/context/manager.py` | 构建 `ContextResult`，计算压力、窗口外工具压缩和等级 4 历史语义压缩。 |
| `src/context/result.py` | 定义 `ContextResult`、`HistoryEvent` 和 `ToolDefinition`。 |
| `src/context/prefix.py` | 生成稳定 `prefix`，不包含工具 schema 或输出协议。 |
| `src/memory/working.py` | 保存短期任务状态、文件 freshness、工具观察、恢复状态和压缩摘要。 |
| `src/state/history.py` | 向 session 追加 Provider 无关的结构化历史事件。 |
| `src/providers/deepseek.py` | 将 `ContextResult` 编译为 DeepSeek Responses 请求，并解析原生响应。 |
| `src/evidence/store.py` | 写入 `trace.jsonl`、checkpoint、report 与 artifact。 |

## 三、ContextResult

`ContextManager.build()` 的产物是 `ContextResult`，不是最终 prompt 字符串：

```python
@dataclass
class ContextResult:
    prefix: str                 # 稳定系统规则与项目规则
    skill: str                  # 本轮技能上下文
    history: list[HistoryEvent] # 经治理后的会话历史
    working_memory: WorkingMemory # 构建时冻结的短期记忆快照
    current_request: str        # 当前真实用户请求
    tools: list[ToolDefinition] # 当前允许调用的原生工具
    ctx_info: dict              # 压力、裁剪与压缩审计
```

`WorkingMemory` 使用现有运行时类型。构建时以 `to_dict()` / `from_dict()` 复制为快照，Provider 只读其渲染结果，不能修改读取计数、freshness 或其他运行时状态。

## 四、五段上下文与缓存顺序

原来的五段名称和业务语义保持不变：

```text
prefix
skill
history
working_memory
current_request
```

DeepSeek Responses Adapter 将其编译为：

```text
instructions:
  prefix

input:
  user: [JCode Skill Context] + skill
  history 的原生结构化事件
  user: [JCode Working Memory] + working_memory.render()
  user: current_request
```

这样安排的原因：

- `prefix` 最稳定，单独进入 `instructions`，便于命中稳定前缀缓存。
- `skill` 变化较少，位于 history 前。
- `history` 按 run 递增，已有前缀可复用。
- `working_memory` 变化频率最高，置于 history 后，避免破坏其缓存前缀。
- `current_request` 始终最后，且是唯一真实用户请求。

当前 run 的 user event 会先写入 session，但构建 `ContextResult.history` 时会排除该 event，避免与末尾 `current_request` 重复发送。当前 run 后续产生的 assistant、tool call 和 tool result 仍保留在 history 内。

`skill` 与 `working_memory` 在 API 层使用 user message，但带有 JCode 内部来源标签，不能被当作用户追加的业务请求。

## 五、历史事件

`history` 由 `HistoryEvent` 构成：

```python
@dataclass
class HistoryEvent:
    kind: Literal["user", "assistant", "tool_call", "tool_result", "compact_summary"]
    event_id: str
    turn_id: str
    content: str
    tool_name: str | None
    call_id: str | None
    arguments: dict | None
    metadata: dict
```

事件规则：

- `tool_call` 与 `tool_result` 以同一个 `call_id` 关联。
- `arguments` 保持字典，永远不按字符截断。
- 工具结果的状态、artifact、文件变更和 stale 标记保留在 `metadata`。
- DeepSeek 同 run 回放需要的 reasoning 和 function-call 原生 item 放在关联事件的 `metadata` 中，不单独维护 continuation 对象。
- `compact_summary` 是 session 中的持久化摘要事件；构建时同步至 `WorkingMemory.compact_summary`，并作为普通历史前的内部 Provider 消息发送，不重复混入 Working Memory。

## 六、预算与四档压力治理

预算仍使用字符近似 token，默认按 `prefix`、`skill`、`history`、`working_memory` 分配。`current_request` 保持完整。

| 压力等级 | 触发比例 | 行为 |
| ---: | ---: | --- |
| 0 | `< 60%` | 不压缩历史工具结果。 |
| 1 | `60% - 70%` | 保留完整 history，窗口外工具结果按规则压缩。 |
| 2 | `70% - 80%` | skill 缩减至 70%，历史窗口外工具结果压缩。 |
| 3 | `80% - 90%` | skill 缩减至 50%，Working Memory 仅保留活跃状态，历史窗口外工具结果压缩。 |
| 4 | `>= 90%` | 对旧 completed turn 做语义压缩，仅保留最近 4 个 turn，并继续压缩窗口外工具结果。 |

最近完整 turn 窗口随压力从 7、6、5 逐级减少到 4；等级 4 语义压缩同样保留最近 4 个 completed turn。

当前约束：

- 不再把 `history` 渲染成大文本后调用 `tail_clip()`。
- `tail_clip()` 仍可用于 skill 和 working memory 的文本预算。
- 历史窗口外工具结果压缩发生在 `HistoryEvent.content`，不是 Provider 编译后的请求文本。
- 任何压缩都不能截断 `call_id`、工具名称或 `arguments`。
- 工具调用与结果必须成对保留、压缩或进入同一个语义摘要，不允许只保留一侧。

## 七、窗口外工具结果与 artifact

窗口外的成功工具结果按以下规则压缩：

1. stale 的 `read_file` 替换为“源文件已变化”的受控提示，旧正文不再暴露。
2. 已外置的大结果保留 artifact 路径和内容摘要。
3. 重复的旧 `read_file` 保留首次证据，后续同路径读取替换为重复读取提示。
4. `run_shell` 保留前三条非空输出行。
5. 其他可压缩工具保留前 80 个字符。

写入、patch、todo、用户确认和子任务工具默认不压缩，避免丢失运行状态。工具结果仍以合法的 Responses `function_call_output` 形式发送，artifact 路径不是模型自行伪造或猜测的普通对话文本。

## 八、等级 4 的历史语义压缩

`compact_history()` 是唯一会永久修改 `session["history"]` 的治理动作：

```text
按 turn 分组
  -> 保留最近 4 个 completed turn
  -> 收集更早 completed turn
  -> 从结构化事件生成确定性摘要
  -> 写入 kind=compact_summary 事件
  -> history = compact_summary + 最近事件
  -> 同步 WorkingMemory.compact_summary
```

摘要包含任务目标、约束、读取和修改的文件、关键决策、阻塞项和下一步；不包含 Provider 原生 reasoning。未闭合的工具调用链不能进入压缩范围。

## 九、DeepSeek Responses 原生调用循环

固定 Provider 配置为：

```toml
[provider]
name = "deepseek"
api_protocol = "openai_responses"
base_url = "https://api.deepseek.com"
api_key_env = "DEEPSEEK_API_KEY"
```

每个模型档案只描述模型与可选 reasoning effort。Provider 和 API 协议不可通过 session 或 Web 切换。

运行循环：

```text
写入当前 user history
  -> ContextManager.build()
  -> ContextResult
  -> DeepSeek Responses 请求
  -> 是否存在 tool_calls？

有 tool_calls
  -> 写入 assistant / tool_call HistoryEvent
  -> 按返回顺序执行工具
  -> 用相同 call_id 写入 tool_result
  -> 下一子轮

无 tool_calls
  -> content 非空：作为最终回答结束
  -> content 为空：以 empty_model_content 结束，不重试
```

中间工具轮允许 `content` 为空。最终答案完全来自 Provider 返回的 `content`，不经过 final 协议或 FinalGate 重试。

## 十、工作记忆与新鲜度

`WorkingMemory` 是当前任务的短期控制面，保存：

- 当前目标与约束。
- 最近文件、file freshness 和重复读取计数。
- 检索结果、工具观察、子任务结果与安全提示。
- checkpoint 恢复信息与历史压缩摘要。
- 当前运行模式和工作区运行时说明。

工具执行更新 working memory；`ContextResult` 使用其冻结快照。成功写入或 patch 后，JCode 遍历历史 `tool_result`，将依赖被修改文件的旧读取结果标记为 stale。下一轮只会向模型发送 stale 提示，要求重新读取当前文件。

## 十一、session、checkpoint 与恢复

session schema 为 v4：

- `history` 保存结构化 `HistoryEvent` 字段。
- `working_memory` 保存短期记忆可序列化数据。
- `active_model_profile` 和 per-profile effort 用于 run 间模型切换。
- schema v3 及更早的 session 不能恢复到原生工具调用链路，必须开始新 session。

checkpoint 继续保存 task、working memory、workspace fingerprint、文件 freshness、todo 和 worker 引用。恢复校验仍返回 `full_valid`、`partial_stale`、`workspace_mismatch` 等状态；恢复状态进入 working memory，不改写历史事实。

## 十二、Trace 与 Web

每个 run 位于 `.jcode/runs/<run_id>/`：

```text
trace.jsonl
task_state.json
checkpoint.json
report.json
artifacts/
```

关键 trace 事件：

| 事件 | 内容 |
| --- | --- |
| `context_built` | 脱敏后的 `ContextResult` 快照和 `ctx_info`。 |
| `compact_evaluated` / `compact_triggered` | 压力等级与压缩决定。 |
| `compact_completed` | 历史摘要审计。 |
| `model_responded` | Provider content、reasoning、finish reason 与原生 tool calls。 |
| `native_tool_calls_received` | Provider 返回的 call id、工具名和参数。 |
| `tool_requested` / `tool_executed` | 工具请求、结果、状态、artifact 和文件变化。 |
| `run_finished` | 最终状态、停止原因和最终文本。 |

Web 时间线直接聚合 Provider 原生 tool call 与工具结果，不再展示 XML 解析或协议解析失败事件。

## 十三、排查入口

遇到“模型看到的上下文不对”时：

1. 查看对应 run 的 `context_built`，检查五段字段、历史事件、工具集合和压缩记录。
2. 检查 `compact_*` 事件，确认是否发生等级 4 语义压缩。
3. 检查 session 的 `history`、`working_memory` 和 `ctx_info`，确认 call id 配对、artifact 元数据与 stale 标记。
4. 检查 `model_responded` 与 `native_tool_calls_received`，确认 Provider 的原生返回。
5. 对工具问题检查 `tool_requested`、`tool_executed`、对应 `tool_result.metadata` 和 artifact 可用性。
6. 恢复任务再检查 `checkpoint.json`、`resume_evaluated` 和 workspace fingerprint。
