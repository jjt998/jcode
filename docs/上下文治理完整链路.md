# JCode 上下文治理完整链路

本文以当前代码实现为准，描述 JCode 从一次运行开始，到上下文构建、模型调用、工具结果回流、历史压缩、记忆维护和恢复校验的完整链路。

## 一、治理目标

上下文治理解决四个问题：

1. 把稳定规则、项目规则、工具定义、短期状态、历史证据和当前请求组织成固定结构。
2. 在上下文接近预算上限时，按压力等级减少低优先级内容，同时保留当前任务所需证据。
3. 让工具执行结果、文件新鲜度、工作区变更和失败信息可以回流到下一轮上下文。
4. 把构建结果、压缩决策、模型输入和运行状态写入 session、trace、checkpoint 和 report，便于恢复与审计。

## 二、核心模块和中文职责

| 模块 | 中文职责 | 主要责任 |
| --- | --- | --- |
| `src/runtime/agent.py` | 代理运行时 | 驱动回合循环，调用上下文管理器和模型，接收动作并执行工具 |
| `src/context/manager.py` | 上下文管理器 | 构建五段上下文、估算压力、按等级压缩历史，执行语义压缩 |
| `src/context/budget.py` | 上下文预算 | 估算 token 数和按字符尾部裁剪 |
| `src/context/skills.py` | 技能提示 | 生成技能相关上下文段 |
| `src/runtime/plan.py` | 运行模式 | 将 plan mode 等当前模式状态注入工作记忆段 |
| `src/memory/working.py` | 工作记忆 | 保存任务目标、最近文件、文件新鲜度、工具观察、检索结果和压缩摘要 |
| `src/state/history.py` | 会话历史 | 向 session 追加用户、助手和工具历史项，并分配 turn/event 标识 |
| `src/state/session.py` | 会话存储 | 加载和保存 `.jcode/sessions/<session_id>.json` |
| `src/state/checkpoint.py` | 检查点 | 保存可恢复状态并校验工作区及文件新鲜度 |
| `src/state/resume.py` | 恢复上下文 | 评估最近运行的 checkpoint，并将结果放入工作记忆 |
| `src/evidence/store.py` | 运行证据 | 写入和读取每次运行的 `trace.jsonl`、`report.json` |
| `src/evidence/session_log.py` | 会话事件流 | 写入 Web 和跨运行查看使用的 `<session_id>.events.jsonl` |
| `src/memory/consolidation.py` | 记忆整理 | 回合结束后将任务结果写入 Daily Log 和 Durable Memory |

## 三、完整时序

```text
开始运行
  -> 加载 session、工作记忆和恢复状态
  -> 创建 TaskState、run 目录和初始 checkpoint 管理器
  -> 追加本轮 User history
  -> ContextManager 构建上下文
       -> 同步 compact summary
       -> 生成五个上下文段的初始文本
       -> 估算输入压力
       -> 按压力等级压缩
       -> 生成最终上下文和 ctx_info
  -> 保存 session，发出 context_built
  -> 调用模型
  -> 记录模型原始返回并解析动作
  -> assistant history 记录模型动作
  -> 执行工具或检查 final
  -> 工具结果写入 history、trace、工作记忆和 checkpoint
  -> 文件变化标记旧读取证据 stale
  -> 进入下一轮，重新构建上下文
  -> 运行结束后创建 checkpoint、维护长期记忆、写 report
```

代理主循环位于 `src/runtime/agent.py`。每一轮的上下文都是根据当前 session 和 working memory 重新构建的，不复用上一轮的最终 prompt。

## 四、上下文的五段结构

`ContextManager.build()` 使用固定顺序拼接以下段落：

```text
prefix
skill
working_memory
history
current_request
```

最终由 `_build_prompt()` 以两个换行连接，并去掉首尾空白。

### 4.1 稳定前缀

构建函数是 `ContextManager._build_prefix_text()`，包含：

- JCode 身份和基础系统规则。
- 输出协议，包括 `<reasoning>`、`<tool>`、`<tools>` 和 `<final>`。
- 运行时动态生成的工具定义、工具说明、读写风险和参数 schema。
- 工作区根目录下的 `JCODE.md` 项目规则，最多读取 12000 字符。
- 工作区边界、读取后写入、重复调用、sandbox、敏感信息和 artifact 读取规则。

工具定义来自当前 `ToolRegistry`，因此上下文中的工具列表和 schema 是运行时状态，而不是硬编码文档。

### 4.2 技能提示

`render_skill_section()` 生成技能段。该段优先级低于稳定前缀和当前任务证据，在压力等级 2、3、4 时会依次按 70% 或 50% 的预算尾部裁剪。

### 4.3 工作记忆

`_build_working_memory_text()` 将 `WorkingMemory.render()`、工作区根目录、运行模式和工作区运行时信息拼接起来。

当前工作记忆包括：

- `task`：当前任务目标。
- `files`：最近访问文件和文件 freshness。
- `retrieval`：从 Durable Memory 检索到的内容。
- `tools`：工具观察、失败结果和子任务结果摘要。
- `safety`：恢复状态和其他安全相关状态。
- `compact_summary`：历史被语义压缩后的摘要。

工作记忆是当前回合的短期控制面。它既被上下文渲染使用，也被工具策略使用，例如 `read_file` 的重复读取计数和写文件前的读取门槛。

### 4.4 历史

`_build_history_section_texts()` 从 `session["history"]` 取出历史，过滤 `compact_summary` 项后交给 `_build_history_text()`。

历史按 `turn_id` 分组。每个 turn 按以下结构渲染：

```text
--- Turn {turn_id} ---

[User]
用户消息

[Assistant]
<reasoning>可选的模型推理</reasoning>
<tool ...>...</tool> 或 <tools>...</tools>

[ToolResult (工具名)]<args>{...}</args>
工具结果

[Assistant]
<final>最终回答</final>
```

当前实现的具体行为：

- 没有结构化 assistant 项时，补充 `[Assistant]` 和空内容。
- assistant 的 `reasoning` 非空时才渲染 `<reasoning>`。
- `final` 动作渲染为 `<final>...</final>`。
- 工具结果始终带工具名和参数 JSON，参数来自 history item 的 `args`。
- 旧 turn 可根据压力进行工具结果压缩，但不会改变 session 中的原始 history item。
- stale 的 `read_file` 结果不再直接暴露旧正文，而是渲染为文件已变化的提示。

当没有历史时，历史段为：

```text
Transcript:
- empty
```

### 4.5 当前用户请求

当前请求直接渲染为：

```text
Current user request:
{user_message}
```

它不参与历史分组，始终位于最终上下文的最后，保证模型能明确识别本轮目标。

## 五、预算和压力治理

### 5.1 预算分配

默认总预算由 `ContextManager.total_budget` 控制，默认值为 60000 字符。预算提示比例为：

| 段落 | 比例提示 | 最小字符预算 |
| --- | ---: | ---: |
| `prefix` | 20% | 40000 |
| `skill` | 7% | 6000 |
| `working_memory` | 23% | 35000 |
| `history` | 50% | 60000 |

`current_request` 不分配固定预算，保持完整。

如果总预算低于所有最小预算之和，则按比例直接分配；否则每段取“比例预算”和“最小预算”中的较大值。

### 5.2 压力估算

`_build_pressure()` 先把五段拼成初始 prompt，再用 `estimate_tokens()` 按每 4 个字符约 1 token 估算输入 token 数：

```text
压力比例 = 估算输入 token 数 / 模型预算 token 数
模型预算 token 数 = (总字符预算 + 3) // 4
```

压力等级如下：

| 等级 | 比例 | 处理方式 |
| ---: | --- | --- |
| 0 | `< 60%` | 保持初始渲染 |
| 1 | `60% - 70%` | 历史窗口缩小到 3 个 turn |
| 2 | `70% - 80%` | 技能预算降至 70%，历史窗口缩小到 2 个 turn |
| 3 | `80% - 95%` | 技能和工作记忆进一步裁剪，历史窗口保持 2 个 turn |
| 4 | `>= 95%` | 触发历史语义压缩，技能和工作记忆裁剪，历史只保留近期 turn |

压力等级由初始 prompt 计算，压缩后会再次计算最终压力。所有初始预算、最终预算、字符数、token 估算和差异都会进入 `ctx_info`。

### 5.3 尾部裁剪

`tail_clip()` 在内容超过预算时保留文本尾部，并在前面添加 `...`。因此技能段和工作记忆段在压力下优先保留最近内容。

历史段的预算裁剪发生在生成 `History:` 后的最终文本上；历史内部还会先按照 turn 窗口和工具压缩规则减少内容。

## 六、历史工具结果的分级压缩

历史压缩分为“只改变本次渲染”和“改变 session 结构”两种，不能混为一谈。

### 6.1 渲染级压缩

`_compress_old_tool_history_item()` 只改变送入模型的文本，不删除或改写 session history：

1. stale 的 `read_file`：替换为过期证据提示。
2. 已外置为 artifact 的结果：保留 artifact 路径。
3. 旧的重复 `read_file`：按路径省略重复正文。
4. 旧的 `run_shell`：保留前三条非空输出行。
5. 其他可压缩工具：保留结果前 80 个字符。

写入、patch、todo、用户确认和子任务相关工具默认不压缩，避免丢失关键状态。

每次压缩会生成 `compression_records`，记录 turn、工具名、压缩规则、压缩前后字符数和预览，并进入 `ctx_info`。

### 6.2 语义压缩

压力等级 4 调用 `compact_history()`，这是唯一会真正修改 `session["history"]` 的历史压缩：

```text
按 turn 分组
  -> 保留最近 2 个 turn
  -> 收集更早 turn
  -> 用 LLM 生成摘要
  -> LLM 不可用时使用确定性摘要
  -> 插入 kind=compact_summary 的 system history item
  -> session history = 摘要 + 保留的近期 history
  -> working_memory.compact_summary 同步为摘要
```

摘要包含目标、约束、已读文件、已修改文件、关键决策、阻塞项和下一步。摘要生成审计保存 prompt、response、来源、状态和 fallback 原因。

下一轮构建时，`_sync_compact_summary_from_history()` 从最近的 `compact_summary` 恢复工作记忆摘要；渲染历史本身会过滤该特殊项，避免摘要被当成普通 turn 重复渲染。

## 七、模型调用和历史回流

上下文构建完成后，`JCodeAgent._build_context()` 会：

1. 将 `ctx_info` 放入 session。
2. 保存 session 文件。
3. 发出 `compact_evaluated`、`compact_triggered`、`compact_completed` 或 `compact_fallback` 事件。
4. 发出并写入 `context_built`，事件包含完整 `context` 和 `ctx_info`。

随后 `_call_model()` 将最终上下文交给 `ModelRouter.complete()`，并记录 `model_responded`，包含模型原始返回和输入输出 token 估算。

动作解析完成后，assistant history 保存：

- `action_kind`：`tool`、`tools`、`final` 或 `invalid`。
- `reasoning`：模型返回的可选 reasoning。
- `raw_content`：模型原始文本。
- 工具动作的工具名、参数或工具列表。
- final 动作的 `final_text`。

解析失败时，原始模型输出仍保留在 assistant history，并额外写入 `model_parse_failed` trace，包含原始内容、解析错误和 reasoning，便于定位协议问题。

## 八、工具结果如何回流上下文

工具执行由 `JCodeAgent._execute_tool_call()` 统一接收结果。工具结果会同时进入：

- `history`：供下一轮历史渲染，包含工具名、`args`、结果正文、状态、artifact、metadata 和变更文件。
- `trace.jsonl`：记录 `tool_requested` 和 `tool_executed`，包含参数、结果、状态、错误类型和策略信息。
- `WorkingMemory`：写入工具观察；子任务结果还会进入子任务结果列表。
- `checkpoint.json`：工具执行后保存恢复所需的当前状态。

工具结果过大时，完整结果写入 `.jcode/runs/<run_id>/artifacts/`，history 和模型上下文只保留路径及预览。再次读取 artifact 时直接返回 artifact 内容，避免重复外置。

工具返回的 `metadata.source_files` 会记录读取或搜索涉及的文件及 freshness。文件被写入或 patch 修改后，agent 会遍历相关 history item，把命中的读取证据标记为：

```json
{
  "stale": true,
  "stale_reason": "source_file_changed",
  "stale_paths": ["..." ]
}
```

下一次历史渲染时，stale 结果只显示过期提示，要求模型重新读取当前文件。

## 九、工作记忆、长期记忆和检查点

### 9.1 工作记忆

工作记忆在运行开始时从 session 恢复，工具执行和上下文构建过程中持续更新，运行结束时序列化回 session。它服务当前任务，不等同于长期知识库。

### 9.2 长期记忆

回合结束后，`maintain_after_turn()` 使用用户消息和最终答案整理记忆：

```text
最终答案
  -> Daily Log: .jcode/memory/logs/YYYY/MM/YYYY-MM-DD.md
  -> Durable Memory: MEMORY.md、topics/*.md、索引
```

长期记忆写入前会经过敏感信息检查，明显的 key、token、password、secret 等内容不会进入长期结论层。长期记忆默认不会自动回灌全部内容，只在检索阶段按当前请求选取相关内容放入工作记忆。

### 9.3 检查点和恢复

每次运行的 checkpoint 保存：

- session、run、task 和 step 状态。
- 最近动作、已完成步骤、待执行步骤。
- 已修改文件。
- 最近读取文件及文件 freshness。
- 完整 working memory。
- workspace fingerprint。
- 子任务引用。

恢复时 `evaluate_checkpoint_data()` 按以下顺序判断：

| 状态 | 含义 |
| --- | --- |
| `no_checkpoint` | 没有可用检查点 |
| `schema_mismatch` | 检查点版本不匹配 |
| `checkpoint_not_resumable` | 检查点被标记为不可恢复 |
| `workspace_mismatch` | 工作区 fingerprint 已变化 |
| `partial_stale` | 最近读取文件的 freshness 已变化 |
| `full_valid` | 检查点与当前工作区一致 |

恢复结果会写入 `resume_evaluated` trace，并进入工作记忆的恢复上下文。恢复判断不会删除旧 history 或 artifact，只负责告诉模型哪些状态可能已经过期。

## 十、证据和可观测性

每次运行都会在 `.jcode/runs/<run_id>/` 下产生：

```text
trace.jsonl          逐事件审计
task_state.json      当前任务状态
checkpoint.json      可恢复状态
report.json          运行汇总
artifacts/           大工具结果
```

与上下文治理直接相关的 trace 事件包括：

| 事件 | 记录内容 |
| --- | --- |
| `context_built` | 最终上下文全文和 `ctx_info` |
| `compact_evaluated` | 压力等级、是否需要压缩、压缩状态 |
| `compact_triggered` | 触发原因和保留 turn 数 |
| `compact_completed` | 语义摘要成功结果 |
| `compact_fallback` | LLM 摘要失败及确定性摘要结果 |
| `compact_history_audit` | 摘要 prompt、response、来源和摘要全文 |
| `model_responded` | 模型原始输出和 token 估算 |
| `model_parsed` | 解析出的动作 |
| `model_parse_failed` | 协议失败时的原始输出和错误 |
| `tool_requested` | 工具名和原始参数 |
| `tool_executed` | 工具结果、状态、错误和变更 |
| `checkpoint_created` | 检查点创建时机 |
| `memory_maintained` | Daily Log 和 Durable Memory 整理结果 |

Web 层通过 session event 流把这些事件聚合成 turn 和步骤时间线。`context_built` 的上下文全文会挂到对应步骤，因而可以直接检查某一轮模型实际看到的 prompt，而不只是查看最终答案。

## 十一、当前治理边界

- 上下文压力使用字符近似 token，不是 Provider 返回的精确 token 计数。
- 压力等级先按初始文本计算，压缩后再计算最终压力；如果最终仍然偏高，当前实现不会无限递归压缩。
- `tail_clip()` 保留尾部，可能截断段落开头的背景信息。
- 渲染级工具压缩不修改 session history；只有等级 4 的 `compact_history()` 会永久移除旧 turn，并保存摘要替代。
- compact summary 不携带原始文件 freshness，也不会参与 stale 标记；摘要中的旧事实需要模型结合当前文件重新验证。
- Daily Log 和 Durable Memory 是回合结束阶段的语义沉淀，不是当前轮历史的替代品。
- checkpoint 只保存恢复所需状态，不保存完整 context 文本；完整 context 由 `context_built` trace 保存。
- 旧 session 不做协议兼容式回退；缺少结构化 assistant 时，历史渲染使用空 assistant 内容。

## 十二、排查入口

遇到“模型看到的上下文不对”时，建议按以下顺序检查：

1. 查看 `.jcode/runs/<run_id>/trace.jsonl` 中最后一次 `context_built`，确认最终 prompt、压力等级和压缩记录。
2. 对照同一 run 的 `compact_*` 事件，判断是否发生了历史语义压缩或摘要 fallback。
3. 检查 session JSON 的 `history`、`working_memory` 和 `ctx_info`，确认源数据是否已经被修改或标记 stale。
4. 检查 `model_responded` 和 `model_parse_failed`，区分模型没有看到信息、模型输出协议错误和动作解析错误。
5. 对工具证据检查 `tool_requested`、`tool_executed`、history item 的 `args`、`metadata.source_files` 和 `metadata.stale`。
6. 若是恢复任务，再检查 `checkpoint.json` 与 `resume_evaluated` 的 workspace fingerprint 和 stale paths。
