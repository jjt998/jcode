# 会话延续与执行环境一致性实施计划

## 1. 实施范围

本计划实现《改进方案/2026-09-08-会话延续与执行环境一致性改进方案.md》冻结的产品语义：同一会话第二次及之后的发送与启动恢复统一视为 `session continuation`，统一评估 workspace、文件 freshness、execution fingerprint 和 Provider continuation；stale 只标记旧证据失效，不删除历史。

## 2. 阶段一：统一会话延续入口

### 目标

把启动恢复和会话内后续发送接入同一个 evaluator，建立第一次 run 基线、后续 run 评估的明确边界。

### 任务

1. 在 `src/state/resume.py` 抽取 `SessionContinuationEvaluator`，输入 session、上一 run、workspace 和当前执行环境，输出结构化评估结果。
2. 保留 `build_resume_context()` 作为统一 evaluator 的结果适配入口，不再复制另一套判断逻辑。
3. 在 `JCodeAgent._begin_run()` 创建新 `TaskState` 前判断是否已有历史 run；有则执行 evaluator。
4. `bootstrap.py` 启动加载已有 session 后复用同一 evaluator，不单独实现恢复规则。
5. 第一次发送只建立基线，不产生误导性的 mismatch 状态。
6. 将评估结果写入当前 run 的 trace、session event 和 Working Memory。

### 验收

- 新 session 第一次发送状态为 `new_session`。
- 同一进程第二次、第三次发送均执行 evaluator。
- 重启后加载旧 session 的第一次发送与进程内后续发送产生同类评估结构。
- 每次发送仍产生新的 `run_id`。

## 3. 阶段二：统一 stale 标记

### 目标

让 JCode 自己修改和外部工作区变化共享同一个 stale 入口。

### 任务

1. 保留 `JCodeAgent._mark_stale_file_evidence()` 的现有行为。
2. 将参数统一命名为 `changed_paths`，明确只接受路径集合/列表。
3. JCode 自己 `write_file`、`apply_patch` 成功后继续调用该方法。
4. evaluator 比较 workspace/freshness 后，将 `changed_paths` 传入同一方法。
5. 保持 history、artifact 和 Working Memory 原始记录，不新增 stale 索引。
6. 在上下文前缀和 Working Memory 中继续明确要求重新读取 stale 文件。

### 验收

- JCode 修改文件会标记对应旧 `read_file/search` 事件 stale。
- IDE 或脚本外部修改 hot 文件后，后续发送也会标记同样的旧事件 stale。
- 未受影响的读取证据不被标记。
- stale 后旧历史和 artifact 仍可审计、可参与摘要输入。

## 4. 阶段三：Workspace baseline

### 目标

替换当前浅层、前 200 个一级条目的 fingerprint，建立可解释的递归工作区基线。

### 任务

1. 在 `src/state/workspace.py` 增加结构化 workspace baseline 构建函数。
2. 递归收集 workspace 相对路径、文件大小和 `mtime_ns`，排除 `.jcode`。
3. 同时记录 Git HEAD、branch 和 status；Git 不可用时保留明确的不可用状态。
4. 对 hot 文件、当前 run 读写文件、`AGENTS.md`、`JCODE.md` 和项目配置增加内容 hash。
5. checkpoint 保存结构化 baseline 及整体 hash。
6. evaluator 对比上一 run baseline 与当前 baseline，输出 `changed_paths`。
7. 文件不存在、权限不可读和索引失败必须返回明确状态，不静默当作未变化。

### 验收

- 嵌套文件变化能够被发现。
- 新增、删除和移动文件能够被发现。
- 超过 200 个一级条目的文件变化不会漏检。
- 外部修改 hot 文件能够产出 `changed_paths` 和 `stale_paths`。
- `.jcode` 内部文件变化不会污染普通 workspace baseline。

## 5. 阶段四：Execution fingerprint

### 目标

让 checkpoint 能判断当前执行环境是否与生成 checkpoint 时兼容。

### 任务

1. 增加 execution fingerprint 构建函数，使用当前实际模型 profile 和 Provider 配置。
2. 收集 provider、model profile、模型名称/版本、reasoning 开关、reasoning effort、Provider 协议。
3. 基于实际暴露给模型的工具 schema 规范序列化并计算 `tool_schema_hash`。
4. 增加 runtime protocol 和 context policy 版本字段。
5. checkpoint 保存结构化 execution fingerprint。
6. evaluator 输出逐字段差异，不能只返回一个不可解释的 mismatch。

### 验收

- 同 Provider、同模型、同配置返回兼容。
- 切换模型、Provider、reasoning 开关或 effort 时产生对应差异字段。
- 工具 schema 变化能够被识别。
- 协议或上下文策略版本变化能够被识别。

## 6. 阶段五：Continuation 兼容性

### 目标

防止不兼容执行环境继续使用旧的 Provider 原生 continuation。

### 任务

1. checkpoint 明确保存是否存在未完成 `provider_continuation`。
2. evaluator 根据 execution fingerprint 和 continuation 类型判断兼容性。
3. 有未完成 continuation 且 Provider、协议、工具 schema 或模型能力不兼容时，返回 `continuation_incompatible`。
4. 无未完成 continuation 时，模型变化只记录 mismatch，不阻止创建新 run。
5. 保持新的 `_begin_run()` 默认创建新的 `TaskState`，不直接继承旧 continuation。
6. 对未闭合 function call/tool output 执行严格 call id 校验，禁止降级发送。

### 验收

- 无 continuation 时切换模型可以开启新的 session continuation run。
- 有 continuation 时切换 Provider 或工具 schema 不会继续旧调用链。
- 兼容 continuation 恢复时 reasoning/tool item 和 call id 不丢失。

## 7. 阶段六：Working Memory、事件与前端审计

### 目标

让恢复状态在模型、trace 和 Web 页面中一致可见。

### 任务

1. 修复 `WorkingMemory.render()` 中 `resume_context` 被覆盖的问题。
2. 用稳定字段渲染 continuation、workspace、stale 和 execution 状态。
3. 新增并规范 `session_continuation_evaluated`、`workspace_baseline_evaluated`、`workspace_changed_detected`、`execution_fingerprint_evaluated`、`continuation_compatibility_evaluated` 事件。
4. Web 时间线展示状态和差异，但不把完整 checkpoint JSON 嵌入普通消息。
5. 历史正文、artifact 和 stale 标记保持审计可追溯。

### 验收

- 模型可见 Working Memory 包含实际恢复评估结果。
- Web 和 trace 展示相同的状态与 changed paths。
- 新事件不会破坏已有未知事件过滤规则。

## 9. 测试矩阵

### 会话链路

- 新 session 第一次发送。
- 同进程第二次和第三次发送。
- 重启后恢复 session 再发送。
- 无 checkpoint 但存在历史 run。
- checkpoint 不可恢复或 schema 不匹配。

### Workspace

- 工作区一致。
- 一级文件、嵌套文件修改。
- 新增、删除、移动文件。
- 外部修改 hot 文件。
- 外部修改非 hot 文件。
- Git HEAD、branch、status 变化。
- JCode 自己 write/patch 后变化。
- 文件权限/索引异常。

### stale

- changed paths 通过统一入口标记旧 read/search 结果。
- 同一路径多条旧证据全部标记。
- 未受影响路径不标记。
- stale 不删除 history、artifact 和 Working Memory。
- stale 证据仍可参与摘要，但不能被当作当前事实。

### Execution fingerprint

- 同模型同配置。
- 切换 model profile。
- 切换 Provider。
- reasoning 开关变化。
- reasoning effort 变化。
- 工具 schema 变化。
- Provider 协议变化。
- context policy/runtime protocol 变化。

### Continuation

- 无 continuation 时模型变化允许新 run。
- 有 reasoning continuation 时模型变化被拒绝继续。
- 有 tool continuation 时工具 schema 变化被拒绝继续。
- Provider 变化时旧 continuation 不发送。
- 兼容 continuation 保持 call id 闭环。

## 10. 失败语义

- workspace 变化：允许新的 session continuation run，但标记 stale 并要求重新读取。
- execution mismatch：允许新的 session continuation run，但写入差异审计。
- continuation incompatible：停止旧 continuation 恢复，不伪造兼容，不自动降级。
- workspace baseline 无法读取：返回明确的系统状态，不当作 `full_valid`。
- schema/protocol 不兼容：按既定 runtime stop 语义停止。

任何阶段都不得新增静默删除、模糊恢复、自动替换、吞掉异常或降低校验标准的兜底逻辑。

## 11. 实施顺序与交付物

1. 阶段一、二：统一入口和 stale 标记；交付 evaluator 初版与会话链路测试。
2. 阶段三：递归 workspace baseline；交付外部变化检测测试。
3. 阶段四、五：execution fingerprint 与 continuation 兼容性；交付模型切换评测集。
4. 阶段六：Working Memory、事件和 Web 审计；交付端到端展示测试。
5. 运行项目完整测试集，确认旧历史未被删除、旧 continuation 未被不兼容复用。

## 12. 完成标准

- 启动恢复和会话内后续发送只使用一套 continuation evaluator。
- JCode 自己修改和外部修改都通过同一个 stale 标记方法。
- stale 不删除任何历史或 artifact。
- workspace 和 execution baseline 可解释、可审计。
- 不兼容的 Provider continuation 不会继续执行。
- 全部测试通过，事件、Working Memory、trace 和 Web 展示语义一致。
