# JCode 上下文治理改进策略 9.5：细节讨论议程

本文记录总策略逐项讨论后的冻结结论，作为编码前的细节规格。history、Working Memory、Skills、预算、摘要事务和 runtime 异常边界均以本文的已确认规则为准；明确后置的范围不得在 9.5 验收中宣称已经支持。

## 1. 已确认的总边界

- 统一最大上下文窗口：375000 token。
- `max_new_tokens` 默认值：16384；实际值允许由 `.jcode.toml` 和 CLI 覆盖。
- safety margin：7500 token，占总窗口 5%，不可被普通 section 使用。
- instructions 完全固定，不压缩，先作为固定占用扣除。
- tools schema 完全固定，不压缩，先作为固定占用扣除；未来可作为独立策略移出固定占用。
- provider continuation 按 reasoning 和 tool 原生项拆分固定计量；非思考模式只释放 reasoning 占用，工具调用闭环仍按实际内容计量。
- 不再设置独立 current request section。当前 user event 保留在 history，`working_memory.core.task_goal` 同时保存相同用户请求完整原文，两份都不可压缩。
- 压力等级继续使用 0-4 档：60%、75%、85%、95%。
- section 使用动态预算，不使用固定比例。
- 压缩后必须重新编译和重新估算最终 Provider 请求。
- `95%` 只触发 Level 4；压缩后只按最终容量公式判断是否发送，不以最终压力仍处于 Level 4 为拒绝条件。
- Level 0/1/2/3/4 的总体窗口和文件数量规则已确定。

## 2. History 细节讨论

### 2.0 已确认的 History 规则

- 一个 history turn 等于一次用户请求对应的完整运行。
- 当前 turn 在运行结束前完整保留，不进行历史压缩，并计入各等级的 history 总窗口。
- 当前 turn 内的失败工具结果仍属于当前 turn，runtime 应在同一 turn 内继续处理。
- 不维护跨 turn 的 unresolved history 或失败优先队列。
- `completed`、`stopped`、`aborted`、`failed` turn 离开当前状态后按相同旧 turn 规则处理。
- 工具调用和对应工具结果是不可拆分的结构原子，但失败状态不额外提高历史优先级。
- 原始完整窗口为：Level 0 保留 7 个 turn，Level 1 保留 5 个，Level 2 保留 4 个，Level 3/4 保留 3 个；数量均包含当前 turn，不再另加。Level 0 不做裁剪，因此 7-turn 只是最近原始窗口边界，容量允许时窗口外旧 turn 也原样发送。
- Level 1-3 窗口外 `tool_result` 按 Python 字符数严格使用“首 400 + 全文正中心 100 + 尾 400”规则，不做换行边界调整。
- `list_files` 是 400/100/400 的例外：窗口内全部完整保留，窗口外按规范化 path 只保留最后一次完整调用及结果。
- 窗口外 `user`、`assistant` 和 `tool_call` 暂不压缩；后续若 assistant 过程文本成为主要膨胀来源，再增加独立规则。
- `write_file.content`、`apply_patch.old_text`、`apply_patch.new_text` 超过 2000 字符时，窗口外使用“artifact + 前 100 + 后 100”字段级摘要；窗口内完整保留。
- session 原始参数始终合法、完整地保存；只有 Provider history 视图替换超大正文，替换值仍是合法 JSON 字符串。
- session 原始 history 不因 request-level 压缩而改写；Level 4 的语义摘要才是持久化历史压缩动作。

### 2.1 turn 的定义

以下实现边界已经固定：

```text
user
assistant
tool_call
tool_result
assistant continuation
```

- 当前尚未闭合的工具调用链始终属于当前 turn。
- 一个模型响应包含多个工具调用时仍属于同一个 turn。
- Provider continuation 在预算中与普通 history 分开计量，但在 turn 语义上仍属于当前 turn。
- `completed`、`stopped`、`aborted`、`failed` 或 `suspended` 会闭合当前 turn；闭合后统一按旧 turn 规则处理。
- 当前 turn 中已由 continuation 承载的 reasoning、function call 和 function output 不从普通 history 重复发送。

### 2.2 当前窗口的原始保留

总策略已经确定各等级的原始窗口：

```text
Level 0: 7 turns
Level 1: 5 turns
Level 2: 4 turns
Level 3: 3 turns
Level 4: 3 turns
```

窗口按 session 事件顺序选择，不按 turn ID 字典序或时间字符串重新排序。当前任务涉及的文件不能使旧 turn 突破窗口；相关事实由 Working Memory 文件索引保护。当前 turn 的全部实际发送内容，包括错误结果，都完整保留并归入固定占用；其自身导致窗口无法容纳时返回 `mandatory_context_exceeds_window`。

### 2.3 窗口外工具结果压缩

Level 1-3 的统一正文规则为：

```text
首 400 字符 + 中间 100 字符 + 尾 400 字符
```

以下实现细节已经确认：

- 400/100/400 使用 Python 字符。
- 中间片段取全文正中心 100 个字符。
- 严格字符窗口，不做换行边界调整。
- 多行代码不按完整行边界调整，严格使用 Python 字符位置。
- 工具状态、错误类型、退出码、changed_files、artifact 路径、读取完整性和 source freshness 保留在结构化 metadata。
- artifact 路径保留在结构化 metadata，不依赖正文头尾解析。
- 每次请求都从原始 session 账本生成 Provider 投影，不对上一次已经压缩的投影再次压缩。

`list_files` 专用规则：

- 工具本身只有 `max_entries`，不增加 `max_chars`。
- 当前完整窗口内所有 `list_files` 的 `tool_call + tool_result` 原样保留。
- 旧窗口按规范化 path 分组，每个 path 只保留 session 事件顺序中的最后一组完整调用原子。
- `recursive` 和 `max_entries` 不参与合并键；最后一次失败或中止同样替换旧成功快照。
- 被淘汰的 `tool_call` 和对应 `tool_result` 必须按 call ID 成对移除。
- 完整结果不受通用 inline 阈值限制，不因长度自动外置为 artifact，但仍参与最终 token 校验。
- `list_files` 不产生文件 freshness、`read_ranges` 或 `covered_ranges`。

### 2.4 大型工具调用参数

以下规则已确认：

- `write_file.content`、`apply_patch.old_text`、`apply_patch.new_text` 共享 2000 字符阈值。
- 窗口内完整保留，窗口外只替换 Provider 视图。
- 原始正文保存到 artifact，Provider 参数值使用带 artifact 和摘要的合法字符串。
- session 原始 history 不改写。
- git、当前文件和 artifact 都可用于模型验证历史修改。

artifact 命名和根目录已确认；创建时机、完整性校验和字段级审计信息按 3.8 规则执行。

### 2.5 Level 4 语义摘要

摘要固定保留以下事实字段：


```text
summary_version
task_goal
decisions
files_read
files_modified
key_findings
tool_failures
freshness_events
unresolved_blockers
next_steps
artifact_paths
```

Level 4 只摘要 3-turn 原始窗口之外的旧 turn；该窗口包含当前 turn，因此最多额外保留最近 2 个已闭合 turn。使用模型生成结构化 JSON，按任务阶段分组，并持久化覆盖活动 Provider history。

摘要按任务阶段组织。`freshness_events` 只记录实际的 freshness 变化，不复制读取覆盖。摘要基于上一版 compact summary 与新淘汰 turns 增量更新；摘要损坏或版本不兼容时由 `compact_summary_rebuild_on` 控制是否从原始 history artifact 重建，关闭时记录 `compact_summary_hurt=true` 和 `compact_summary_rebuild_on=false`。

摘要模型单次超时 `120` 秒，首次失败后最多额外重试两次，总共最多调用 3 次，指数退避为 `2s -> 4s`，理论最坏时长约 366 秒；仍失败再使用确定性结构摘要，仍超限则另开会话。artifact 完整性异常不参与重试。

摘要请求单独满足 `summary_input_tokens + summary_output_reservation + safety_margin_tokens <= effective_context_window_tokens`。它不携带工具、普通 Working Memory 或 continuation，只包含摘要 instructions、合法旧摘要和本次新淘汰的旧 turn。实际输出预留不超过本轮 `actual_max_new_tokens`；可用输出低于 2048 token 时跳过模型摘要，直接使用确定性结构摘要。

确定性结构摘要已确认采用“结构化聚合 + 合法旧摘要字段继承”：`summary_version`、`task_goal`、`files_read`、`files_modified`、`tool_failures`、`freshness_events`、`unresolved_blockers`、`artifact_paths` 仅从结构化元数据聚合；`decisions`、`key_findings`、`next_steps` 只继承合法旧摘要中无冲突字段，缺少可靠来源时为空。不得从普通 assistant 文本推断新事实。

生成顺序固定为：读取旧摘要并按 `compact_summary_rebuild_on` 处理无效版本；收集新淘汰 turn 的结构化事件；按字段来源聚合且不读取正文；去重文件、artifact 和工具 ID；以最新 freshness 和工具状态覆盖旧状态；冲突只保留最新事实；输出固定 JSON schema；校验 JSON、schema、字段类型和 artifact 路径。校验失败时不发送 Provider 请求，直接另开会话。

数组元素必须使用短结构对象，不生成长段落，不使用“可能”“推测”“应该”等推理词；不得将工具失败视为任务失败、写入正文视为读取事实或旧 freshness 视为当前 freshness。`artifact_paths` 只保存裸路径。

持久化顺序固定为：复制原始 history，写只读 history artifact，重新读取并校验 SHA-256，生成并校验摘要，用候选 history 构建最终 `ContextResult` 并校验容量，再将 session 副本写入同目录临时文件并 flush，使用 `os.replace()` 原子替换，最后更新内存 session。`ContextManager` 不得直接改写活动 session。提交失败时旧 session 保持有效；允许留下无引用 history artifact。

## 3. Working Memory 细节讨论

### 3.1 逻辑结构

计划将文件相关状态合并为统一文件索引，避免 `recent_files`、`file_freshness` 和 `file_reads` 三套结构互相漂移：

```text
files
├── hot
├── cold
└── file metadata
```

单个文件版本至少包含：

```text
path
current_freshness
file_size
last_access_order
versions
  ranges
    start
    end
    max_chars
    returned_chars
    missing_chars
    complete
    read_count
```

文件索引规则已经确定：

- 每个文件只保留当前 freshness 和上一 stale freshness，不保留全部历史版本。
- Provider 只展示当前 freshness；上一 stale 版本只作为持久化索引和审计依据。
- 同一范围每次成功重复读取都会刷新 `last_access_order`，但 `covered_ranges` 合并结果不重复扩张。
- 文件修改后旧范围保留在上一 stale 版本，不得继续作为当前读取证据展示。
- `search` 扫描来源进入同一个文件索引，只记录扫描 freshness，不产生读取覆盖。

已确认的版本刷新规则：

- `write_file` 或 `apply_patch` 成功后，必须刷新目标文件的当前 freshness。
- 新 freshness 建立新的读取记录，旧版本的 `read_ranges` 和 `covered_ranges` 不得继续沿用。
- 写入动作本身不等价于重新读取，不得把写入正文自动标记为当前文件的已读覆盖。
- 当前文件记录可以保留“刚刚被修改”的动作元数据，但需要重新 `read_file` 才能获得当前版本的读取证据。

### 3.2 Working Memory 核心字段

Working Memory 固定分为：

```text
core
  task_goal
  constraints
  active files
  current file versions
  incomplete reads
  pending todos
  unresolved safety state

auxiliary
  tool observations
  retrieved memory
  subagent results
  resume details
  old compact metadata
```

`task_goal` 保存当前用户请求完整原文，与当前 turn 的 user history event 使用同一个原文快照；它属于固定占用，不受 Working Memory 最低保障和压力裁剪。其他 core 字段根据压力等级和候选优先级保留，不具有无限制固定占用。auxiliary 按检索结果、已结束工具观察、旧恢复细节和旧 compact metadata 的顺序逐步淘汰；活动状态优先于已结束状态。

后续工具循环和输出截断续写必须继续使用原始 task goal，不得用内部 `continue` 请求覆盖。审计按最终 Provider 输入的实际 token 正常计量，不增加“重复用户请求”专用字段。

冷文件索引至少保留 path、current freshness、上一 stale freshness、file size、covered ranges、完整性、last access order 和 last modified time，但不进入当前 Provider Working Memory。Working Memory 不设置 maximum 或 preferred 子预算；它具有 4096 token 的实际最低保障，满足后与其他 section 候选竞争全局余量。

### 3.3 热文件晋升与冷文件归档

热文件数量规则已经确定：

```text
Level 0: 30
Level 1: 20
Level 2: 16
Level 3: 12
Level 4: 12
```

排序评分已确认，使用字典序：

```text
(
    user_mentioned,
    modified_in_current_run,
    current_freshness,
    incomplete_read,
    last_access_order,
    last_modified_time,
    task_relevance,
    normalized_path
)
```

用户明确提及的文件全部强制进入 hot，允许超过 nominal hot 上限；其他文件降级。冷文件仅保留索引，不进入 Provider Working Memory，也不占用本轮模型输入预算。

### 3.4 非文件型工具观察

`run_shell`、`ask_user` 和 `todo` 放在 `tool_observations`，记录内容改为可审计的结构化元数据，不再生成泛化的 `content_summary` 或 `output_summary`。`list_files` 只在观察中记录状态和参数，完整目录正文由 history 或 continuation 提供。

统一记录外壳：

```text
observation_id
turn_id
call_id
tool_name
status                 # pending/succeeded/failed/aborted
started_at
finished_at
duration_ms
arguments              # 规范化参数；敏感值脱敏
result
  return_code
  signal
  error_type
  error_message_ref
  result_artifact
  result_bytes
  result_chars
  result_hash
provenance
  run_id
  provider_call_id
```

完整正文只保存在 artifact。小型标量结果可以使用 `storage=inline` 直接记录；大参数或大结果使用 artifact 引用、长度和 hash 定位，原始值仍保存在 session 原始记录中。`list_files` 完整结果是不受通用 inline 阈值和自动 artifact 外置影响的明确例外。

工具专用字段：

- `run_shell`：命令摘要/hash、workspace 派生 cwd、`timeout`、`return_code`、`signal`、统一输出 artifact 和输出长度；当前 schema 没有 env 参数，不虚构 `env_keys`。
- `ask_user`：`question`、`choices`、`answer`、`selected_choice`、`response_status`。
- `todo`：`operation`、`todo_id`、`title`、`priority`、`todo_status`、`changed_ids`、`remaining_count`、`snapshot_artifact`。
- `list_files`：`path`、`recursive`、`max_entries` 和执行状态，不复制目录正文。

按压力等级的非文件观察视图：

- Level 0：保留选中的全部观察记录和全部结构化字段。
- Level 1：仍保留全部结构化字段；大参数只显示 artifact 引用、长度和 hash。
- Level 2：按逻辑对象合并连续状态，保留首次创建信息、最新状态和全部 artifact 引用。
- Level 3：每个逻辑对象只保留最新状态、失败/中止状态字段和结果 artifact 引用。
- Level 4：只保留当前 turn 观察、未完成 todo 和未回答问题；已结束对象只保留审计索引。Level 4 不再做更高级的非文件观察压缩，语义压缩只针对 history。

逻辑对象和合并边界已确认：

- `run_shell` 按 `call_id` 标识；不同调用即使命令文本相同也不得合并，必须分别保留返回码、执行时间和 artifact 关系。
- `ask_user` 按 `question_id` 标识。
- `todo` 按 `todo_id` 标识。
- 同一逻辑对象的合并结果保留首次创建信息、最新状态、状态变更次数、全部 artifact 引用和最新错误元数据。
- 展示顺序按最近活动时间倒序；当前 turn 的活动对象优先展示。这是展示排序，不改变旧 turn 的历史优先级。

`enter_plan_mode` 和 `exit_plan_mode` 只更新 `working_memory.runtime_state`，不进入 `tool_observations`；History 仍保留对应调用原子。`runtime_state` 只展示最终 `mode`、`topic` 和 `plan_path`，不重复模式切换过程。

`spawn_subagent`、`send_subagent_message`、`wait_subagent` 暂不定义生命周期压缩、对象合并、参数外置和 Working Memory 投影。本次只保留现有执行能力与 history 调用原子，并在三个 tool definition 旁添加中文缺口注释。

### 3.5 原始账本与 Provider 视图

- session 原始 history、原始工具参数和完整观察元数据组成不可变的原始事实账本。
- 每次请求根据本次压力等级，从原始账本重新生成 Provider 视图；不得把上一次压缩后的视图作为下一次压缩的输入。
- 因此压力从 Level 4 降到 Level 1 时，可以重新展示原始账本中仍存在的完整结构化参数；Level 2 的大参数 artifact 引用也可以在 Level 1 恢复为完整参数。这不是历史倒退，而是同一事实账本的低压视图展开。
- 如果 Level 4 的 history 语义摘要已经替换活动 history，则 Provider 视图不会自动恢复被替换的原文；只有 `compact_summary_rebuild_on=true` 的重建流程可以从只读 history artifact 重新生成摘要。

### 3.6 单次定档与终极超限拦截

1. 使用未压缩的完整候选上下文计算压力等级。
2. 只执行该等级对应的一次压缩规则：Level 0 和 Level 1 不压缩结构化非文件字段；Level 2 只处理大参数；Level 3 合并逻辑对象；Level 4 只保留最新状态。
3. 用压缩后的候选重新估算最终 Provider 请求。
4. 所有等级都不因最终压力变化重新升档；最终容量公式成立就直接发送。
5. Level 4 压缩后即使仍处于 Level 4 也允许发送，只有最终容量公式不成立时才返回“当前已无剩余上下文空间，请你另开会话吧”。

拦截路径必须留下注释和审计字段，说明：已按 Level 4 完成语义压缩、已重新估算、仍无法在 375000 token 窗口内容纳请求，因此要求另开会话。

### 3.7 Working Memory 已确认决策汇总

以下规则已经确认，后续实现必须以此为准：

#### 全局预算关系

- Working Memory 不设置 maximum 或 preferred 子预算，只设置 4096 token 最低保障。
- 最低保障实际取 `min(raw_working_memory_demand, 4096)`，不预留空额度；满足后继续参与跨 section 候选竞争。
- “预算不足”专指最终 Provider 输入、实际输出预留和 safety margin 超过有效模型窗口，不是 Working Memory 局部预算不足。
- 所有等级都只执行原始压力对应的一次规则，不因为压缩后压力变化重新定档。
- `95%` 只触发 Level 4；Level 4 只有最终容量公式不成立时才触发另开会话拦截。

#### 文件索引与 freshness

- `read_file`、`search`、`write_file`、`apply_patch` 统一进入 `files`；`list_files` 是不产生 freshness 或读取覆盖的目录快照；plan mode 工具进入 `runtime_state`。
- 同一文件的不同 freshness 不得同时展示；只展示最新 freshness 版本。
- 文件 freshness 变化后，旧版本的 `read_ranges` 和 `covered_ranges` 不得继承。
- `write_file` 或 `apply_patch` 成功后必须重新读取文件或刷新 freshness；写入正文不等价于读取证据。
- `read_file` 使用双层读取记录：`read_ranges` 保存每次成功读取的精确半开区间，`covered_ranges` 保存累计合并覆盖区间。
- 读取区间使用 Python 字符偏移；实际覆盖末端使用 `start + returned_chars`，不能直接使用请求的 `end`。
- 当前用户请求中明确提到的文件优先进入 hot 候选；hot 容量不足时先淘汰其他低优先级文件，不能淘汰被明确提及的文件。
- hot 文件数量按压力等级为：Level 0 为 30，Level 1 为 20，Level 2 为 16，Level 3 为 12，Level 4 为 12。
- 普通工作区文件与 `.jcode/runs/.../artifacts/` 中已经存在的 artifact 都不再通过 `read_file` 二次外置到 artifact，直接允许分段读取。

#### 非文件型观察

- 非文件型观察在本次协议中包括 `run_shell`、`ask_user`、`todo`，以及不复制正文的 `list_files` 状态索引。
- 观察记录使用具体元数据，不再记录泛化的 `content_summary` 或 `output_summary`。
- 原始记录至少包含工具身份、turn/call 标识、状态、完整参数、结果状态、返回码或错误类型、结果尺寸/hash、artifact 引用和 provenance；Provider 视图不直接展示参数正文。
- 完整正文只以 inline 小结果或 artifact 形式存在；Working Memory 不把自然语言摘要作为正文替代品。`list_files` 完整目录结果由 history/continuation 原样提供。
- `run_shell` 按 `call_id` 标识；不同调用即使命令文本相同也不得合并，必须分别保留返回码、执行时间和 artifact 关系。
- `ask_user` 按 `question_id` 标识，`todo` 按 `todo_id` 标识。
- 同一逻辑对象的合并结果保留首次创建信息、最新状态、状态变更次数、全部 artifact 引用和最新错误元数据。
- 观察展示按最近活动时间倒序，当前 turn 的活动对象优先；这只是展示排序，不改变旧 turn 的历史优先级。
- 非文件观察的压力等级规则为：Level 0 和 Level 1 保留全部选中的结构化字段；Level 2 合并逻辑对象状态并保留首次信息、最新状态和全部 artifact 引用；Level 3 每个逻辑对象只保留最新状态和结果引用；Level 4 只保留当前 turn 观察及仍有效的逻辑对象，已结束对象仅保留审计索引。
- 大型正文写入 artifact 失败属于系统故障，必须抛出明确的 `ArtifactWriteFailureError`，异常消息固定包含“artifact写入失败”。本次运行立即结束，不降级为摘要、缺失引用或继续发送 Provider 请求；控制台必须输出该异常。
- 非文件观察采用单向状态机：`pending -> succeeded`、`pending -> failed`、`pending -> aborted`。`run_shell` 非零返回码是工具业务失败，记录为 `failed` 后运行继续；超时、用户取消等记录为 `aborted`；部分 stdout/stderr 仍保留 artifact；未回答的 `ask_user` 保持 `pending`。终态不可覆盖，重试必须使用新的 `call_id`。`ArtifactWriteFailureError` 是 harness 系统异常，不属于工具业务状态，发生后立即终止运行。
- 非文件观察展示采用双区顺序：当前 turn 的观察按实际事件时间正序保留，保证模型能还原执行过程；跨 turn 的逻辑对象按 `last_event_at` 倒序展示，活动对象优先于终态对象。该展示顺序已确认；排序只影响 Provider 视图，不改变原始账本和历史优先级。
- 非文件观察候选集合已确认：当前 turn 的全部观察事件进入 Working Memory；跨 turn 每个逻辑对象只展示最新状态，仍活动对象必须保留；创建信息、状态变更次数和全部 artifact 引用作为最新记录字段保留；更早事件仅保存在原始 session/history，不在 Working Memory 重复展开。该语义去重不构成局部 token 配额。
- 非文件观察参数展示协议已确认：原始参数完整、合法、不可变地保存在 session；Provider 视图的 `args` 按工具协议展示最小必要字段，大参数正文和敏感字段以 artifact 裸路径及必要的长度/hash 定位信息替代。参数 artifact 化不受压力等级影响。
- artifact 引用使用裸路径字符串，不包装为 `artifact_ref` 对象。尺寸、字符数、hash、来源 `call_id` 等仍作为观察记录的并列元数据保存；Provider 视图直接展示 artifact 路径。
- Working Memory 的非文件观察采用统一精简外壳：`current_turn` 项包含 `tool`、`id`、`status`、`args`、`result.details`、`result.artifacts`；`previous` 项包含 `tool`、`id`、`status`、`latest`、`artifacts`。工具专用关键结果放在 `result.details`，不扩散为顶层字段；完整审计字段只保留在原始 session。
- `result.details` 最小字段已确认：`run_shell` 使用 `return_code`、`signal`；`ask_user` 使用 `response_status`、`selected_choice`、`answer`；`todo` 使用 `operation`、`todo_status`、`remaining_count`；`list_files` 使用 `path`、`recursive`、`max_entries` 和执行状态。完整正文、错误正文和大型输出只通过 `result.artifacts` 引用，`list_files` 完整结果除外；压力等级只裁剪记录和对象，不改写这些事实字段。

#### 原始账本与 Provider 视图

- session 原始 history、原始工具参数和完整观察元数据组成不可变的原始事实账本。
- 每次请求都从原始账本重新生成 Provider Working Memory 视图，不得把上一次压缩后的视图作为下一次压缩输入。
- 因此压力从 Level 4 降到 Level 1 时，可以重新展示原始账本中仍存在的完整结构化参数；Level 2 的 artifact 引用也可以在 Level 1 展开为完整参数。
- 这属于同一事实账本的视图展开，不是历史倒退。
- 如果 Level 4 history 语义摘要已经持久化并删除中间原文，被删除的历史事实不可恢复，只能使用摘要和 artifact 引用。

### 3.8 新增边界决策

- 参数暴露按当前 `src/tools/schemas.py` 区分：`read_file` 展示 path、start、end、max_chars；`list_files` 展示 path、recursive、max_entries 并完整返回目录结果；`search` 展示 path、query、max_results，超长 query 使用 artifact，本次不新增 glob/正则；`write_file` 展示 path 以及派生的 UTF-8、replace、正文长度/hash，仅窗口外超过 2000 字符的 content 使用 artifact 投影；`apply_patch` 展示 path 以及派生的单次 exact 操作、old/new 长度/hash，仅窗口外超过 2000 字符的 old_text/new_text 使用 artifact 投影；`run_shell` 展示 workspace 派生 cwd、timeout、命令摘要和 hash，完整 command 使用 artifact，当前工具没有 env 参数；`ask_user` 的参数展示 question/choices，answer/status 属于结果，secret 回答使用 artifact；todo 按具体操作展示 todo_id、content、priority、status、note，超长 content/note 使用 artifact；`enter_plan_mode` 展示 topic/path；`exit_plan_mode` 无参数。三个子 Agent 工具的参数暴露暂不定义。
- 参数 artifact 使用 `.jcode/runs/<run_id>/artifacts/parameters/<sequence>-<kind>.<ext>`；路径不含用户输入、凭据或完整命令。Provider 可以直接用 `read_file` 读取，且不得路径逃逸。
- artifact 失效区分 `ArtifactUnavailableError` 与 `ArtifactIntegrityError`；当前运行中立即终止，历史回放只显示 `artifact_status=unavailable`。
- Level 4 摘要模型单次超时 120 秒，首次失败后额外重试两次，等待 `2s -> 4s`；随后使用确定性结构摘要，仍超限则另开会话，不退回 Level 3。摘要持久化使用 history artifact 校验和 session 原子替换。
- section 的实际最低保障之和超过 flexible budget 时，直接返回 `system_minimum_budget_overflow`，不静默溢出或整体截断；实际保障取原始需求与配置最低值的较小值。
- 候选稳定排序使用 `(user_mentioned, modified_in_current_run, current_freshness, incomplete_read, last_access_order, last_modified_time, task_relevance, normalized_path)` 字典序；用户明确提及的文件全部强制进入 hot，允许超过 nominal 上限。
- 一个 turn 包含一次用户请求及其全部 assistant 响应、tool call/result 和 continuation；多工具响应仍属同一 turn。最终回答、用户中止、runtime 终止或进入 suspended 时闭合。历史窗口数包含当前 turn。
- token 使用 Provider 官方 tokenizer 的 `TokenizerAdapter.count(serialized_input)`；`serialized_input` 仅含 instructions、input、tools 和协议结构开销。不可用时使用 `ceil(字符数 / 4)`，误差只能由 safety margin 覆盖。
- Provider 仅展示安全参数视图和 artifact 路径；trace/UI 展示完整普通正文但持续脱敏凭据；原始 session 保存完整数据且不可被 Provider/UI 修改。

### 3.9 Working Memory 实现边界确认

- 非文件观察的 `previous` 使用 `latest.args + latest.details`；当前 turn 保留全部事件，历史只保留逻辑对象最新状态。
- 文件 freshness 保留当前版本和上一 stale 版本；`search` 只记录扫描 freshness，不产生读取覆盖。
- 当前 turn 与完整 task goal 属于固定占用。section 只设 history=8192、working_memory=4096、skills=512 的最低保障，不设 preferred 或 maximum；满足后由跨 section 候选竞争余量。
- 参数 artifact 使用 run 内单调 sequence、UTF-8、固定文本扩展名和严格 workspace/artifact 根目录校验。
- 敏感参数使用固定字段规则优先、模式检测补充；无法确定时只通过 artifact 暴露。
- Skills 以完整条目为单位，核心规则不可丢弃，其余按原始文件顺序截取。
- Provider tokenizer 不可用时按 `tokens = ceil(字符数 / 4)` 估算。
- 不做旧数据兼容和迁移，直接按新协议更新。
- 验收测试矩阵覆盖各 Level、artifact 异常、freshness 刷新、Level 4 摘要失败、session 原子提交和预算溢出。
- 明确后置：trace/UI 细节排版、artifact slug 样式、cold 文件长期清理、复杂相关性评分、assistant 文本压缩、非文件观察数量上限优化，以及三个子 Agent 工具的上下文治理。

## 4. Skills 渐进式加载

已确定的条目加载比例：

```text
Level 0: 100%
Level 1: 70%
Level 2: 70%
Level 3: 30%
Level 4: 70%
```

比例向下取整。

skill 条目以加载器输出的完整条目为最小单位，不允许从条目中间按字符截断。内建 JCode 核心规则属于不可丢失条目；其余条目按原始文件顺序保留，不按任务相关性重排。70% 和 30% 按原始条目数量向下取整；若取整结果少于核心条目数量，仍完整保留核心条目。Level 4 恢复到 70% 时不重新升档，只按本次原始压力定档生成并执行最终容量校验。

## 5. 动态 section 预算算法

最终采用“实际最低保障 + 跨 section 候选竞争”，不使用需求比例分配，也不设置 preferred 或 maximum budget：

```text
固定占用先扣除
-> section 实际最低保障
-> 跨 section 候选统一排序打包
-> 最终请求重新估算
```

先选入各 Level 明确要求完整保留的原始 History 窗口、核心 skill 和强制 hot 文件，再用候选补足 `min(raw_section_demand, configured_minimum)`；必保 token 已达到最低目标时不重复预留。必保是语义规则，不是 preferred/maximum 子预算。其余 history、Working Memory 和 skills 只有在全局竞争中被选中才可超过最低保障。工具调用与结果作为不可拆分候选原子；必保与最低保障原子合计装不下时返回 `system_minimum_budget_overflow`。

### 5.1 Token 与模型配置

```text
effective_context_window_tokens =
    min(375000, profile.context_window_tokens)

actual_max_new_tokens =
    CLI --max-new-tokens
    > .jcode.toml [runtime].max_new_tokens
    > 16384

serialized_input_tokens
+ actual_max_new_tokens
+ 7500
<= effective_context_window_tokens
```

每个模型档案必须声明 `context_window_tokens` 和 `max_output_tokens`。启动或切换模型时校验 `0 < actual_max_new_tokens <= profile.max_output_tokens`，并校验输出预留、safety margin 和静态最低容量；失败时直接返回配置错误，不静默缩小。每轮再根据实际固定占用执行 `mandatory_context_exceeds_window` 或 `system_minimum_budget_overflow`。

`serialized_input_tokens` 仅表示 `instructions + input + tools` 和 Provider 协议结构开销，不包含 model、max_output_tokens 字段文本、temperature、reasoning effort 或其他控制字段。统一 Provider tokenizer 不可用时使用 `ceil(字符数 / 4)`。

### 5.2 固定占用实现

普通固定项使用不可变 `BudgetOccupancy(name, tokens, source)` 记录，包括 provider protocol envelope、instructions、tools schema、current turn history、Working Memory task goal、output reservation 和 safety margin。只为 continuation 保留 `ReasoningContinuationBudgetOccupant` 与 `ToolContinuationBudgetOccupant` 两个专用计算器。

计量器按规范序列化顺序计算增量；协议字段名、括号和分隔符归入 provider protocol envelope。所有输入类占用之和必须严格等于 `serialized_input_tokens`，output reservation 和 safety margin 仅参与总容量公式。未知 continuation item 返回 `unsupported_provider_continuation_item`，不得漏算。

### 5.3 已确认实施配置

- section 最低保障：`history=8192`、`working_memory=4096`、`skills=512`。
- Level 4 模型摘要单次调用超时 `120` 秒，首次失败后额外重试 `2` 次；初始退避 `2` 秒、倍率 `2`，等待 `2s -> 4s`，总共最多调用 3 次，最坏时长约 `366` 秒。
- 可用摘要输出低于 2048 token 时直接采用确定性摘要；artifact 完整性异常不参与重试。

### 5.4 Runtime 异常边界

采用 `JCodeRuntimeStopError` 异常族：`MandatoryContextExceedsWindowError`、`SystemMinimumBudgetOverflowError`、`FinalContextExceedsWindowError`、`ArtifactWriteFailureError`、`ArtifactUnavailableError`、`ArtifactIntegrityError`、`FreshnessRefreshError`。

`ask()` 的统一边界覆盖 Context 构建、审计 artifact、Provider、工具、freshness、工具 artifact 和 checkpoint/session 持久化。已知异常停止后续动作、写入独立 stop reason，并通过 `_finish_run()` 收口；容量异常返回另开会话提示，artifact/freshness 异常返回具体中文错误。未知异常使用 `unexpected_runtime_error`，不能继续归为 `Model error`。

## 6. 必须保持的工程约束

- `ContextResult` 是 Provider、审计和压缩的唯一真相。
- 不允许 Provider 使用一份结构化 history，而预算系统测量另一份文本 history。
- 不允许整体尾部截断核心上下文。
- 工具调用和工具结果必须成对处理。
- provider continuation 无论是否启用思考都必须保持原生闭环；非思考模式只不产生 reasoning item。
- 用户请求不能被静默压缩。
- 固定占用超限时必须直接返回另开会话提示。
- 每次压缩必须留下 before/after token、丢弃项和压缩规则。
- 所有已确认规则都必须有针对性测试。
