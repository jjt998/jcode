# JCode 上下文治理改进策略 9.5

模型档案容量已确认并由 `.jcode.toml` 作为唯一配置来源：deepseek-flash/deepseek-pro `1048576/393216`，minimax-m3 `1000000/524288`，minimax-m2.7 `204800/32768`，minimax-m2.7-speed `204800/131100`（窗口/最大输出 token）。

## 1. 目标与范围

本策略重新定义 JCode 的上下文预算、压力计算和分层压缩规则。目标是让最终发送给 Provider 的请求始终可审计、可收敛，并且在压缩时优先保留任务证据、工具调用闭环和当前状态。

本策略固定使用统一的 JCode 上下文窗口，并继续使用 0-4 档压力等级。section 不再采用固定比例，而是依据固定占用和当前内容需求动态分配预算。

## 2. 统一窗口与固定参数

```text
MAX_CONTEXT_TOKENS = 375000
DEFAULT_MAX_NEW_TOKENS = 16384
SAFETY_MARGIN = 7500
```

`MAX_CONTEXT_TOKENS` 是 JCode 允许使用的统一窗口上限。每个模型档案必须声明 `context_window_tokens` 和 `max_output_tokens`，本轮有效窗口为：

```text
effective_context_window_tokens =
    min(MAX_CONTEXT_TOKENS, profile.context_window_tokens)
```

本轮实际输出预留 `actual_max_new_tokens` 的来源优先级固定为：

```text
CLI --max-new-tokens
> .jcode.toml [runtime].max_new_tokens
> DEFAULT_MAX_NEW_TOKENS
```

完整容量约束固定为：

```text
serialized_input_tokens
+ actual_max_new_tokens
+ SAFETY_MARGIN
<= effective_context_window_tokens
```

`serialized_input_tokens` 只表示 `instructions + input + tools` 及其 Provider 协议结构开销的实际输入 token。它不包含 `model`、`max_output_tokens` 字段自身、`temperature`、`reasoning effort` 或其他请求控制字段。`actual_max_new_tokens` 是输出容量预留，不是 `max_output_tokens` 这段 JSON 文本的 token 长度。

最终 Provider 输入的逻辑组成是：

```text
instructions
+ tools schema
+ skills
+ history
+ provider continuation
+ working memory
```

不再设置独立 `current_request` section，也不再在 `ContextResult` 中保留 `current_request` 字段。当前用户请求完整原文同时保存在当前 turn 的 user history event 和 `working_memory.core.task_goal` 中；两份内容来自同一个原文快照，不允许分别加工。后续工具循环和输出截断续写继续使用该原始 task goal，内部 continuation prompt 不得覆盖它。审计按最终 Provider 输入正常计量，不设置重复输入专用字段。

`safety margin` 固定为 `7500` token，不得被普通 section 或输出使用。

## 3. 固定预算占用

以下内容属于固定占用，不参与普通 section 的预算竞争，也不允许被压缩：

- `instructions`。
- `tools schema`。
- `provider protocol envelope`。
- 当前 turn 中实际进入 Provider history、且未由 continuation 承载的全部内容。
- `working_memory.core.task_goal` 中的用户请求完整原文。
- `reasoning continuation`。
- `tool continuation`。
- `output reservation`。
- `safety margin`。

`provider continuation` 按原生 item 拆分计量。`ReasoningContinuationBudgetOccupant` 只负责 `type="reasoning"` 的原生项；`ToolContinuationBudgetOccupant` 负责 `function_call` 和 `function_call_output`。非思考模式只表示 reasoning 占用为 0，工具 continuation 仍按实际内容计量。未知 continuation item 不得静默忽略，必须返回 `unsupported_provider_continuation_item`。

同一 `call_id` 的 `function_call` 与 `function_call_output` 不得拆分、裁剪或分别从 history 和 continuation 重复发送。当前 turn 仍计入 history 窗口，但其中已由 continuation 承载的原生工具事件只发送一次。

### 3.1 BudgetOccupancy

普通固定占用使用不可变 `BudgetOccupancy` 记录，不为每一项建立只有名称和估算函数的类：

```text
BudgetOccupancy
  name
  tokens
  source
```

普通记录名称包括：

```text
provider_protocol_envelope
instructions
tools_schema
current_turn_history
working_memory_task_goal
output_reservation
safety_margin
```

只有 continuation 保留专用计算器：

- `ReasoningContinuationBudgetOccupant`
- `ToolContinuationBudgetOccupant`

统一计量器按规范序列化顺序计算 token 增量，并将请求字段名、括号和分隔符计入 `provider_protocol_envelope`。所有输入类 `BudgetOccupancy.tokens` 之和必须严格等于 `serialized_input_tokens`；`output_reservation` 和 `safety_margin` 单独进入总容量公式，不属于序列化输入 token。

未来如果工具 schema 支持压缩，只需改变 `tools_schema` 的占用类别，不改变统一计量器和 `BudgetOccupancy` 结果结构。

## 4. 硬停止规则

先计算固定占用：

```text
fixed_demand =
    provider protocol envelope
  + instructions
  + tools schema
  + current turn history
  + working memory task goal
  + reasoning continuation
  + tool continuation
  + output reservation
  + safety margin
```

如果：

```text
fixed_demand > effective_context_window_tokens
```

则本轮直接停止：

- 不调用模型。
- 不执行工具。
- 不压缩用户请求。
- 不压缩当前 turn。
- 不压缩 instructions。
- 不压缩 tools schema。
- 不进入历史压缩流程。

最终答案固定为：

```text
当前已无剩余上下文空间，请你另开会话吧。
```

审计中记录 `mandatory_context_exceeds_window`，并保存最大窗口、各固定占用和总固定需求。

该状态独立于压力等级 4。压力等级 4 表示仍可通过压缩可变内容恢复；硬停止表示连最小必要请求都无法构造。

## 5. 可压缩预算与压力计算

固定占用未超限时，剩余预算为：

```text
flexible_budget = effective_context_window_tokens - fixed_demand
```

未压缩的可变内容需求为：

```text
raw_flexible_demand =
    未压缩 skills
  + 未压缩的可变 history
  + 未压缩的可变 working memory
```

压力比例使用剩余预算计算：

```text
pressure_ratio = raw_flexible_demand / flexible_budget
```

同时保留总利用率用于审计：

```text
total_utilization =
    (fixed_demand + raw_flexible_demand) / effective_context_window_tokens
```

`pressure_ratio` 用于决定压缩档位，`total_utilization` 用于说明完整窗口使用情况。

## 6. 压力等级

| 等级 | 压力比例 | 总体行为 |
| ---: | ---: | --- |
| 0 | `< 60%` | 不裁剪，直接发送 |
| 1 | `60% - 75%` | 轻度去冗余和工具结果压缩 |
| 2 | `75% - 85%` | 减少完整历史窗口和文件观察数量 |
| 3 | `85% - 95%` | 严格按任务相关性打包，skills 大幅减少 |
| 4 | `>= 95%` | 历史语义摘要化，并建立工作记忆冷热分层 |

压缩后必须重新编译最终 Provider 请求并重新估算。所有等级都只执行原始压力对应的一次压缩规则，不因压缩后压力变化重新升档。`95%` 只负责触发 Level 4；Level 4 压缩后即使压力仍不低于 `95%`，只要最终容量公式成立就发送。只有最终容量公式不成立时才返回另开会话答案。

## 7. 动态 section 预算

section 不再使用固定比例，例如 `history=50%` 或 `working_memory=23%`。每个 section 只声明：

```text
minimum_budget
compression_priority
```

固定占用先扣除后，先选入各 Level 明确要求完整保留的原子，再用 section 候选补足最低保障，最后由 skills、可变 history、可变 working memory 竞争剩余 `flexible_budget`。实际最低保障为 `min(raw_section_demand, configured_minimum)`，section 需求不足最低值时不预留空额度。原始 History 窗口、核心 skill 和强制 hot 文件是语义必保规则，不是 preferred/maximum 子预算；其 token 已覆盖最低目标时不重复预留。满足这些规则后不再划分 section 配额或上限，所有剩余 token 由跨 section 候选统一竞争。必保原子与实际最低保障的不可拆原子合计装不下时返回 `system_minimum_budget_overflow`。

当前 turn、`working_memory.core.task_goal` 等固定内容不计入 section 最低保障。分配依据包括：

- 当前实际内容需求。
- 任务相关性。
- 当前回合优先级。
- 文件和工具的新鲜度。
- 未解决错误或阻塞状态。
- 最近访问顺序。

最终审计记录实际分配，而不是只记录比例：

```json
{
  "current_turn_history_fixed": 12000,
  "history_recent_turns": 26000,
  "history_old_evidence": 18000,
  "working_memory_core": 6000,
  "working_memory_auxiliary": 2400,
  "skills": 900,
  "unused_reserve": 1700
}
```

## 8. 各压力档位策略

history 原始窗口数量统一表示“包含当前 turn 在内的总 turn 数”，不再把当前 turn 另行加在窗口之外。当前 turn 必须位于窗口内并完整保留，因此各级原始窗口最多包含的已闭合 turn 数分别为 6、4、3、2、2。Level 0 的 7-turn 数量只是始终原样保留的最近窗口边界；由于 Level 0 不做裁剪，窗口外旧 turn 在容量允许时也原样发送。当前 turn 的 user event 继续进入 Provider history；`working_memory.core.task_goal` 同时保存相同的用户请求完整原文。

### Level 0

- history 原始窗口：7 个 turn。
- working memory 最近文件：30 个。
- skills：100% 加载。
- 不做裁剪，直接发送最终 ContextResult。

### Level 1

- history 原始窗口：5 个 turn。
- 窗口内原始保留。
- 窗口外工具结果执行 400/100/400 压缩，`list_files` 使用专用合并规则。
- working memory 最近文件：20 个。
- skills 加载原始条目的 70%，向下取整。
- 不做语义摘要。

窗口外工具结果使用统一的 400/100/400 规则：

```text
首 400 字符
+ 中间 100 字符
+ 尾 400 字符
```

省略位置必须带明确省略标记。artifact 路径继续保留在结构化 metadata 中。

`list_files` 不使用 400/100/400。完整窗口内所有 `list_files` 调用及结果完整保留；窗口外按规范化 `path` 分组，每个 path 只保留 session 事件顺序中的最后一组完整 `tool_call + tool_result`，其余按 `call_id` 成对移除。最后一次无论成功、失败还是中止都覆盖旧快照；合并键只使用 path，`recursive` 和 `max_entries` 不参与分组。

### Level 2

- history 原始窗口：4 个 turn。
- 窗口内原始保留。
- 窗口外工具结果使用 400/100/400 压缩，`list_files` 继续使用按 path 合并并完整保留最后一次结果的专用规则。
- working memory 最近文件：16 个。
- skills 加载原始条目的 70%，向下取整。
- 开始移除低价值旧工具观察。

### Level 3

- history 原始窗口：3 个 turn。
- 窗口内原始保留。
- 窗口外工具结果使用 400/100/400 压缩，`list_files` 继续使用按 path 合并并完整保留最后一次结果的专用规则。
- working memory 最近文件：12 个。
- skills 加载原始条目的 30%，向下取整。
- 只保留工作记忆核心状态。
- 当前任务相关文件、未完成读取、stale、失败结果优先保留。

### Level 4

- history 原始窗口：3 个 turn。
- 窗口外 history 进行语义摘要。
- working memory 热文件保持 12 个。
- 其余文件逻辑归档，不物理删除。
- skills 恢复为原始条目的 70%，向下取整。
- 生成或更新持久化 compact summary。
- 重新编译并验证最终请求。

Level 4 完成压缩后重新编译最终 Provider 输入。压缩后的压力等级只用于审计，不作为拒绝条件；最终容量公式成立就发送。公式不成立时，审计必须记录已执行 history 语义压缩、压缩后压力等级、最终 token 数和超限原因，控制台和最终答案明确说明当前已无剩余上下文空间，请另开会话。

Level 4 语义摘要只处理 3-turn 原始窗口之外的旧 turn；该窗口已经包含当前 turn，因此实际最多额外保留最近 2 个已闭合 turn。摘要必须由模型生成结构化 JSON 并按任务阶段组织。

摘要字段固定为：`summary_version`、`task_goal`、`decisions`、`files_read`、`files_modified`、`key_findings`、`tool_failures`、`freshness_events`、`unresolved_blockers`、`next_steps`、`artifact_paths`。基于上一版 compact summary 与新淘汰 turns 增量更新；摘要损坏或版本不兼容时，由 `compact_summary_rebuild_on` 控制是否从按版本归档的原始 history artifact 重建。关闭重建时忽略旧摘要，并记录 `compact_summary_hurt=true`、`compact_summary_rebuild_on=false`。

`freshness_events` 只记录实际发生的 `read`、`write`、`patch`、`stale` 变化；未变化文件不产生事件，读取覆盖仍由 Working Memory 管理。摘要工具链只保留工具名、状态、失败类型或返回码、关键 artifact 路径和任务影响，完整参数与结果仍保存在 session/artifact。

摘要模型单次超时 `120` 秒；首次调用失败后最多额外重试 2 次，等待序列固定为 `2s -> 4s`，总共最多调用 3 次，理论最坏时长约 366 秒。仍失败时使用确定性结构摘要；确定性摘要仍超限则另开会话，不退回 Level 3。artifact 完整性异常不参与摘要重试。

摘要请求使用独立容量公式：

```text
summary_input_tokens
+ summary_output_reservation
+ safety_margin_tokens
<= effective_context_window_tokens
```

摘要请求不携带 tools schema、普通 Working Memory 或 Provider continuation，只包含摘要 instructions、合法旧 compact summary 和本次新淘汰的旧 turn。`actual_max_new_tokens` 是摘要输出上限，实际 `summary_output_reservation` 取该上限与剩余容量中的较小值。可用输出低于 2048 token 时不调用摘要模型，直接进入确定性结构摘要。

确定性结构摘要采用“结构化聚合 + 合法旧摘要字段继承”。它不读取普通 assistant 正文，也不推断新事实。`summary_version`、`task_goal`、`files_read`、`files_modified`、`tool_failures`、`freshness_events`、`unresolved_blockers`、`artifact_paths` 只从结构化元数据聚合；`decisions`、`key_findings`、`next_steps` 只继承合法旧摘要中无冲突的字段，没有可靠来源时为空。

确定性摘要算法固定为：读取旧摘要并按 `compact_summary_rebuild_on` 处理无效版本；收集新淘汰 turn 的结构化事件；按字段来源聚合且不读取被压缩正文；对文件、artifact 与工具 ID 去重；以最新 freshness 和工具状态覆盖旧状态；冲突仅保留最新事实；输出固定 JSON schema；校验 JSON、schema、字段类型和 artifact 路径。校验失败时不发送 Provider 请求，直接进入另开会话出口。

确定性摘要数组元素必须为短结构对象，禁止生成长段落或使用“可能”“推测”“应该”等推理词；不得将工具失败视为任务失败、将写入正文视为读取事实，或将旧 freshness 视为当前 freshness。`artifact_paths` 仅保存裸路径。

Level 4 持久化采用候选副本和原子提交：先复制原始 history，写入只读 history artifact，重新读取并校验 SHA-256，再生成和校验摘要；随后用候选 history 构建最终 `ContextResult` 并完成容量校验。全部成功后，将新 session 写入同目录临时文件并 flush，再使用 `os.replace()` 原子替换，最后更新运行中的内存 session。`ContextManager` 不得直接修改传入的活动 session。

session 不得引用尚未成功写入并校验的 artifact。session 提交失败时旧 session 保持有效；history artifact 已成功但提交失败时允许留下无引用 artifact。摘要事务成功后即使后续 Provider 调用失败，已提交的 compact history 仍然有效。

## 9. 工作记忆冷热分层

Level 4 不物理删除超出 12 个热文件范围的记录，而是划分为：

```text
files.hot
files.cold
```

热文件优先级：

1. 当前回合刚读取或修改的文件。
2. 当前 freshness 的文件。
3. 存在未完成分段读取的文件。
4. 存在 stale 或错误状态的文件。
5. 当前任务相关文件。
6. 最近访问文件。

冷文件仍保留路径、freshness、大小、已读取范围、完整性和最近访问顺序，但不进入当前模型上下文。压力下降后不自动恢复全部冷文件，而是按当前任务重新晋升。

## 10. 最终输入一致性

`ContextResult` 是唯一的最终输入真相。预算、压缩审计、trace 和 Provider 请求都必须从同一个最终 ContextResult 派生。

流程固定为：

```text
测量原始需求
-> 计算固定占用
-> 硬停止检查
-> 计算压力等级
-> 分配 section 实际最低保障
-> 跨 section 候选竞争剩余预算
-> 压缩 history / working memory / skills
-> 编译最终 Provider 请求
-> 重新估算最终 token
-> 满足窗口后调用模型
```

禁止只压缩一份文本投影，却让 Provider 使用另一份未压缩结构。禁止对最终上下文整体使用无语义的尾部截断。

## 11. Working Memory 非文件观察

非文件型工具中的 `run_shell`、`ask_user` 和 `todo` 进入 `tool_observations`。`list_files` 是目录快照，不进入文件 freshness 或读取覆盖；其观察只记录调用状态和参数，完整目录内容由 history 或当前 continuation 提供，避免在 Working Memory 重复正文。模型视图使用精简结构，审计字段只保存在原始 session：

```text
tool_observations:
  current_turn:
    - tool
      call_id
      status
      args
      result:
        details
        artifacts
  previous:
    - tool
      object_id
      status
      latest:
        args
        details
      artifacts
```

当前 turn 的全部观察按事件时间正序展示；跨 turn 每个逻辑对象只展示最新状态，按最近活动时间倒序展示，活动对象优先。不同 `run_shell` 的 `call_id` 即使命令相同也不得合并。`list_files` 在旧 history 中另按规范化 path 合并，不能套用非文件观察的对象合并规则。

`result.details` 最小字段为：`run_shell` 使用 `return_code`、`signal`；`ask_user` 使用 `response_status`、`selected_choice`、`answer`；`todo` 使用 `operation`、`todo_status`、`remaining_count`；`list_files` 使用 `path`、`recursive`、`max_entries` 和执行状态，但不复制目录正文。完整的大型正文只通过裸 artifact 路径引用，`list_files` 的完整结果是明确例外。

`enter_plan_mode` 和 `exit_plan_mode` 只更新 `working_memory.runtime_state`，不进入 `tool_observations`；对应 `tool_call + tool_result` 仍正常保留在 history。`runtime_state` 只展示当前最终的 `mode`、`topic` 和 `plan_path`，不重复模式切换过程。

`spawn_subagent`、`send_subagent_message`、`wait_subagent` 的生命周期压缩、对象合并、参数外置和 Working Memory 投影暂不在 9.5 中定义。本次实现只保留现有执行能力与 history 调用原子，并在三个 tool definition 旁增加中文注释，明确该治理缺口；不得在验收报告中声明这三项已完成新协议治理。

Level 0/1 保留选中对象的全部结构化字段；Level 2 合并状态并保留首次信息、最新状态和全部 artifact 路径；Level 3 每个对象只保留最新状态和结果引用；Level 4 只保留当前 turn 与仍活动对象，已结束对象仅保留最新审计索引。

大型正文 artifact 写入失败必须抛出 `ArtifactWriteFailureError`，消息包含“artifact写入失败”，立即终止运行并在控制台输出；不得降级或继续请求 Provider。工具业务失败（如 shell 非零返回码）仍按工具状态机记录并允许运行继续。

参数安全规则：原始参数完整保存在 session；Provider 按工具协议展示最小必要字段，大正文和敏感字段只显示 artifact 路径。文件 hot/cold 排序固定为：用户明确提及 > 当前修改 > 当前 freshness > 未完成读取 > 最近访问 > 最近修改 > 其他相关性。模型只展示 `covered_ranges`，不展示逐次 `read_ranges`。

## 12. 其他压缩决策

- Level 4 history 使用模型生成语义摘要；原始 session 和 artifact 作为事实来源保留。
- Skills 按原始文件顺序截取，不按相关性重排。
- 动态 section 预算采用“固定占用先扣除，按 section 实际最低保障，再由跨 section 候选竞争剩余预算”。不设置 preferred 或 maximum budget。

## 13. 已确认边界协议

### 13.1 各工具参数暴露

原始 session 保存完整合法参数；Provider 按工具只展示必要字段，大正文和敏感参数只展示 artifact 路径，且与压力等级无关。

| 工具 | Provider 可见参数 | 仅 artifact 参数 |
| --- | --- | --- |
| `read_file` | `path`、`start`、`end`、`max_chars` | 无 |
| `list_files` | `path`、`recursive`、`max_entries`；完整结果直接返回 | 无 |
| `search` | `path`、`query`、`max_results` | 超长 `query` |
| `write_file` | `path`；派生的 UTF-8、replace、正文长度/hash | 窗口外超过 2000 字符的 `content` |
| `apply_patch` | `path`；派生的单次 exact 操作、old/new 长度/hash | 窗口外超过 2000 字符的 `old_text`、`new_text` |
| `run_shell` | workspace 派生 cwd、`timeout`、命令摘要、命令 hash | 完整 `command` |
| `ask_user` | `question`、`choices`；结果中展示 answer/status | 标记为 secret 的回答 |
| `todo` | todo id、title、priority、status | 超长 note 或正文 |
| `enter_plan_mode` | `topic`、`path` | 无 |
| `exit_plan_mode` | 无 | 无 |

`spawn_subagent`、`send_subagent_message`、`wait_subagent` 的参数安全视图暂未冻结，只在 tool definition 注释和实施缺口中记录，不在本表虚构规则。

本表严格对应当前 `src/tools/schemas.py`：不为 search 虚构 glob/正则选项，不为 run_shell 虚构 env 参数。UTF-8、replace、exact 和 cwd 是由当前工具实现派生的审计字段，不扩展模型可提交的参数 schema。

`list_files` 不受 `max_chars` 或通用 inline 字符阈值限制，也不因长度自动外置为 artifact；它仍受工具自身 `max_entries` 限制，完整内容仍参与最终 token 计量和窗口校验。

### 13.2 参数 artifact

```text
.jcode/runs/<run_id>/artifacts/parameters/<sequence>-<kind>.<ext>
```

根目录固定为当前 run 的 artifacts 目录；`sequence` 单调递增；路径中不得包含用户输入、凭据或完整命令。Provider 可以直接使用 `read_file` 读取参数 artifact，但不得路径逃逸。

### 13.3 artifact 失效

`ArtifactUnavailableError` 表示缺失、权限不足或无法读取；`ArtifactIntegrityError` 表示 hash 不匹配或内容损坏。当前运行中发现任一异常立即终止并输出异常；历史回放只显示路径和 `artifact_status=unavailable`。`ArtifactWriteFailureError` 专用于创建失败。

### 13.4 Level 4 摘要

Level 4 使用模型生成语义摘要，单次超时 120 秒，首次失败后额外重试两次，等待 2 秒和 4 秒；仍失败时使用确定性结构摘要，仍超限则另开会话，不退回 Level 3。摘要持久化通过候选副本、history artifact 校验和 session 原子替换完成；原始 history 保存为只读审计 artifact，下一轮不恢复到活动上下文。

### 13.5 预算与排序

各 section 的实际最低保障之和超过 flexible budget 时，直接返回 `system_minimum_budget_overflow`，不静默溢出、不整体截断。实际最低保障为 `min(raw_section_demand, configured_minimum)`，不足最低值的 section 不占用空额度。候选排序按字典序：

```text
(user_mentioned, modified_in_current_run, current_freshness,
 incomplete_read, last_access_order, last_modified_time,
 task_relevance, normalized_path)
```

用户明确提及的文件全部强制进入 hot，即使超过 nominal 上限，其他文件降级。

### 13.6 Turn 和 token

一个 turn 包含一次用户请求及其全部 assistant 响应、tool call/result 和 continuation；多工具响应仍属于同一 turn。最终回答、用户中止、runtime 终止或进入 suspended 状态时闭合；工具失败在同一 turn 内继续处理。`7/5/4/3/3` 是包含当前 turn 的总窗口，当前 turn 不另加。当前 turn 实际发送内容不可压缩，属于固定占用。

使用 Provider 官方 tokenizer：

```text
TokenizerAdapter.count(serialized_input)
```

`serialized_input` 是 `instructions + input + tools` 及协议结构开销的规范序列化结果。`actual_max_new_tokens` 使用 CLI、TOML、默认值的最终解析值，并作为独立输出预留；tokenizer 不可用时按 `tokens = ceil(字符数 / 4)` 估算，误差只能由 safety margin 覆盖。

启动或切换模型时先校验 `0 < actual_max_new_tokens <= profile.max_output_tokens`，以及输出预留、safety margin 和静态最低容量可以装入有效窗口；失败时直接返回配置错误，不自动缩小数值。每轮再按真实 instructions、tools、当前 turn、task goal 和 continuation 执行动态硬停止检查。

### 13.7 隐私展示

- Provider 只看安全参数视图、状态元数据和 artifact 路径。
- trace/UI 展示完整普通工具结果，但凭据、token、password 等仍脱敏；普通正文不做 1500 字符截断。
- 原始 session 保存完整参数、结果和事件链，只供审计和恢复。
- Provider 和 UI 不得修改原始 session；脱敏动作记录规则版本。

### 13.8 Runtime 系统异常边界

系统异常使用明确的 `JCodeRuntimeStopError` 异常族：`MandatoryContextExceedsWindowError`、`SystemMinimumBudgetOverflowError`、`FinalContextExceedsWindowError`、`ArtifactWriteFailureError`、`ArtifactUnavailableError`、`ArtifactIntegrityError`、`FreshnessRefreshError`。

`ask()` 的统一运行边界覆盖 Context 构建、审计 artifact、Provider 调用、工具执行、freshness 更新、工具 artifact 和 checkpoint/session 持久化。已知系统异常停止后续 Provider 与工具调用，写入独立 `stop_reason`，并通过 `_finish_run()` 保存状态、trace 和 report。容量异常统一返回另开会话提示；artifact 和 freshness 异常返回具体中文错误。未知异常使用 `unexpected_runtime_error`，不得伪装为模型错误。

## 14. Working Memory 实现边界

- 非文件观察的 `previous` 记录采用 `latest.args + latest.details`；当前 turn 保留全部事件，历史 turn 只保留每个逻辑对象的最新状态。
- 文件 freshness 只保留当前版本和上一 stale 版本；`search` 只记录扫描来源 freshness，不产生读取覆盖。
- 当前 turn 和完整 `task_goal` 已由固定占用保护；section 最低保障保护其余可变 history、Working Memory 和 Skills。满足实际最低保障后，Skills 与旧证据候选仍可因全局竞争而不再获得额外预算。
- 参数 artifact 使用 run 内单调 sequence、UTF-8 编码和固定文本扩展名，并严格校验 workspace/artifact 根目录。
- 敏感参数采用固定字段规则优先、模式检测补充的策略；无法确定时只通过 artifact 暴露。
- Skills 以完整条目为裁剪单位，核心规则不可丢弃，其余按原始文件顺序截取。
- 不做旧 Working Memory 数据结构兼容和迁移，直接按新协议更新实现。
- 验收测试矩阵覆盖各 Level、artifact 异常、freshness 刷新、Level 4 摘要失败、原子提交和预算溢出。

明确后置：trace/UI 细节排版、artifact slug 样式、cold 文件长期清理、复杂相关性评分、assistant 文本压缩、非文件观察数量上限优化。

## 15. 实施配置基线

section 使用固定 token 最低保障：`history=8192`、`working_memory=4096`、`skills=512`。每项实际保障取原始需求和配置最低值中的较小值；固定占用先扣除，先选入 Level 语义必保原子，再补足实际最低保障，剩余预算由跨 section 候选统一竞争，不设置 preferred 或 maximum。必保原子与三项实际最低保障的不可拆原子合计超过 flexible budget 时，返回 `system_minimum_budget_overflow`。

Level 4 模型摘要单次调用超时为 `120` 秒，首次失败后最多额外重试 `2` 次，初始退避 `2` 秒、退避倍率 `2`，等待序列为 `2s -> 4s`，总共最多调用 3 次，最坏时长约 `366` 秒。摘要调用可用输出低于 2048 token 时直接采用确定性结构摘要；artifact 完整性异常不参与摘要重试，仍立即终止运行。
