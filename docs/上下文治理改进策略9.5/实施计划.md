## 2. 编码前必须补齐的配置数据

当前 `.jcode.toml` 有五个模型档案：`deepseek-flash`、`deepseek-pro`、`minimax-m3`、`minimax-m2.7`、`minimax-m2.7-speed`。权威容量已确认并同步到配置：DeepSeek 两档为 `1048576/393216`，MiniMax-M3 为 `1000000/524288`，MiniMax-M2.7 为 `204800/32768`，MiniMax-M2.7-speed 为 `204800/131100`（依次为窗口/最大输出 token）。

阶段 1 开始前，必须为五个档案分别取得当前 API 服务实际支持的：

```text
context_window_tokens
max_output_tokens
```

实现和测试不得填入虚构统一值。若当前 `[runtime].max_new_tokens=32768` 超过某个档案的 `max_output_tokens`，选择该档案时应按设计直接失败；不得把 32768 自动改成档案上限。

这项只缺配置数据，不改变已冻结算法。三个子 Agent 工具的上下文治理仍是明确后置范围，不是阶段 1 的阻塞项。

## 3. 目标数据结构和职责边界

### 3.1 `src/context/budget.py`

保留一个普通不可变占用记录和两个 continuation 专用计算器：

```text
BudgetOccupancy(name, tokens, source)
ReasoningContinuationBudgetOccupant
ToolContinuationBudgetOccupant
```

增加以下具体结构：

- `TokenizerAdapter`：优先调用当前 Provider 注册的 tokenizer；没有可用 tokenizer 时使用 `ceil(len(serialized_input) / 4)`，并在审计中标记 `source="fallback_chars_div_4"`。
- `ContextCapacity`：保存 `effective_context_window_tokens`、`actual_max_new_tokens`、`safety_margin_tokens`、`serialized_input_tokens`、`remaining_tokens` 和最终是否可发送。
- `ContextBudgetCandidate`：保存 section、稳定名称、原子 payload、原始顺序、token 增量和优先级字段；工具调用/结果使用同一 atomic key。
- `calculate_pressure()`：只使用 `raw_flexible_demand / flexible_budget`，并返回 0-4 级和审计范围。
- `validate_static_model_capacity()`：供启动和模型切换共同使用。
- `validate_final_capacity()`：统一执行最终容量公式并抛出明确系统错误。

`ContextCapacity.remaining_tokens` 固定为 `effective_context_window_tokens - serialized_input_tokens - actual_max_new_tokens - safety_margin_tokens`；不得另设“95% 余量”或把 output reservation 再算进 serialized input。

`tail_clip()` 删除。普通 section 不得再调用字符尾截断。

`BudgetOccupancy.source` 只允许 `input`、`output_reservation`、`safety_margin` 三类。固定输入、最终选中的 Skills/History/Working Memory 都使用同一个记录类型；两个 continuation 计算器也只返回该记录，不建立额外结果类。只有 `source="input"` 的记录参与 `serialized_input_tokens` 求和，另外两类只参与容量公式。

`serialize_counted_input()` 必须同时生成规范 JSON 字符串和带类别的有序序列化片段。occupancy 不能把各字段分别估算后相加，因为 tokenizer 可能跨片段合并 token；具体计量方式固定为：对累计前缀逐次调用同一个 tokenizer，以“本次累计 token - 上次累计 token”作为当前片段增量，JSON 字段名、引号、逗号、括号等归入 `provider_protocol_envelope`。最后再次直接计量完整规范字符串，并断言所有输入 occupancy 之和严格等于该值。

`calculate_pressure()` 用整数交叉乘法判断 60/75/85/95 边界，避免浮点误差。`flexible_budget=0` 且 `raw_flexible_demand=0` 时定为 Level 0；budget 为 0 但仍有可变需求时定为 Level 4，随后由必保/最低保障或最终容量检查明确停止。

### 3.2 `src/context/result.py`

保留 `HistoryEvent` 和 `ToolDefinition`，修改 `ContextResult`：

- 删除 `current_request`。
- 新增不可变 `ProviderInputSnapshot`，字段固定为 `instructions`、`input`、`tools`、`serialized_input_json`、`serialized_input_tokens`、`tokenizer_source` 和输入 occupancy；`ContextResult.provider_input` 保存该对象。
- `serialized_input_json` 只序列化前三个 Provider 输入字段，不包含 model、输出上限、temperature 或 reasoning 控制字段；Provider 发送与审计均使用同一快照，不允许再次编译前三个字段。
- 保留治理后的 `history`、冻结 Working Memory 视图、skill 文本、`ctx_info` 和 `provider_continuation`，用于审计和回放。
- `compact_audit` 只保存摘要过程审计，不保存废弃字段或原始旧 History 正文。

新增 `ContextBuildOutcome`，把纯 Provider 输入与待提交状态分开：

```text
context_result
session_candidate
working_memory_candidate
session_commit_required
history_artifact_ref
```

只有 Level 4 产生 `session_commit_required=true`。ContextManager 返回候选，`JCodeAgent` 负责调用 `SessionStore.save()` 并在成功后替换内存对象。

`history_artifact_ref` 使用固定 dict schema：`path`、`sha256`、`bytes`、`sequence`、`created_at`，路径一律为 workspace-relative 裸路径。普通 build 中它为 `None`；Level 4 中只有 artifact 重新读取验签成功后才能赋值。

### 3.3 `src/providers/request.py`

新增单一 Responses 协议编译模块，提供：

- `compile_responses_input()`：按 skill、History、continuation、Working Memory、内部续写指令的规范顺序生成 input items。
- `compile_responses_tools()`：只从 `ToolDefinition` 生成函数 schema。
- `serialize_counted_input()`：只序列化 `instructions + input + tools`，固定键顺序、`ensure_ascii=False` 和紧凑 separators，并产生 3.1 所述计量片段。
- `compile_provider_input_snapshot()`：返回 `ContextResult.provider_input` 使用的不可变快照。

`DeepSeekClient` 和 `MiniMaxClient` 不再自行从 Context sections 重建 input。两者的 `_compile_request()` 只从 `context.provider_input` 取三个已编译字段，再增加 `model`、`max_output_tokens`、temperature/reasoning 和各自允许的 extra 字段。

### 3.4 `src/runtime/errors.py`

新增 `JCodeRuntimeStopError` 基类，至少携带 `code`、`user_message` 和可选 audit payload。定义以下子类：

- `MandatoryContextExceedsWindowError`
- `SystemMinimumBudgetOverflowError`
- `FinalContextExceedsWindowError`
- `UnsupportedProviderContinuationItemError`
- `ArtifactWriteFailureError`
- `ArtifactUnavailableError`
- `ArtifactIntegrityError`
- `FreshnessRefreshError`

未知 Python 异常不包装成模型错误，统一使用 `unexpected_runtime_error` 收口。

### 3.5 session 和 Working Memory schema

- `SessionStore` schema 从 4 升到 5；读取旧 schema 直接提示新开会话，不做迁移。
- `WorkingMemory` schema 从 `jcode.layered_memory.v1` 升到 `jcode.layered_memory.v2`；`from_dict()` 删除 `recent_files`、`file_freshness`、`file_reads` 等旧键 fallback。
- 模块级 `src/state/checkpoint.py::SCHEMA_VERSION` 从 1 升到 2，直接保存新 Working Memory，不再另外复制 `recent_files/file_freshness`。
- 所有新增 dataclass 成员按项目约定在成员右侧添加简明中文注释。

### 阶段 1：配置、模型容量和规范 Provider 输入

#### 1.1 修改配置模型

在 `src/providers/profiles.py::ModelProfile`：

- 在 `base_url` 后新增 `context_window_tokens`、`max_output_tokens` 两个必填正整数。
- `snapshot()` 必须输出这两个字段，确保 run、session event 和 Web 模型列表能看到有效容量。

在 `src/app/config.py`：

- `_profile_from_raw()` 必须读取并校验两个新字段；缺失、布尔值、0、负数或非整数都抛 `ValueError`。
- 把两个键加入 `known`，不能落入 `ModelProfile.extra`。
- `load_config()` 先解析 `runtime.max_new_tokens`，再按 `args.max_new_tokens is not None` 实现 CLI > TOML > 16384；删除当前 `... or 8192`。
- `AppConfig` 增加 `explicit_model_profile`，仅当 CLI 实际提供 `--model` 时保存 profile ID；TOML `default_model` 仍只作为新会话默认值。
- 为 `AppConfig` 增加 `compact_summary_timeout_seconds=120`、`compact_summary_retry_count=2`、`compact_summary_initial_retry_delay_seconds=2`、`compact_summary_retry_multiplier=2`、`compact_summary_rebuild_on=True`；TOML 均从 `[runtime]` 读取。
- `load_config()` 只完成不依赖 workspace 的数值校验；完整静态输入校验由 `build_agent()` 在 workspace 和工具 registry 建立后执行。

静态校验至少执行：

```text
0 < actual_max_new_tokens <= profile.max_output_tokens
actual_max_new_tokens + 7500 + static_minimum_input_tokens
    <= min(375000, profile.context_window_tokens)
```

`static_minimum_input_tokens` 使用启动时已知的完整 instructions、完整工具 schema、Provider envelope 和三个配置最低保障计算；未知的当前 user/task goal/continuation 留给每轮动态校验。

容量校验只实现一套共享函数，不在四个入口复制公式：

```text
validate_profile_capacity_fields(profile)
resolve_actual_max_new_tokens(cli_value, toml_value, default=16384)
compile_static_capacity_input(workspace, registry, allowed_tools, tokenizer)
validate_static_model_capacity(profile, actual_max_new_tokens, static_input)
```

`compile_static_capacity_input()` 使用与正式请求相同的 prefix、tool definitions、Provider compiler 和 tokenizer，只把运行时未知项置空，并额外加入 `history=8192`、`working_memory=4096`、`skills=512` 三项配置最低保障。它返回结构化明细，不能只返回一个无法审计的合计数。

#### 1.2 覆盖四条模型容量校验入口

- `src/app/config.py::load_config()`：校验所有档案的容量字段，并对启动选中的档案执行 `actual_max_new_tokens <= profile.max_output_tokens`。
- `src/app/bootstrap.py::build_agent()`：`Workspace.build()`、`build_default_registry()` 和 session candidate 读取完成后，根据 candidate 的活动模型与 runtime mode 选择实际 tool profile，构造完整 prefix 和 `static_minimum_input_tokens`；失败时不保存 session、不发 resumed/model-switched event。
- `src/app/cli.py::main()`：删除 `build_agent()` 后再次调用 `switch_model_profile()` 的路径；显式 `--model` 由 `AppConfig.explicit_model_profile` 交给 `build_agent()` 一次性处理。
- `src/runtime/agent.py::switch_model_profile()`：用当前 workspace、prefix 和 active tool profile 重新计算静态输入，在修改 `session["active_model_profile"]`、写 `model_switches`、保存 session 和发事件之前校验。
- `src/app/web_runs.py::WebRunManager.switch_model()`：用目标 project root 和 session runtime mode 对应的实际 tool profile 计算同一静态输入，在写 Web session 之前校验目标档案；失败时保持原 profile 和 model options 不变。

`SessionStore.load_requested()` 是只读候选加载，不算运行状态提交。`build_agent()` 必须在任何 `SessionStore.save()`、event bus 写入和 Agent 状态绑定之前完成静态校验。Web 切换不得临时构造一个 Agent 来做校验，而是直接调用上述共享编译与校验函数。

目标档案选择顺序固定为：显式 CLI `--model` > session candidate 的 `active_model_profile` > TOML `default_model`。对最终目标只执行一次完整静态校验；成功后，若目标与 candidate 不同，再在 candidate 中追加唯一一条 `source="cli"` model switch 并原子保存，随后才能创建 event bus、写 resumed event 或赋给 Agent。这样既保留恢复会话的 CLI 覆盖，也避免默认档案与恢复档案各校验一次或记录 from/to 相同切换。

### 阶段 2：统一异常边界和原子 session 存储

#### 2.1 改造 `SessionStore`

在 `src/state/session.py`：

- `save()` 先 `deepcopy(session)`，只修改副本的 `schema_version/updated_at`。
- 使用目标 JSON 的同目录临时文件，UTF-8 写入后 `flush()`、`os.fsync()`，再 `os.replace()`。
- 保持现有 `save() -> Path` 调用契约；`os.replace()` 成功后才把副本的 `updated_at/schema_version` 回写到传入 dict。禁止写失败时污染传入对象。
- 临时文件写入或替换失败时清理临时文件并抛 `JCodeRuntimeStopError(code="session_persistence_failure")`，原 session 文件保持有效；session 失败不得伪装成 artifact 创建失败。

`PlanModeController.enter()/exit()`、todo 修改、模型切换、`_build_context()`、`_finish_run()` 和 Web session 写入继续调用统一 `SessionStore.save()`，不各自实现临时文件逻辑。所有调用方遵循同一 candidate 模式：深复制 session 及关联的 todo/Working Memory 状态，在 candidate 上修改，`save(candidate)` 成功后才替换活动引用；plan mode 的 tool profile/write scope、模型事件和 todo ledger 也只能在提交后更新。否则即使磁盘文件原子，保存失败仍会污染进程内状态。

#### 2.2 改造 `JCodeAgent.ask()`

把当前 while 循环提取为 `_run_task_loop()`，`ask()` 负责完整生命周期边界：

```text
task_state = None
run_dir = None
try:
    task_state, run_dir, checkpoint = _begin_run()
    return _run_task_loop(task_state, run_dir, checkpoint)
except JCodeRuntimeStopError as error:
    return _finalize_stopped_run(task_state, run_dir, error.code, error.user_message)
except Exception as error:
    return _finalize_stopped_run(task_state, run_dir, "unexpected_runtime_error", ...)
```

具体调整：

- `_build_context()` 从现有 Provider-only `try` 外移入统一边界。
- Provider 临时错误的重试仍留在 `_call_model()`，用尽后向外抛，由统一边界收口。
- `_execute_tool_call()` 中 artifact、freshness、checkpoint 和 task-state 持久化异常不再被转换为工具业务失败。
- 已知容量错误统一返回“当前已无剩余上下文空间，请你另开会话吧”。
- 未知异常 trace 使用真实 `error_type`，stop reason 固定 `unexpected_runtime_error`，用户文本不再以 `Model error:` 开头。
- `_finish_run()` 改为幂等：先完成内存状态，再按 trace/report/session/task_state 顺序写入；若其中一次持久化已经触发系统错误，禁止递归调用自身。
- 新增 `_finalize_stopped_run()` 作为无递归的最后收口。它允许 `task_state/run_dir` 尚未创建；对已经存在的 trace、report、task-state、session 四个持久化目标分别做一次 best-effort 写入并记录失败，绝不再次调用 `_finish_run()`。即使原始错误就是 session/report 写入失败，也必须返回原始系统错误的用户文本，不能让第二个持久化异常逃出 `ask()`。
- `_begin_run()` 只返回完全创建成功的 `(task_state, run_dir, checkpoint)`；若创建过程中已经追加 user History 后失败，统一边界按当前内存状态完成收口，不重放用户请求。

在 `src/tools/executor.py::ToolExecutor.execute()` 和 `_execute_runtime_tool()` 中增加明确的异常穿透：捕获到 `JCodeRuntimeStopError` 必须原样 `raise`，只有普通工具异常才转换成 `ToolResult`。否则 `PlanModeController.enter()/exit()` 和 todo 的 session 保存失败会被错误伪装为工具业务失败。

#### 2.3 保留业务失败语义

- `ToolExecutor.execute()` 捕获的普通工具执行异常继续返回 `ToolResult(error/partial_success)`，不升级为系统异常。
- `run_shell` 非零返回、patch 非唯一、权限拒绝继续进入 History 和 continuation 闭环。
- 只有 harness 自身的 artifact、完整性、freshness 和持久化失败进入 `JCodeRuntimeStopError`。

测试：

- 新增 `test/test_runtime_errors.py`，分别在 `_build_context()`、context audit、Provider、tool artifact、freshness、checkpoint、session save 和 report 写入点注入错误。
- 断言已知错误都有独立 stop reason、停止后续模型/工具调用并经过 `_finish_run()`。
- 断言未知错误为 `unexpected_runtime_error`。
- 覆盖 `_begin_run()` 尚未返回、`_finish_run()` 内第二次写盘失败、runtime tool 内 `SessionStore.save()` 失败，断言异常不会递归收口、不会变成 `ToolResult`，且 `ask()` 始终返回明确文本。
- 新增 `test/test_session_store.py`，验证临时文件、fsync/replace、提交失败保留旧 JSON、输入 dict 不被提前修改；另覆盖 plan/todo/model switch 三个调用方在保存失败时活动引用不变。

### 阶段 4：Working Memory v2 和工具观察写入链

#### 4.1 替换字段模型

在 `src/memory/working.py::WorkingMemory`：

- 删除 `recent_files`、`file_freshness`、`read_file_counts`、`file_reads`、summary 型 `tool_observations` 和 `subagent_results` Provider 投影。
- 新增 `files`，每个规范化 path 保存 current version、最多一个 stale version、file size、last access order、last modified time、modified in current run、user mentioned、hot/cold。
- current version 内保存原始 `read_ranges` 和合并后的 `covered_ranges`；Provider 只渲染 covered ranges，审计保留 read ranges。
- 新增结构化 `tool_observations`，原始事件包含 tool、call/object ID、turn ID、status、args、details、artifacts、error、event time、provenance。
- 新增 `runtime_state`，只保存最终 `mode/topic/plan_path`。
- `core.task_goal` 直接保存完整用户原文；`constraints/todos/safety` 等保留为 core，其余作为 auxiliary 候选。

持久化 JSON 固定为：

```text
schema: jcode.layered_memory.v2
core:
  task_goal
  constraints
  todos
  safety
files:
  hot: [normalized_path]
  cold: [normalized_path]
  records: {normalized_path: file_record}
tool_observations:
  events: [raw_structured_event]
runtime_state:
  mode
  topic
  plan_path
auxiliary:
  retrieval
  resume
  compact
```

替换方法：

- `note_file_read()` 改为写精确半开区间 `[start, start + returned_chars)` 并更新合并覆盖。
- 新增 `note_search_sources()`，只写扫描 freshness，不写读取范围。
- 新增 `note_files_modified()`，建立新 current freshness，把旧 current 移为唯一 stale，清空新版本读取覆盖。
- `read_file_count()`、`read_file_complete_count()` 改从 current version 的精确 range 记录读取。
- `observe_tool()` 改为 `record_tool_observation()`，不接收自然语言 summary。
- `list_files` 也写一条不含目录正文的 observation，details 只保存 path/recursive/max_entries 和执行状态；完整结果只在 History 或 continuation。
- `render()` 拆成 `render_core()`、`render_file_candidates()`、`render_tool_candidates()` 和最终 `render_provider_view()`，不再用 `[-5]/[-10]/[-20]` 隐式裁剪。

`auxiliary.compact` 只保存与 session compact-summary event 同步的恢复索引和审计状态，`render_provider_view()` 不再次渲染摘要正文；Provider 只从 History 中接收一份 compact summary。用户请求双份输入是唯一明确接受的正文重复。

逻辑对象键固定为：`run_shell`、`ask_user` 使用 call ID，todo add/update 使用 todo ID，todo list 使用 call ID，`list_files` observation 使用规范化 path。当前 turn 不按对象合并；旧 turn 才按对象只取最后状态。`enter_plan_mode/exit_plan_mode` 不创建 observation，因此没有对象键。

结构化 details 不从显示文本反向解析：

- `src/tools/shell.py::run_shell()` 在 `ToolResult.metadata` 直接返回 `return_code` 和由负 return code 派生的 `signal`。
- `src/tools/workspace.py::list_files()` 返回规范化 path、recursive、max_entries 和条目数；正文仍是完整目录列表。
- `JCodeAgent.ask_user()` 与 todo 三个方法返回运行结果同时提供 `response_status/selected_choice/answer` 或 `operation/todo_status/remaining_count` metadata；`ToolExecutor._execute_runtime_tool()` 原样并入 ToolResult。
- plan mode 方法只更新 `runtime_state`，其 metadata 不进入 observation。

`files.records` 是文件事实的唯一来源，`files.hot/files.cold` 只是由 records 重算的有序路径索引。每次读取、搜索或修改先更新 records，再用 4.4 的稳定排序重建两个索引，禁止分别修改三处导致漂移。每个 path 最多保留 current 和 previous_stale 两个版本；新版本进入时覆盖更老 stale。

#### 4.2 修改 runtime 写入顺序

在 `src/runtime/agent.py`：

- `_begin_run()` 把 `working_memory.task_goal` 设置为 `task_state.user_request`；不再清空。
- `ask()` 在输出截断续写时仍把 `task_state.user_request` 传给 ContextManager；`CONTINUATION_REQUEST` 作为瞬时内部续写 input，不能写入 task goal。
- `src/tools/workspace.py::read_file()` 删除 `working_memory` 参数和内部 `note_file_read()` 副作用，只返回正文及完整读取 metadata；`ToolExecutor.execute()` 同步删除 read_file 特殊注入。`_execute_tool_call()` 在 candidate Working Memory 上调用 `note_file_read()`；对 `search` 的 `source_files` metadata 调用 `note_search_sources()`。
- write/patch 成功后先逐个重新读取 `freshness()`，调用 `note_files_modified()`，再执行 `_mark_stale_file_evidence()`；刷新失败抛 `FreshnessRefreshError`。
- 完成上述更新后才追加 tool result History、Working Memory observation、continuation output、trace 和 checkpoint。

`_execute_tool_call()` 开始时复制 Working Memory；`read_file` 及后处理只修改该 candidate。safe 参数投影、必要 artifact 写入、source freshness 校验全部成功后，才一次性替换活动 Working Memory 并追加 History/continuation。write/patch 已经发生的文件系统副作用无法回滚；若其后 freshness 或 artifact 步骤失败，统一边界使用相同 call ID 追加 `status="system_error"` 的终止 tool result（能够持久化时），明确记录 changed files 和原始系统错误，同时停止运行，不能把它记为普通工具失败或留下已闭合 turn 的孤立 call。

#### 4.3 plan mode 和子 Agent 边界

- `PlanModeController.enter()/exit()` 继续更新 session `runtime_mode`，同时同步 `working_memory.runtime_state`。
- `enter_plan_mode/exit_plan_mode` 的 tool call/result 仍由 `_record_model_history()` 和 `_execute_tool_call()` 写 History，但不调用 `record_tool_observation()`。
- `src/tools/registry.py` 中三个子 Agent `registry.register(...)` 前各增加一条简短中文注释，说明 9.5 暂未定义生命周期压缩和 Working Memory 投影。

#### 4.4 hot/cold 选择

按 Level 使用 `30/20/16/12/12` nominal hot 上限。稳定比较键按降序布尔优先和最近值优先实现：

```text
user_mentioned
modified_in_current_run
current_freshness
incomplete_read
last_access_order
last_modified_time
task_relevance
normalized_path
```

`normalized_path` 只作为最终稳定 tie-breaker。全部 user-mentioned 文件强制 hot，可以超过 nominal 上限；其余文件进入 cold，只在 session 保存索引，不进入当前 Provider view。

### 阶段 5：结构化 History 编译和工具原子

#### 5.1 删除 ContextManager 的重复文本管线

从 `src/context/manager.py` 删除：

- `SECTION_ORDER`、`CURRENT_REQUEST_SECTION`、`MIN_SECTION_BUDGETS` 的字符版本、`SECTION_RATIO_HINTS`、`PRESSURE_LEVELS` 旧表。
- `compute_section_budgets()`、`_SectionRender`、`_build_prompt()`、`_base_budgets()`、`_budget_tokens()`。
- `_build_sections_texts()`、`_build_history_section_texts()`、`_build_history_text()`、`_build_history_item_text()`、`_build_turn_history_text()` 及其 block 渲染辅助函数。
- `_reduce_working_memory_for_pressure()` 和所有 `tail_clip()` 路径。
- 现有 `_compress_old_tool_history_item()`、80 字符截断、shell 前三行、artifact-path-only 旧规则。

保留并重写 `_group_turns()`，所有预算、审计和 Provider 请求只使用结构化 `HistoryEvent`。

#### 5.2 建立 History 原子编译

新增以下私有函数：

- `_ordered_turns()`：按 session 事件出现顺序分组，不按 turn ID 或时间字符串排序。
- `_continuation_call_ids()`：从 continuation 提取实际存在的 function call/output call ID。
- `_build_turn_atoms()`：把同一 `call_id` 的 `tool_call + tool_result` 组成不可拆原子；普通 user/assistant 是单事件原子。
- `_select_history_window(level)`：固定返回 `7/5/4/3/3`，数量包含当前 turn。
- `_compress_old_tool_result_400_100_400()`：按 Python 字符取首 400、正中心 100、尾 400，加入明确省略标记并保留 metadata。
- `_project_large_tool_arguments()`：窗口外 write/patch 超过 2000 字符时调用安全参数 artifact 规则，Provider 字符串保留前 100、后 100 和裸路径。
- `_merge_old_list_files_atoms()`：按规范化 path 只保留事件顺序最后一个完整原子。

当前 user History event 不再被 `_build_structured_history()` 跳过。History 去重不再按 `continuation_run_id` 删除当前 run 的所有工具事件，而是仅排除 continuation 中实际存在的 `(item type, call_id)`；当前 assistant 正文仍保留。

原子只用于选择，最终 Provider input 仍按 session 原事件顺序渲染，不能因为配对而重排多工具调用。已闭合 turn 中只有 call 或只有 result 的旧孤立事件整体不进入 Provider，并在 `compression_records` 记录 `orphan_tool_protocol_event`；当前 turn 中尚在执行、且 continuation 已有原生 function call 的未闭环调用允许暂存。`ProviderContinuation` 每次发送前另做 call ID 闭环校验：已执行完成的调用必须同时具有 function_call 与 function_call_output。

400/100/400 的边界固定为：正文长度 `<=900` 时原样返回；`>900` 时中心起点为 `(len(text)-100)//2`，分别计算 head/center/tail 区间，只在两个相邻区间之间确有字符被省略时插入省略标记。这样奇偶长度、901 字符和更长正文都不会重复字符或伪造省略量。

#### 5.3 `list_files` 规则

- 完整窗口内所有 list-files 调用/结果原样保留。
- 窗口外 grouping key 只用 `workspace.resolve_path(path)` 后的规范化 workspace-relative path。
- `recursive/max_entries` 不进入 key。
- session 事件顺序最后一次成功、失败或中止结果覆盖旧快照。
- 只有同时存在 call 和 result 的完整原子参与保留；删除时按 call ID 同时删除两项。
- 当前尚未获得 result 的调用只允许存在于当前 turn/continuation，不得被当作旧目录快照。
- Level 0 虽以 7 turn 作为“始终原样保留”的窗口边界，但不压缩窗口外内容；由于 Level 0 的原始需求必然能放入 flexible budget，最终应保留全部合法旧 History。Level 1-3 才把窗口外事件变成压缩候选，Level 4 则把窗口外 turn 交给摘要事务。

### 阶段 6：动态 token 预算和单次定档

#### 6.1 重写 `ContextManager.build()`

新的 `build()` 接收：

```text

working_memory
task_goal
internal_continuation_instruction
allowed_tools
provider_continuation
model_profile
actual_max_new_tokens
run_dir
```

其中 `task_goal` 始终为 `task_state.user_request`；只有输出被截断续写时才传 `internal_continuation_instruction=CONTINUATION_REQUEST`。

执行顺序固定为：

1. 深复制 session 和 Working Memory，刷新 todo/runtime state，不修改活动对象。
2. 一次生成 tools definitions、完整 instructions、全部 skill entries、未压缩 History、未压缩 Working Memory 和 continuation 分类。
3. 用公共 Provider compiler 生成未压缩 `instructions/input/tools`。
4. 计算普通输入 occupancy、reasoning continuation、tool continuation、output reservation 和 safety margin。
5. `fixed_demand` 超有效窗口时抛 `MandatoryContextExceedsWindowError`。
6. 计算 flexible budget、raw flexible demand 和原始 pressure level，只定档一次。
7. 按该 Level 生成 History/Working Memory/Skills 候选原子，并标出 Level 规则要求完整保留的原子。
8. 先放入必保原子，再为三个 section 补足 `min(raw demand, minimum)`；实际原子总和放不下时抛 `SystemMinimumBudgetOverflowError`。
9. 对剩余候选做一次全局稳定排序和打包。
10. 若 Level 4 需要历史摘要，进入阶段 7 的候选事务；否则编译最终 `ContextResult`。
11. 从最终 `ContextResult.provider_input` 重新计量；公式失败抛 `FinalContextExceedsWindowError`，成功才返回。

固定输入明确包括完整 instructions、tools schema、Provider envelope、当前 turn 中未由 continuation 承载的实际 History、完整 task goal、瞬时内部续写指令以及两类 continuation。内部续写指令归入当前 turn 固定输入，不参加 section 最低保障或候选竞争。

History 在步骤 2 就拆成 `current_turn_atoms` 和 `previous_turn_atoms`：前者计入 fixed demand，后者才进入 History section。`7/5/4/3/3` 是包含当前 turn 的原始完整窗口；窗口内旧 turn 原子由 Level 规则标为必保，不能在全局竞争中淘汰，窗口外才进入普通候选。Level 0 不做裁剪，因此全部合法旧 History 都标为必保。Level 4 的 session candidate 和 Provider 视图都保留当前 turn 加最近两个闭合 turn，窗口外旧 turn 只通过 compact summary 提供。

Level 必保原子只包括原始 History 窗口内的旧 turn、全部 core skill，以及 4.4 强制晋升的 user-mentioned hot 文件。它不是 preferred/maximum 子预算，审计必须单列 `level_required_tokens`。它与 section minimum 一起从 flexible budget 支付：若必保原子本身已超过该 section 的最低目标，不再为空缺最低值预留 token；若所有必保原子总和已经超过 flexible budget，同样抛 `SystemMinimumBudgetOverflowError` 并列出造成溢出的原子。窗口内超长 `list_files` 因而只能完整发送或明确停止，不能裁剪、外置或悄悄删除。

最低保障按不可拆原子实现：每个 section 从尚未被 Level 规则选中的候选中，按该 section 的稳定优先级加入完整原子，直到“Level 必保 + 补入候选”的累计 token 首次达到 `min(raw_section_demand, configured_minimum)`。审计同时记录目标值、Level 必保值和因最后一个原子产生的实际值；三个 section 的实际值之和超过 flexible budget 时抛 `SystemMinimumBudgetOverflowError`。禁止把最后一个原子裁开来精确凑数。

候选的 token 增量不能在候选创建时永久缓存。每次尝试加入一个原子，都按最终 source order 重建临时 `instructions/input/tools`，用同一 TokenizerAdapter 计算“加入后 serialized token - 加入前 serialized token”；接受后把这个决策时增量写入 `ContextBudgetCandidate` 审计，拒绝则记录所需增量和剩余量。最低保障与全局竞争共用这条路径，避免 BPE 边界和候选重排造成累计值失真。

规范 `input` 顺序固定为：选中的 skill entries、按事件顺序的 History、Provider continuation 原生 items、Working Memory provider view、可选的 `internal_continuation_instruction`。task goal 位于 Working Memory core；当前 user event 位于 History，因此接受双份输入但只从 `task_state.user_request` 生成一次原文快照。

#### 6.2 全局候选的确定性顺序

最低保障阶段完成后，候选不再拥有 section preferred/maximum。统一比较键为：

```text

last_access_order

```

排序方向固定为：`priority_class` 升序；所有布尔值按 true 在前；`task_relevance`、`last_access_order` 降序；`source_order` 升序；`stable_name` 按 Unicode code point 升序。没有对应字段的候选使用 false/0，不允许使用当前时间或 dict/set 遍历顺序作为 tie-breaker。

`priority_class` 固定为：

1. 未解决安全状态、未完成 todo/提问、当前相关 hot file。
2. Level 原始窗口内的旧 turn 原子和最新有效工具证据。

4. 窗口外旧 History 证据和已结束工具观察。
5. cold 文件索引、旧恢复信息和终态审计索引。

比较键只决定是否打包，不裁剪候选内部正文。相同 call ID 的调用/结果、单个 skill 条目和单个结构化观察均不可拆。

### 阶段 7：Level 4 摘要容量和候选事务

#### 7.1 提取摘要模块

新增 `src/context/summary.py`：

- `build_summary_request()` 只加入摘要 instructions、合法旧摘要和本次淘汰旧 turns。
- `call_summary_model()` 使用当前 model profile，timeout 120 秒；首次失败后等待 2 秒、4 秒各重试一次，总调用数最多 3。
- `build_deterministic_summary()` 只读取结构化 metadata；普通 assistant content 不参与事实提取。
- `validate_summary_payload()` 校验 JSON、字段类型、短对象约束和每个 artifact 路径。

从 `ContextManager` 删除现有 `_summarize_compacted_history_deterministic()`、`_collect_sentences()`、`_collect_paths()`、`_collect_blockers()`、`_collect_next_steps()` 和 Markdown 摘要逻辑。

#### 7.2 摘要请求独立容量检查

摘要请求不使用普通 ContextResult，不携带 tools、普通 Working Memory 或 Provider continuation。`ModelRouter` 增加 `complete_summary()`，DeepSeek/MiniMax 使用同一 HTTP/响应解析但编译最小 payload。

具体契约为 `complete_summary(summary_provider_input, *, profile_id, max_output_tokens, timeout_seconds)`：`summary_provider_input` 只含摘要 instructions 和 input，tools 固定为空数组；client 复用认证、HTTP 和普通 response text 解析，不允许把普通 ContextResult 或当前运行 continuation 填进去。摘要请求也使用当前 profile 对应的同一个 TokenizerAdapter。

在调用模型前：

```text
available_summary_output =
    effective_context_window_tokens
    - summary_input_tokens
    - 7500

summary_output_reservation =
    min(actual_max_new_tokens, available_summary_output)
```

若 reservation 小于 2048，直接执行确定性摘要。artifact 缺失/损坏立即抛系统错误，不进入模型重试。HTTP/transport 错误、timeout、非 JSON、summary schema 错误都算一次摘要调用失败；每次失败保留审计但不接受半合法结果。三次调用均失败后执行确定性摘要；确定性摘要 schema 或最终容量失败则停止运行，不回退 Level 3。

#### 7.3 候选事务顺序

替换现有 `ContextManager.compact_history()` 原地修改逻辑。Level 4 顺序必须逐条实现：

1. 从活动 session 深复制 `original_history`，按事件顺序划分淘汰 turns 和包含当前 turn 的最近 3 turns。
2. 用新增 `RunStore.write_history_artifact()` 写 `history-before-compact-<sequence>-<sha12>.json`；文件名不复用，已存在时只允许校验同内容，不覆盖。
3. 用 `read_verified_artifact()` 重新读取并核对 SHA-256。
4. 基于合法旧 compact summary 和淘汰 turns 生成摘要并验证；若旧摘要损坏或版本不兼容，按下面的 rebuild 规则处理。
5. 在 `session_candidate` 中创建 compact-summary event，加上保留的 3 turns；event sequence 只在 candidate 中递增。summary event metadata 保存 `summary_version`、本次 history artifact path/hash 以及累积的版本化 artifact 链，供后续 rebuild 使用，但不进入 Provider 正文。
6. 摘要只写入 session 的 `compact_summary` 历史事件，不再同步到 Working Memory，避免重复进入 Provider 上下文。
7. 用 candidate 再调用最终 Context 编译和容量校验。
8. 容量成立后由 `JCodeAgent._build_context()` 调用 `SessionStore.save(session_candidate)`。
9. `os.replace()` 成功后才执行 `self.session = committed_session`、`self.working_memory = working_memory_candidate`，并重新绑定 `session_path/plan_mode` 所需引用。
10. 最后写 compact completed 事件和 context audit，再调用 Provider。

session commit 失败时，旧磁盘 session 和活动内存对象不变；已写且校验成功的 History artifact 可以成为无引用孤立文件。session 成功后 Provider 即使失败，compact History 仍保持已提交状态。

`compact_summary_rebuild_on=True` 时，从旧 summary event metadata 的 artifact 链按 sequence 升序逐个验签读取；只收集非 `compact_summary` 事件，以 `event_id` 去重，首次出现决定原始顺序，后续同 ID 内容不同视为完整性错误。再追加当前 artifact 中此前未出现的事件并按 turn 的首次事件顺序分组，形成重建输入。禁止把 artifact 链本身、event ID 列表或任何来源 turn 清单写入 Provider summary JSON。rebuild 关闭时不读链，只忽略坏摘要并基于本次淘汰 turns 生成新摘要，同时记录已冻结的 hurt/rebuild 审计字段。
