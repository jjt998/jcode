# 恢复上下文携带完整工作区基线导致后续 run 爆量

## 发现日期

2026-09-09

## 现象

同一会话第二次发送 run 后，上下文占用突然大幅增加，随后进入高压或无法继续执行。

## 复现证据

会话文件：`demo_test/snake_game/.jcode/sessions/20260908T161419.713153+0000-531032.json`

- 第一个 run 的上下文约为 `16,883` tokens。
- 第二个 run 第一次上下文约为 `124,022` tokens。
- `resume_context` 中包含递归 workspace baseline，覆盖 `.git`、`node_modules` 及其大量文件的 size/mtime 信息。

## 根因

`build_resume_context()` 将完整 `workspace.baseline()` 放入恢复上下文，`WorkingMemory.render()` 再将整个字典发送给 Provider。恢复元数据因此从本地校验数据变成了模型输入，占用大量上下文空间。

## 影响

后续 run 的有效上下文容量被大幅挤占，Level 4 压缩无法抵消该固定开销，可能导致上下文超限或 Provider 请求失败。
