# 恢复上下文完整变更路径导致后续 run 爆量

## 发现日期

2026-09-10

## 现象

同一会话的前一 run 上下文约为 `9.35` 万 token，下一 run 在尚未执行任何工具前直接增至约 `22.85` 万 token。

## 复现证据

会话文件：`demo_test/snake_game/.jcode/sessions/20260910T075224.152206+0000-221af9.json`

- `run-9b74e3af65` 的第二次上下文构建有 `431` 个历史事件，输入为 `93,547` token。
- 紧接着的 `run-7ec4def7af` 第一次上下文构建共 `439` 个历史事件，比前一快照仅多出前一 run 收尾事件和一个新用户事件，输入却为 `228,534` token。
- 前者 `resume_context` 序列化后为 `5,257` 字符，`changed_paths` 为空。
- 后者 `resume_context` 序列化后为 `535,621` 字符，含 `4,406` 条 `changed_paths`；其中 `4,405` 条位于 `pvz/node_modules`，另有 `pvz/package-lock.json`。
- Provider 的 `role:user` 输入从约 `13,274` 字符增至约 `551,781` 字符，增量来自 Working Memory 渲染的恢复上下文。

## 根因

`build_resume_context()` 为本地 stale 检查生成完整 `changed_paths` 后，直接将该列表放入 `resume_context`。`JCodeAgent._begin_run()` 将该对象赋给 Working Memory，`WorkingMemory.render()` 使用 `str(self.resume_context)` 将完整字典发送给 Provider。

9.5 已移除完整 `workspace_baseline` 的模型注入，但完整派生变更路径仍穿过同一条渲染链路。当运行 Vite 后 `node_modules` 及缓存文件变化时，该列表足以占满大量上下文。

## 影响

后续 run 在模型请求前消耗大量固定输入容量，压缩等级被抬高，工具循环中的每次请求也会重复携带这些路径。工作区真实变更越多，问题越明显。
