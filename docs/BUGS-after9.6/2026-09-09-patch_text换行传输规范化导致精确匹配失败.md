# patch_text 换行传输规范化导致精确匹配失败

## 方案日期演进

- **2026-09-08**：完成原始字节读取一致性、newline/BOM 元数据和失败诊断，但仍要求模型保留 CRLF。
- **2026-09-09**：确认模型参数传输会将 CRLF 规范化为 LF，正式修订为仅允许 LF/CRLF 传输等价匹配，并把诊断信息放入模型可见正文。

完整合并方案见 [`docs/BUGS-solve/2026-09-09-patch_text换行传输规范化导致精确匹配失败.md`](../BUGS-solve/2026-09-09-patch_text换行传输规范化导致精确匹配失败.md)。

## 发现

2026-09-09 在 `snake_game` 项目中执行 `apply_patch` 时，模型先成功读取了 `apply_patch_test.js`，随后使用读取结果构造跨行 `old_text`，但工具连续返回：

```text
old_text matched 0 times; expected exactly 1; file_newline=crlf
```

## 证据

- `read_file` 与 `apply_patch` 操作之间文件 freshness 未变化，文件没有被外部修改。
- 磁盘目标片段使用 CRLF：8 个 `CRLF`，长度 315 字符。
- 模型提交的 `old_text` 使用 LF：0 个 `CR`、8 个 `LF`，长度 307 字符。
- 将模型参数中的 LF 转换为 CRLF 后，文本与磁盘目标片段完全一致。
- 因此不是内容、缩进、大小写或匹配次数错误，而是模型工具参数传输过程中 CRLF 被规范化为 LF。

## 根因

当前 `read_file` 和 `apply_patch` 已使用原始 UTF-8 字节读取并保留文件换行格式，但模型在上下文传递或生成工具参数时不能稳定保留 `\r`。`apply_patch` 仍按原始文本逐字符匹配，导致模型从合法读取结果生成的 LF 文本无法命中磁盘 CRLF 文本。

此前仅统一底层字节读取并增加失败诊断，没有解决模型无法稳定携带 CRLF 的协议问题。

## 影响

所有包含跨行 `old_text` 的 CRLF 文件都可能反复返回匹配失败。重复调用治理还会拒绝相同参数，导致模型无法靠简单重试恢复，阻塞正常修改任务。

## 边界

本问题只涉及 LF 与 CRLF 的换行传输差异。空格、缩进、大小写、正文内容和匹配唯一性仍必须精确一致；不允许引入模糊匹配、自动猜测、静默删除或其它降级行为。
