# JCode 工具治理完整链路

本文描述当前 JCode 从模型输出工具调用，到执行、证据持久化、文件新鲜度失效、上下文回注与恢复校验的完整治理链路。本文以当前代码行为为准。

## 1. 总览

```text
模型响应
  -> 协议解析
  -> 工具调用序列
  -> ToolExecutor 统一校验与治理
  -> 工具执行
  -> 结果外置 / artifact read 特殊处理
  -> history / trace / checkpoint
  -> 文件变更使旧证据 stale
  -> ContextManager 渲染下一轮上下文
```

主要入口：

- `src/runtime/agent.py`：驱动一次 agent 回合、记录历史、处理 artifact 与 stale。
- `src/tools/executor.py`：每个工具调用的统一执行与策略编排入口。
- `src/tools/workspace.py`：文件、搜索等工作区工具的具体实现。

## 2. 模型工具协议

模型输出由 `src/runtime/actions.py:parse_model_action()` 解析，只接受一类主协议：

```text
<tool name="tool_name">{"arg":"value"}</tool>
<tools>[{"name":"tool_name","args":{}}]</tools>
<final>answer</final>
```

复杂任务可在主协议前附加一个 `<reasoning>...</reasoning>`。`<tools>` 内的调用按数组顺序逐个执行；前一个失败不会自动阻止后续项，除非运行被主动中止。

协议解析失败会记录为 assistant 的无效输出，并追加一个 `parser` 工具错误历史项，不会进入真实工具执行。

## 3. 工具执行顺序

每次工具调用都会进入 `ToolExecutor.execute()`，顺序如下：

```text
1. 工具查找
2. Pydantic 参数校验
3. ToolProfile 工具集校验
4. 写入范围校验
5. 重复调用治理
6. runtime 工具分支，或 ToolPolicyChecker
7. 权限校验
8. shell sandbox 校验
9. 执行具体工具
10. risky 工具前后快照比较，补充 changed_files
11. SecretRedactor 处理结果
12. 返回 ToolResult 与统一 policy metadata
```

任一治理层拒绝时，结果状态为 `denied`，并携带拒绝原因、策略层级和调用元数据。

## 4. 工具集、范围与基础策略

### 4.1 ToolProfile

`src/policy/tool_profiles.py` 根据运行模式限制可用工具：

| Profile | 约束 |
|---|---|
| `default` | 所有注册工具 |
| `plan` | 只读工具、runtime 工具、`write_file`、`apply_patch` |
| `readonly` | 仅只读工具 |
| `worker` | 不允许 `run_shell`、`ask_user`、计划切换工具 |
| `dream` | 只读工具及文件写入工具 |

### 4.2 写入范围

有 `write_scope` 时，`write_file` 与 `apply_patch` 的目标必须位于允许根路径内。路径均先经 `Workspace.resolve_path()` 规范化并阻止逃逸工作区。

### 4.3 读后写

`ToolPolicyChecker` 的当前规则：

- `write_file`：新文件允许直接创建；已有文件必须曾被成功 `read_file` 读取过。
- `write_file` 只按路径是否出现于 `working_memory.file_freshness` 判断，不校验 freshness。因此同一文件之后被修改，仍允许连续写入。
- `apply_patch`：保留原有“目标路径曾被读取”的门槛。
- plan 模式可写当前 active plan artifact。
- `apply_patch` 的 `old_text == new_text` 被拒绝。
- `run_shell.timeout` 必须处于 1 到 600 秒。

## 5. 重复调用治理

### 5.1 `read_file` 专用计数

`read_file` 不走通用 `CallGuard`，而是在 `WorkingMemory.read_file_counts` 中计数。

计数 key 是：

```text
read_file + 规范化路径 + max_chars + start + end + freshness
```

规则：

```text
前 3 次成功读取允许
第 4 次相同读取拒绝
文件 freshness 改变后，对新版本从 0 重新计数
不同 start/end 范围独立计数
读取失败不计数
```

第 4 次拒绝时会提示模型不要重复读取已知的未变化内容，并建议在缺少结果时使用 `ask_user` 决定下一步。

### 5.2 其他工具的 `CallGuard`

其他工具由 `src/policy/call_guard.py` 计数，key 是：

```text
工具名 + 规范化完整参数 + context_key
```

规则同样是前三次允许、第四次拒绝。通用 CallGuard 在具体工具执行前记录，因此对非 `read_file` 工具，参数校验成功后的调用尝试会占用次数，即使后续策略或执行失败。

### 5.3 `run_shell` 的工作区版本

`run_shell` 的 `context_key` 使用 `Workspace.fingerprint()`：

```text
run_shell("pytest") + fingerprint A
  -> 前三次允许

文件修改，fingerprint 变为 B
  -> 同一 pytest 作为新 key，再次允许前三次
```

该 fingerprint 是低成本近似：只覆盖有限的工作区元数据，可能漏掉深层目录或高频变更。当前取舍是接受这种不精确，以较低开销允许文件修改后重新执行相同测试命令。`.jcode` 被排除，不会因 artifact、trace、checkpoint 自身改变而重置 shell 额度。

## 6. 文件读取与搜索证据

### 6.1 `read_file`

`read_file` 的执行步骤：

```text
读取 UTF-8 文件
  -> 先按 start/end 截取
  -> 再按 max_chars 截取
  -> 记录路径 freshness 到 WorkingMemory
  -> 返回 source_files 与 missing_chars metadata
```

返回 metadata 示例：

```json
{
  "source_files": [{"path": "src/app.py", "freshness": "mtime_ns:size"}],
  "missing_chars": 1200
}
```

普通文件被 `max_chars` 截断时，工具正文保持截断内容，不追加提示。

### 6.2 `search`

`search` 会遍历目标目录下的文本文件，跳过 `.jcode`。对每个成功扫描的文件记录：

```json
{"path": "src/app.py", "freshness": "mtime_ns:size"}
```

这些记录写入 `ToolResult.metadata.source_files`。记录所有成功扫描文件，而不是只记录命中文件，因为“没有命中”的搜索结果也依赖这些文件当时没有出现匹配文本。

当达到 `max_results` 时，搜索立即结束，`source_files` 只包含实际已扫描的文件。

## 7. 大工具结果与 Artifact

### 7.1 普通大结果外置

`JCodeAgent._execute_tool_call()` 对非 artifact-read 结果调用 `prepare_tool_result_observation()`。

规则：

```text
结果长度 <= 1000 字符
  -> 直接内联

结果长度 > 1000 字符
  -> 完整文本写入 .jcode/runs/<run_id>/artifacts/
  -> history metadata 记录 full_output_artifact、原始字符数、SHA-256
  -> 模型看到路径和前 1000 字符预览
```

artifact 对模型可见的路径是相对 workspace 的：

```text
.jcode/runs/<run_id>/artifacts/<tool>-output-<hash>.txt
```

artifact 文件是当次工具结果快照，不会随源文件后续修改而被覆盖或删除。

### 7.2 artifact read 特殊分支

`ToolExecutor` 在 `read_file` 成功后识别当前协议的 artifact 路径：

```text
.jcode/runs/.../artifacts/...
```

并写入：

```json
{"artifact_read": true}
```

上游 `JCodeAgent` 根据该标记执行特殊处理：

1. 不再调用 `prepare_tool_result_observation()`，防止 artifact A 被读取后再生成 artifact B。
2. 用 artifact 路径在既有 history 中反查 `metadata.full_output_artifact`。
3. 找到原始工具结果后，复用它已有的 `source_files`。
4. 若 `missing_chars > 0`，在当前 artifact read 结果末尾追加：

```text
[read_file result is truncated, the missing chars are <n>; use start/end to continue reading.]
```

因此模型读取超大 artifact 时应使用 `start/end` 分段获取后续内容；当结果确实被 `max_chars` 截断时，能够知道还缺多少字符。

### 7.3 系统提示约束

系统提示明确要求：

```text
When reading a large artifact under .jcode/runs/.../artifacts/, use read_file with start and end to inspect it in segments. Artifact reads are returned directly and must not be externalized again.
```

当前 artifact 预览文本的展示形式是：

```text
whole tool result in: .jcode/runs/<run_id>/artifacts/...
below is partial:
...
```

注意：另一条系统提示仍使用“tool result starts with a workspace-relative artifact path”的措辞，但当前实际展示不是路径首行，而是将路径嵌入 `whole tool result in:` 行中。上下文压缩通过路径正则识别该引用；这是当前提示措辞与实际渲染之间的已知差异。

## 8. 文件变更与 stale 证据

`write_file`、`apply_patch` 或其他 risky 工具成功后，如果结果含有 `changed_files`，agent 调用 `_mark_stale_file_evidence()`。

处理逻辑：

```text
changed_files
  -> 遍历 history 中的 read_file 与 search 工具结果
  -> source_files.path 与 changed_files 相交
  -> metadata.stale = true
  -> metadata.stale_reason = source_file_changed
  -> metadata.stale_paths = 命中的路径
```

由于 artifact read 继承原始工具结果的 `source_files`，原始读取结果和其 artifact 分段读取结果都会在对应文件改变后 stale。

`run_shell`、`search` 等没有 `source_files` 的普通工具结果不会仅因文件变化自动 stale。

## 9. 上下文渲染与压缩

`ContextManager` 把 session history 渲染成模型下一轮可见的 Transcript。

处理顺序中的关键规则：

1. stale 的 `read_file` 结果优先被替换为过期提示，不输出旧正文或旧 artifact 路径。
2. 非 stale 的历史大结果可被压缩为 `.jcode/runs/.../artifacts/...` 路径。
3. 普通旧 `read_file` 会进行重复路径压缩。
4. 普通 `run_shell` 历史只保留前三条非空输出行。
5. 其他可压缩工具通常只保留前 80 个字符。

上下文压缩只识别新 artifact 路径协议：

```text
.jcode/runs/<run_id>/artifacts/<file>
```

旧的 `artifacts/<file>` 不再被识别或兼容。

compact summary 当前不做 freshness 溯源、stale 标记或提示处理。

## 10. 权限、Sandbox 与副作用记录

### 10.1 权限

`PermissionChecker` 根据 approval 模式决定 risky 工具是否允许。`approval=never` 时 risky 工具被拒绝；`auto` 直接允许；`ask` 当前产生 assumed allow 决策。

### 10.2 Shell Sandbox

`run_shell` 会额外进入 `SandboxPolicy`。`required` 但 sandbox 不可用时拒绝；`best_effort` 和 `disabled` 可直接运行。

### 10.3 副作用

标记为 risky 的工具执行前后都会调用 `Workspace.snapshot()`。执行结束后，executor 根据快照差异补齐 `changed_files`，包括工具本身未显式填写的变更。

若工具异常但工作区已经改变，结果状态为 `partial_success`；未检测到变更则为 `error`。

## 11. History、Trace 与 Checkpoint

每个工具调用会：

```text
记录 tool_requested trace
  -> 执行和治理
  -> 记录 tool history item
  -> 记录 tool_executed trace
  -> 创建 checkpoint
  -> 写入 task_state
```

history item 持有：

```text
name、args、tool_status、changed_files、artifacts、metadata、run_id、turn_id
```

这使得 artifact 路径、source freshness、stale 标记和策略决策能够随 session 持久化。

checkpoint 保存 `working_memory`、`file_freshness`、最近读取文件、workspace fingerprint 等。恢复时：

- workspace fingerprint 不同：`workspace_mismatch`；
- 读取过的文件 freshness 不同：`partial_stale`，并返回 `stale_paths`；
- 均一致：`full_valid`。

checkpoint 的 freshness 检查不会删除历史工具结果或 artifact，只用于判断恢复上下文的新鲜度。

## 12. 当前边界与取舍

- `write_file` 只要求路径曾被读取，不要求读取 freshness 与当前文件一致。这是为了允许连续修改；模型自行决定是否应重新读取验证。
- 普通 `read_file` 截断不提示，只有 artifact read 才提示剩余字符数。
- artifact read 的 `source_files` 依赖原始 artifact 生产 history 仍可访问；若该历史已被 compact 移除，无法反查并继承来源。
- compact summary 不参与 stale 治理，可能仍包含旧文件内容。
- `search` 记录所有扫描文件，目录很大时 metadata 也会相应增大。
- `run_shell` 使用近似 fingerprint 重置重复调用额度，可能漏检部分变更，也可能因根目录元数据变化而额外放开一次重试。
- 通用 CallGuard 统计调用尝试；`read_file` 只统计成功读取。这两个计数口径当前不同。
- `.jcode` 不在普通 `list_files`、`search`、workspace snapshot 和 fingerprint 的常规工作区扫描范围内，但 artifact 可通过明确路径被 `read_file` 读取。
