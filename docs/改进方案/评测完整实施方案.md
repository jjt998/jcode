# JCode 评测完整实施方案

## 1. 目标与范围

本文将《评测补充》中的冻结协议落地为从 Case 定义到 CI/基线对比的完整闭环：

\`\`\`text
评测协议
-> Case 数据集
-> 场景准备与隔离
-> 评测运行器
-> RunRecord 标准化
-> 离线评分与回放
-> Baseline / Ablation
-> CI 质量门禁
\`\`\`

评测结果必须可复现、可自动判定、可离线重评分、可回放和可进行版本比较。

本文只规定实施方案，不改变《评测补充》已经冻结的场景和评分语义。未在协议中定义的降级、兼容、重试、裁剪、删除、跳过或自动修复不得在实现中自行增加。

## 2. 目录集中原则

评测相关代码统一放在仓库根目录的 \`eval/\` 下，避免评测逻辑分散在业务模块和普通测试目录中，保持高内聚、低耦合。

\`\`\`text
eval/
  README.md                         # 评测入口、环境和运行命令
  schema/                           # 机器可校验的数据协议
    case.schema.json
    run_record.schema.json
    score.schema.json
    manifest.schema.json
  cases/                            # 版本化 Case 数据集
    checkpoint_resume/
      R1-valid-checkpoint.yaml
      R2-stale-file.yaml
      R3-workspace-drift.yaml
      R4-incompatible-checkpoint.yaml
      R5-shell-partial-success.yaml
      R6-tool-chain-partial-success.yaml
    context_compression/
    layered_memory/
    tool_governance/
  fixtures/                         # 可复制的初始 workspace 和状态材料
  manifests/                        # 评测集版本、模型和环境清单
  runner/                           # 场景准备、JCode 启动、证据收集
  scorer/                           # 离线 RunRecord 和评分
  replay/                           # trace、状态和 diff 回放
  baselines/                        # 直接模型和简单 ReAct 对照实现
  reports/                          # 本地生成的结果，不提交密钥
  tests/                            # 评测运行器、评分器和协议测试
\`\`\`

业务代码继续放在 \`src/\`。产品模块的单元测试继续放在 \`test/\`；只有评测场景、评测运行器、评分器、协议和基线相关测试归入 \`eval/tests/\`。

## 3. 既有评测代码迁移

迁移前先建立清单，不直接移动全部 \`test/\` 文件。分类标准如下：

| 类型 | 判定 | 目标目录 |
| --- | --- | --- |
| 产品单元测试 | 只验证一个类、函数或模块契约 | \`test/\` |
| 产品集成测试 | 验证多个业务模块协作，但不属于评测指标 | \`test/\` |
| 评测场景测试 | 注入恢复、压缩、记忆或治理场景，并产生评测结果 | \`eval/tests/\` |
| 评分器测试 | 验证 RunRecord、谓词、评分和红线 | \`eval/tests/\` |
| 运行器测试 | 验证 fixture 隔离、进程启动、证据收集 | \`eval/tests/\` |
| 基线测试 | 验证 Baseline / Ablation 的统一接口 | \`eval/tests/\` |

当前仓库优先检查并迁移或重构以下评测语义明显的测试：

\`\`\`text
test_checkpoint_timing.py
test_harness_timing.py
test_memory_closed_loop.py
test_session_checkpoint_v2.py 中的恢复场景部分
test_provider_continuation.py 中的恢复/续接场景部分
test_call_guard.py 中的工具治理场景部分
test_write_file_read_gate.py 中的工具治理场景部分
test_read_file_repeat_guard.py 中的工具治理场景部分
test_final_readiness.py 中的评分/收口场景部分
\`\`\`

迁移要求：

1. 先保留原测试语义，迁移后只改变位置和统一 fixture/入口。
2. 将一个测试文件中混合的产品单元测试和评测场景拆开，不整文件机械搬运。
3. 更新导入路径、pytest 配置和 CI 命令。
4. 迁移完成后，\`test/\` 不再包含评测运行器、评分器或 Case 数据集逻辑。
5. 迁移过程不得改变产品代码协议，也不得为了迁移增加兼容分支。

## 4. 评测协议与版本

### 4.1 Case Schema

每个 Case 至少包含：

\`\`\`yaml
case_id: resume-r2-stale-file
eval_version: "1.0"
category: checkpoint_resume
scenario: R2
description: 单文件事实过期后的重新校准
workspace_fixture: fixtures/checkpoint_resume/r2
prompt: 继续完成当前任务
model_profile: deepseek-pro
allowed_tools: [read_file, apply_patch, run_shell]
write_scope: [src]
fault_injection:
  type: external_file_change
acceptance_predicates:
  - checkpoint_status_is: partial_stale
  - stale_paths_include: src/main.py
  - latest_file_content_used: true
forbidden_behaviors:
  - patch_from_stale_content
  - silent_resume
scoring:
  task_execution: required
  harness_instruction: required
\`\`\`

Case 不保存 API key。Provider、模型和密钥通过运行环境或本地未提交配置注入。

### 4.2 协议版本

- \`eval_version\` 发生语义变化时必须递增。
- Case 的验收谓词变化必须在变更记录中说明。
- 结果中同时保存 Case 版本、运行器版本、评分器版本和 JCode 版本。
- 旧评测结果不因新评分器自动重写；需要显式重评分并标记评分器版本。

## 5. Case 数据集

第一版数据集固定为：

\`\`\`text
Checkpoint/Resume：R1-R6 六个核心场景
Context Compression：C1-C4 四类场景
Layered Memory：M1-M4 四类场景
Tool Governance：T1-T10 十个固定场景
\`\`\`

每个核心场景可以有多个参数变体，但对外报告按核心场景汇总。参数变体不得改变场景的核心验收语义。

每个类别提供一个 manifest，声明：

\`\`\`text
case 列表
fixture 版本
需要的 Provider 能力
超时和资源上限
是否允许真实模型
是否属于 deterministic smoke
\`\`\`

## 6. 场景准备与隔离

运行器对每个 Case 执行以下步骤：

\`\`\`text
读取 Case
-> 校验 Case Schema
-> 创建临时 workspace
-> 复制 fixture
-> 创建独立 .jcode 目录
-> 写入初始 session/checkpoint
-> 记录初始 workspace fingerprint
-> 注入规定的故障或外部变化
-> 启动 JCode
-> 收集运行证据
-> 计算最终 workspace diff
-> 输出 raw result 和 RunRecord
\`\`\`

隔离规则：

- 每个 Case 使用独立 workspace、session、run 和 \`.jcode\` 目录。
- 不复用上一个 Case 的 checkpoint、memory 或 Provider continuation。
- 真实项目目录不能作为评测运行目录。
- 失败时保留现场路径，并在结果中记录。
- 测试服务、子进程和 Web 服务必须在 Case 结束后停止。
- 故障注入只能修改 Case 声明的对象，不得通过未记录的外部脚本改变状态。

## 7. 评测运行器

运行器拆成四个高内聚组件：

### 7.1 CaseLoader

职责：读取 YAML/JSON Case、校验 schema、解析 manifest 和 fixture 引用。

不负责启动 JCode，不负责评分。

### 7.2 WorkspaceSandbox

职责：创建临时 workspace、复制 fixture、写入 session/checkpoint、注入外部变更、计算前后 fingerprint 和 diff。

不负责解释 Agent 行为。

### 7.3 JCodeRunner

职责：使用固定解释器和固定配置启动 CLI 或指定入口，管理超时、退出码、stdout/stderr、run_id 和进程清理。

不负责修改评分结果。

### 7.4 EvidenceCollector

职责：收集 \`trace.jsonl\`、\`report.json\`、\`checkpoint.json\`、session history、artifacts、最终 diff 和运行元数据，生成原始结果目录。

原始证据只读保存，不被评分器覆盖。

运行器命令接口建议：

\`\`\`text
eval run --case <case_id>
eval run --category <category>
eval run --manifest <path>
eval run --all
eval validate
eval list
\`\`\`

项目指定解释器必须固定为：

\`\`\`powershell
& 'D:\\jt\\ANACONDA\\envs_dirs\\jcode\\python.exe'
\`\`\`

原始证据转换为统一 RunRecord，至少包括：

\`\`\`text

runner_version
scorer_version
jcode_revision

started_at

model_profile

\`\`\`

\`\`\`text
raw evidence

\`\`\`

## 9. 离线评分器

评分器只读取持久化证据，不依赖运行时内存对象：

\`\`\`text
trace.jsonl
+ report.json
+ checkpoint.json
+ session history
+ artifacts
+ workspace diff
    -> RunRecord
    -> 验收谓词
    -> Agent Quality
    -> Harness Quality
    -> Assurance
    -> 红线检查
\`\`\`

评分模块边界：

- \`predicate_engine\`：文件、内容、命令、状态、路径和证据谓词。
- \`agent_quality\`：任务理解、执行正确性、工具决策、验证和交付。
- \`harness_quality\`：指令遵循、策略执行、状态管理、恢复、副作用和证据完整性。
- \`assurance\`：最终文本、执行证据、运行状态可信度。
- \`redline_checker\`：伪造成功、越权写入、丢证据、错误续接等不可平均的红线。
- \`report_builder\`：生成 Case、类别、版本和基线汇总。

评分结果必须包含判定依据和证据路径，不能只输出一个分数。

## 10. 回放工具

回放工具读取原始结果目录，提供：

\`\`\`text
按 Case 查看
按 run 查看
按事件顺序查看 trace
查看模型请求/响应摘要
查看工具调用和结果
查看 checkpoint/resume 判定
查看 workspace diff
查看每条评分谓词及证据
\`\`\`

回放不得重新执行工具或模型请求。缺失 artifact 时按当前协议展示不可用状态，不猜测原始内容。

## 11. Baseline 与 Ablation

所有对照必须使用相同 Case、workspace fixture、模型、Provider、超时和验收谓词。

### Baseline

\`\`\`text
Baseline A：直接模型调用，不使用 JCode Harness
Baseline B：简单 ReAct 工具循环
System C：完整 JCode
\`\`\`

### Ablation

\`\`\`text
JCode - Final Gate
JCode - Context Compression
JCode - Checkpoint/Resume
JCode - Tool Policy
JCode - Layered Memory
\`\`\`

对比指标：

\`\`\`text
任务成功率
Agent Quality
Harness Quality
恢复成功率
工具错误率
副作用识别率
伪造成功率
越权写入率
证据完整率
平均输入 token
平均工具调用次数
P95 延迟
\`\`\`

Baseline 不具备某项能力时，结果必须标记为“不支持”或环境失败，不得伪造为零分或成功。

## 12. CI 质量门禁

### Pull Request

执行：

\`\`\`text
Python 单元测试
Case/RunRecord/Score schema 校验
评分器 deterministic 测试
少量恢复和工具治理 smoke case
离线重评分一致性测试
\`\`\`

门禁：

- schema 校验失败，阻断。
- 评分器不能离线重建，阻断。
- 红线次数大于 0，阻断。
- smoke case 发生回归，阻断。

### Nightly

执行：

\`\`\`text
全部 R1-R6、C1-C4、M1-M4、T1-T10
多次重复运行
Baseline / Ablation
token、延迟和工具次数统计
\`\`\`

输出按版本归档，不覆盖历史报告。

### Release

执行固定模型、固定数据集和固定环境的完整评测，生成可发布报告。Provider 不可用时必须标记环境失败，不能把未执行的结果计入通过率。

## 13. 结果汇总

报告至少包含：

\`\`\`text
总 Case 数和有效运行数
各类别通过率
Checkpoint/Resume R1-R6 明细
Tool Governance T1-T10 明细
Agent Quality 分布
Harness Quality 分布
Assurance 分布
红线统计
token 和延迟统计
Baseline / Ablation 对比
失败 Case、失败阶段、责任归属和证据路径
\`\`\`

建议的第一版报告格式：

\`\`\`text
Checkpoint/Resume：通过 5 / 6
Tool Governance：通过 10 / 10
Context Compression：平均 token 降低 14.6%
Layered Memory：召回准确率 91.2%，敏感信息泄漏 0
Agent Quality：green / yellow / red 分布
Harness Quality：green / yellow / red 分布
Assurance：verified / unverified 分布
\`\`\`

只有在分母、Case 清单、运行配置和证据路径可追溯时，才允许对外使用“100%”“10/10”等表述。

## 14. 实施阶段与验收

### 阶段 P0：协议和目录

交付：

- 创建 \`eval/\` 目录骨架。
- 完成 Case、RunRecord、Score、Manifest schema。
- 编写 \`eval/README.md\`。
- 完成现有测试清单和迁移分类。

验收：所有 Case 能通过 schema 校验，且没有评测逻辑继续新增到业务模块。

### 阶段 P1：核心 Case 和运行器

交付：

- R1-R6 六个恢复 Case。
- T1-T10 十个工具治理 Case。
- fixture 隔离和故障注入。
- 单 Case、按类别和全量运行入口。

验收：每个 Case 能从干净 workspace 重复运行并保存原始证据。

### 阶段 P2：RunRecord、评分和回放

交付：

- RunRecord 标准化。
- 离线评分器。
- 红线检查。
- 回放工具。

验收：\`offline_score == runtime_score\`，失败结果包含证据路径和责任归属。

### 阶段 P3：压缩、记忆和迁移收口

交付：

- C1-C4 和 M1-M4 Case。
- 评测语义测试迁移到 \`eval/tests/\`。
- \`test/\` 与 \`eval/tests/\` 的职责边界完成。

验收：四类评测都能生成统一 RunRecord，迁移前后产品行为测试结果不变。

### 阶段 P4：Baseline、Ablation 和 CI

交付：

- Baseline A/B/C。
- 五组消融配置。
- PR、Nightly、Release CI 流程。
- 版本化评测报告。

验收：相同 Case 可比较不同实现，CI 能阻断红线、协议破坏和核心场景回归。

## 15. 依赖与风险

### 必要依赖

- 固定 Python 解释器和依赖版本。
- 可用的 Provider 测试配置或 deterministic fake Provider。
- 可复制的 fixture workspace。
- 稳定的 workspace fingerprint 和 diff 工具。
- 不依赖真实网络的评分器测试。

### 主要风险

- 真实模型输出非确定，导致同一 Case 波动。
- Provider 不可用导致结果被误计入失败。
- 评测代码继续回流到 \`src/\` 或 \`test/\`，造成边界重新腐化。
- 运行器复用 workspace/session，导致 Case 相互污染。
- 评分器读取运行时临时状态，无法离线复核。

处理原则：先区分 Agent、Harness、Provider 和环境责任，再报告结果；不通过静默重试、删除证据或自动修复掩盖问题。

## 16. 最终验收标准

完整闭环完成的必要条件：

\`\`\`text
任意 Case 可以从干净环境重复运行
任意运行都能保存完整原始证据
RunRecord 能通过 schema 校验
评分器可以脱离运行时内存离线重建
失败可以按事件和 diff 回放
Agent Quality 与 Harness Quality 可以分别判定
Baseline / Ablation 使用相同 Case 可比较
CI 可以阻断红线和核心回归
评测逻辑集中在 eval/，业务代码保持边界清晰
\`\`\`

最终项目对外可以这样概括：

> JCode 使用集中在 \`eval/\` 下的版本化 Case、统一运行器和离线评分器进行评测。每个 Case 固定任务、workspace、模型、工具权限和验收谓词，运行后保存 trace、checkpoint、artifacts、workspace diff 和统一 RunRecord。结果分别报告任务执行质量、Harness 指令与运行协议执行质量以及结果可信度，并通过 Baseline、Ablation 和 CI 门禁保证可复现、可审计和可比较。
