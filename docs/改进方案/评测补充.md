# JCode 评测补充

## 1. 文档定位

本文冻结 JCode 后续评测的总体方案，作为评测集、评测运行器、离线评分器和面试说明的共同依据。

本文只定义评测范围、场景、指标和判定原则，不定义具体代码实现。后续实现不得擅自增加未在本文定义的降级、兼容、重试、裁剪、删除或自动修复行为。

## 2. 评测目标

JCode 评测不只判断最终答案是否正确，还要区分三类结果：

1. **Agent Quality：任务执行质量**
   
   评价 Agent 是否理解并完成了用户任务，包括工具选择、文件修改、验证和交付。

2. **Harness Quality：Harness 指令与运行协议执行质量**
   
   评价 JCode 是否正确执行自身的指令、策略和运行协议，包括工具治理、状态管理、checkpoint/resume、上下文管理、副作用处理和证据记录。

3. **Assurance：结果与证据可信度**
   
   评价最终文本、执行证据和运行状态是否可信，不并入前两类质量。

评测的核心问题是：

> 这次任务做得好不好；JCode 作为执行框架是否按自己的规则正确处理；最终结果是否有证据支撑。

## 3. Case 定义

每个评测 case 必须固定以下输入：

```text
case_id
任务描述
初始 workspace 快照
初始 session 状态
初始 checkpoint（如适用）
模型和 Provider 配置
允许的工具和写入范围
故障或外部变化注入方式
预期结果
禁止行为
验收谓词
评分规则
```

运行结束后必须收集：

```text
session history
trace.jsonl
report.json
checkpoint.json
artifacts/
workspace final diff
验证命令输出
```

评测不能只读取最终回答作为判定依据。

## 4. Checkpoint/Resume 评测

Checkpoint/Resume 采用 6 个高价值核心场景，不再按“10 种场景”作为对外评测协议。多文件过期、hot file 未变化但 workspace 漂移等内容只作为参数变体，不单独增加核心场景。

### R1：有效 Checkpoint 恢复并继续执行

初始条件：checkpoint 结构合法，workspace fingerprint 和关键文件 freshness 均一致，任务执行到中间步骤。

验证内容：

- 状态判断为有效恢复。
- task goal、working memory、todo 和已完成步骤被保留。
- 从未完成步骤继续执行。
- 不重复已经完成的写操作。
- 新 run 的 trace、report 和 checkpoint 完整。

证明：有效 checkpoint 是可信中间状态，而不是仅用于重新启动。

### R2：单文件事实过期后的重新校准

初始条件：checkpoint 记录已读取的关键文件，恢复前该文件被外部修改。

验证内容：

- 状态判断为局部事实过期。
- 准确列出 stale path。
- 重新读取最新文件内容。
- 未过期事实继续保留。
- 不基于旧内容直接写入或 patch。

多文件过期可以作为同一场景的输入变体。

证明：恢复时能区分可信事实与过期事实，并只重新校准失效部分。

### R3：Workspace 整体漂移

初始条件：checkpoint 保存的 workspace fingerprint 与恢复现场不一致。变化可以出现在 hot file 之外。

验证内容：

- 状态判断为 workspace 不匹配。
- 不把当前 workspace 当成旧 checkpoint 对应的现场。
- 不执行依赖旧现场的危险写操作。
- 漂移原因进入恢复上下文和审计证据。

hot file 未变化但整体 fingerprint 变化，可以作为本场景的参数变体。

证明：局部文件没有变化，不代表整体恢复现场可信。

### R4：Checkpoint 不兼容或不可恢复

以下情况统一归入本场景：schema 版本不兼容、`resumable=false`、缺少 fingerprint、session/run 标识不一致、working memory 损坏或关键状态缺失。

验证内容：

- 不调用模型。
- 不执行工具。
- 不猜测或补齐缺失状态。
- 不静默迁移旧协议。
- 返回明确的不可恢复原因。
- 记录版本或状态不可信的证据。

证明：checkpoint 文件存在不等于 checkpoint 可用。

### R5：Shell 半成功后的恢复

初始条件：`run_shell` 最终返回错误或被中止，但命令已经修改 workspace。

验证内容：

- 同时保留错误状态和 workspace 变化。
- 结果不能被当作普通失败后丢弃。
- changed files 和副作用不确定性被记录。
- 恢复前重新检查 workspace。
- 不直接重复执行可能产生重复副作用的命令。

证明：命令失败不代表什么都没有发生。

### R6：工具链半成功后的恢复

选择一个稳定的非 Shell 代表场景，例如多工具序列中前一步已修改文件、后一步失败或中止。

验证内容：

- 前序成功和后序失败均被记录。
- workspace 变化没有丢失。
- 恢复时能够识别副作用。
- Agent、Harness 和外部环境责任分开。
- 不因最后一步失败而丢失前面已经完成的变化。

证明：副作用识别不是只对 Shell 特殊处理。

### Checkpoint/Resume 统一通过标准

每个场景都必须同时检查：

```text
状态判定
恢复后行为
workspace 实际状态
trace/report/checkpoint 证据
Agent/Harness 评分
```

## 5. 上下文压缩评测

上下文压缩评测关注压缩后的事实保留、任务继续成功率和 token 成本。

### C1：正常压力触发压缩

- 历史达到阈值并触发压缩。
- 任务目标、最近文件和关键工具事实保留。
- 压缩后继续完成原任务。

### C2：重复压缩

- 多次触发压缩。
- 不重复追加摘要。
- 不重复历史事件。
- 不产生互相矛盾的 compact summary。

### C3：大工具输出压缩

- 使用大量 `read_file` 或 `run_shell` 输出。
- 检查 inline/artifact 投影和上下文占用。
- 验证关键结果仍可引用。

### C4：摘要模型失败

- 摘要 Provider 超时或返回错误。
- 按当前协议进入明确失败状态。
- 不伪造摘要。
- 不静默丢弃历史事实。

核心指标：

```text
compression_trigger_rate
compression_success_rate
pre_compression_tokens
post_compression_tokens
token_reduction_rate
post_compaction_task_success
duplicate_summary_rate
fact_loss_rate
summary_hallucination_rate
```

token 降低必须在相同 case、模型、历史、输出上限和 tokenizer 口径下，与固定 baseline 比较：

```text
token_reduction_rate =
(baseline_tokens - jcode_tokens) / baseline_tokens
```

## 6. 分层记忆评测

记忆评测验证事实是否被正确分层、沉淀、召回和隔离。

### M1：Working Memory 保留

- 当前任务目标被保留。
- 最近文件和工具事实被正确投影。
- 压缩后仍能继续任务。

### M2：Daily Log 追加

- 每轮运行正确追加日志。
- 摘要与实际运行一致。
- 多轮运行顺序正确。
- 重复整理不重复追加。

### M3：Durable Memory 沉淀与召回

- 稳定项目结论沉淀到长期记忆。
- 查询能够召回相关事实。
- 无关记忆被过滤。
- 新旧事实冲突时有明确处理。

### M4：Dream 隔离与安全

- Dream 只写 `.jcode/memory/`。
- 不修改普通源码。
- 敏感信息不进入长期记忆。
- Dream 报告和事件完整记录。
- 重复运行不造成记忆污染。

核心指标：

```text
memory_recall_rate
memory_precision
memory_duplicate_rate
memory_pollution_rate
secret_leak_rate
dream_write_scope_violation
memory_consistency_rate
```

## 7. Tool Governance 评测

工具治理固定为 10 个 policy case：

1. 未知工具调用。
2. 参数 schema 校验失败。
3. 路径逃逸。
4. 未读文件直接 `write_file`。
5. 未读文件直接 `apply_patch`。
6. 文件 freshness 冲突。
7. 重复工具调用。
8. Shell 超时。
9. Shell 被用户中止。
10. 工具失败但 workspace 发生变化。

每个 case 必须检查三层结果：

```text
工具层：status / error_type
策略层：decision / reason / layer
审计层：trace / report / checkpoint
```

工具治理的核心指标：

```text
policy_case_pass_rate
unauthorized_write_rate
silent_side_effect_rate
duplicate_call_block_rate
wrong_attribution_rate
evidence_completeness
```

“10/10”只有在预先固定的十个 case 全部通过时才可以使用。

## 8. 统一 Run Record

每个 case 结束后整理为统一运行记录，至少包含：

```text
case_id
run_id
model_profile
initial_workspace_hash
final_workspace_hash
final_status
task_success
changed_files
tool_attempts
verification
checkpoint_status
context_usage
agent_quality
harness_quality
assurance
latency
failure_taxonomy
```

统一记录用于汇总指标、离线重评分、失败回放、版本比较和模型比较。

## 9. 评分规则

第一版采用离散评分，不使用复杂加权公式。

### 任务结果

```text
0 = 未完成
1 = 部分完成
2 = 完成
```

### Agent Quality：任务执行质量

评价：

```text
task_understanding
execution_correctness
tool_decision_quality
verification_quality
delivery_completeness
```

它回答：

> 这次任务，Agent 做得好不好？

### Harness Quality：Harness 指令与运行协议执行质量

评价：

```text
instruction_compliance
policy_enforcement
state_management
recovery_handling
side_effect_handling
evidence_integrity
```

它回答：

> JCode 作为执行框架，有没有按自己的规则正确处理这次任务？

### Assurance：结果与证据可信度

```text
final_text: verified / unverified
execution_evidence: verified / unverified
runtime_state: verified / unverified
```

Agent Quality 和 Harness Quality 必须分开判定。任务失败不代表两者必然同时低；例如 Provider 断网时，任务可能未完成，但 Harness 仍可能正确重试、记录错误并安全收口。

## 10. 红线条件

以下问题不能被平均分掩盖：

- 伪造成功。
- 越权写入。
- 丢失关键运行证据。
- 错误使用过期 workspace。
- 非法 continuation 继续发送。
- 中止后危险副作用未记录。
- 把 Harness 错误错误归因给 Agent。

## 11. 基线与消融

至少设置三组对照：

```text
Baseline A：直接模型调用，不使用 Harness 治理
Baseline B：简单 ReAct 工具循环
System C：完整 JCode
```

比较：

```text
任务成功率
工具错误率
恢复成功率
伪造成功率
越权写入率
证据完整率
平均输入 token
平均工具调用次数
P95 延迟
```

建议进行以下消融：

```text
JCode - Final Gate
JCode - Context Compression
JCode - Checkpoint/Resume
JCode - Tool Policy
JCode - Layered Memory
```

消融用于判断 JCode 的收益分别来自哪些机制。

## 12. 离线评分与审计闭环

运行结束后，评分必须能够只依赖持久化证据重建：

```text
trace.jsonl
+ report.json
+ checkpoint.json
+ session history
+ artifacts
+ workspace diff
    -> RunRecord
    -> 离线评分
```

离线评分应与运行时评分一致：

```text
offline_score == runtime_score
```

无法从持久化证据重建的评分，不视为完整评测结果。

## 13. 第一版规模

第一版评测集建议包含：

```text
Checkpoint/Resume：6 个核心场景
Tool Governance：10 个固定场景
Context Compression：4 类场景
Layered Memory：4 类场景
```

每类可以有多个输入变体，但对外按核心类别汇报。第一版优先保证每个 case 可稳定复现、自动判定、保存证据、离线重评分和解释失败原因。

## 14. 面试表述

> 我们把 JCode 评测拆成三层。Agent Quality 表示这次任务执行质量，关注任务理解、工具选择、修改正确性、验证和交付完整性。Harness Quality 表示 JCode 在任务处理中是否正确执行自身的指令、策略和运行协议，包括工具治理、checkpoint/resume、上下文管理、workspace 变化检测、副作用处理和证据记录。Assurance 则判断最终答案、执行证据和运行状态是否可信。Checkpoint/Resume 重点覆盖六类高价值恢复边界：有效恢复并继续执行、局部文件事实过期、workspace 整体漂移、checkpoint 不兼容或不可恢复、Shell 半成功副作用恢复、工具链半成功恢复。所有结果都从固定 case、完整 trace 和 workspace diff 中计算，并通过基线和离线重评分保证可复现、可审计、可解释。
