# apply_patch 换行传输兼容改进方案（日期合并版）

## 方案演进

### 2026-09-08：底层读取一致性

统一 `read_file` 与 `apply_patch` 的原始 UTF-8 字节读取，保留目标文件的 CRLF/LF；记录并诊断 newline、BOM 和匹配失败信息。该阶段解决了工具两端读取方式不一致，但不能阻止模型在生成参数时把 CRLF 变成 LF。

### 2026-09-09：传输层等价匹配修订

在保留上述措施的基础上，`apply_patch` 仅对 LF/CRLF 做传输等价处理，同时将 newline 与 BOM 信息放入模型可见的 `read_file` 正文头部。以下章节是两阶段合并后的现行规范。

## 1. 背景

JCode 的文件工具要求 `apply_patch.old_text` 精确来自 `read_file`。Windows 文件通常使用 CRLF，但模型生成工具参数时经常将跨行文本规范化为 LF。于是模型看到的代码内容、缩进和正文都正确，工具仍因换行字符不同而返回 `old_text matched 0 times`。

## 2. 目标

在不降低精确文本修改安全性的前提下，消除模型传输层造成的 LF/CRLF 差异，并让模型在读取时直接看到换行与 BOM 信息。

## 3. 方案

### 3.1 匹配策略

`apply_patch` 对目标文件保持原始 UTF-8 解码和原始换行：

```text
原始 old_text 精确匹配
    ↓ 仅当 0 次且 old_text 含换行
按目标文件换行格式规范化 old_text
    ↓
精确匹配且必须唯一
```

目标文件为 CRLF 时，将 LF 与 CRLF 统一为 CRLF；目标文件为 LF 时统一为 LF。混合换行文件不自动选择格式，应按既定失败语义处理，避免重写混合格式的未命中内容。

### 3.2 写回策略

替换后的文本统一转换为目标文件当前换行格式，再以 UTF-8 原始字节写回；原有 UTF-8 BOM 原样保留。换行兼容只影响传输表示，不改变文件格式。

### 3.3 读取诊断

`read_file` 正文头部明确展示：

```text
newline: crlf|lf|mixed|none
utf8_bom: true|false
```

这两个字段同时保存在 metadata，供工具历史、审计和问题定位使用。

## 4. 安全边界

- 只允许 LF 与 CRLF 的等价转换。
- 仍要求 old_text 唯一命中。
- 空格、制表符、缩进、大小写、字符编码和正文内容仍精确匹配。
- 0 次或多次匹配都必须返回错误。
- 不进行模糊匹配、自动猜测、自动裁剪或静默重试。
- 写回保留目标文件当前换行格式和 BOM。

## 5. 验证计划

新增测试覆盖：

1. LF 参数替换 CRLF 文件成功，结果仍为 CRLF。
2. CRLF 参数替换 CRLF 文件成功。
3. LF 文件替换成功且仍为 LF。
4. old_text 内容差异仍失败。
5. 规范化后多重命中仍失败。
6. read_file 正文包含 newline 与 utf8_bom 诊断字段。

## 6. 预期结果

模型无需可靠携带不可见的 `\r` 字符即可完成 Windows 跨行补丁；工具仍然是唯一、精确、可审计的文本替换，不会扩大到模糊修改。
