# 记忆系统最小闭环方案

## 1. 目标

在不引入向量检索、数据库或 Web 端功能的前提下，让记忆系统形成一条可验证闭环：

```text
新请求
  -> 自动召回 active 长期记忆
  -> 注入 WorkingMemory
  -> Agent 执行
  -> 结构化 Daily Log
  -> 规则生成 candidate
  -> 确定性准入
  -> 晋升为 active 长期记忆
  -> 下一轮继续召回

用户手动执行 jcode --dream
  -> 整理 Daily Log、候选和已有主题记忆
  -> 更新 MEMORY.md 与 topics/*
  -> 写入 Dream 报告
```

首版只支持三类长期记忆：

- `user_preference`：用户长期协作偏好。
- `project_convention`：项目编码、测试、目录和工具约定。
- `key_decision`：已经明确采用的设计或架构决策。

## 2. 范围边界

本方案包含：

- 每个新用户请求自动词法召回。
- Daily Log 结构化记录。
- 基于明确表达的规则准入。
- candidate、active、冲突和替代状态。
- CLI 手动 Dream 整理。
- 记忆来源、运行证据和 Dream 报告。
- 自动化正例和负例评测。

本方案不包含：

- 向量检索或 embedding。
- SQLite、外部数据库或多项目共享记忆。
- Web 端记忆接口和 Dream 按钮。
- 后台自动 Dream 或定时任务。
- 旧日志、旧 notes 格式的迁移和兼容。
- 自动删除长期记忆。
- 模型自由决定记忆准入。
- 依赖与环境事实记忆。

## 3. 记忆层职责

### 3.1 WorkingMemory

WorkingMemory 是当前运行的短期记忆，保存任务目标、文件 freshness、工具观察、todo、恢复状态和本次召回结果。它服务上下文构建和工具治理，不是长期知识库。

召回结果以结构化条目保存，不再只保存裸字符串：

```json
{
  "memory_id": "mem-...",
  "memory_type": "project_convention",
  "text": "...",
  "score": 4,
  "source_entry_id": "log-..."
}
```

### 3.2 Daily Log

Daily Log 是过程层原始记录，保存每轮运行事实，供规则整理、Dream 和审计回溯使用。它不直接等同于长期记忆。

每条条目至少包含：

```text
entry_id
created_at
session_id
run_id
turn_id
user_message
final_text
changed_files
verification
tool_failures
candidate_signals
```

Daily Log 的事实来源是运行结果，Dream 不改写历史条目。

### 3.3 Durable Memory

Durable Memory 是跨任务复用的长期记忆，继续使用当前文件结构：

```text
.jcode/memory/
  MEMORY.md
  notes.jsonl
  topics/
    project-conventions.md
    key-decisions.md
    user-preferences.md
```

`notes.jsonl` 保存结构化 candidate 和 active 记录；`MEMORY.md` 是入口索引；`topics/*.md` 是人可读的主题结论。

### 3.4 Dream

Dream 是手动记忆整理机制，不是独立记忆层。它读取 Daily Log、候选、入口索引和主题结论，负责去重、归并、冲突标记、过期识别和主题文件更新。

## 4. 自动准入规则

每轮结束后，系统先写 Daily Log，再从用户明确表达中提取候选。最终回答只能作为结果背景，不能单独触发长期记忆晋升。

### 4.1 用户偏好

匹配明确的长期表达，例如：

- “以后都……”
- “请始终……”
- “我偏好……”
- “不要……”

普通一次性要求，例如“这次请……”不进入长期记忆。

### 4.2 项目约定

匹配项目范围表达，例如：

- “本项目规定……”
- “仓库约定……”
- “项目必须……”
- “测试统一使用……”

### 4.3 关键设计决策

匹配明确决策表达，例如：

- “决定采用……”
- “最终选择……”
- “架构确定为……”
- “不再支持……”

讨论中的备选方案、模型推测和“建议以后……”不进入长期记忆。

### 4.4 确定性校验

候选晋升为 active 前必须满足：

- 来源是用户明确表达。
- 类型明确且属于三类之一。
- 文本非空。
- 未命中敏感信息规则。
- 与 active 记忆不完全重复。
- 没有未处理的同类型冲突。

候选不满足条件时保留 Daily Log 证据，但不生成 active 记忆。

## 5. 长期记忆状态

首版状态为：

```text
candidate
active
superseded
stale
conflict
```

状态语义：

- `candidate`：规则识别出的候选，尚未完成准入。
- `active`：允许被自动召回的长期记忆。
- `superseded`：被明确的新决策替代，不参与召回。
- `stale`：已知过期，不参与召回。
- `conflict`：与已有 active 记忆存在未解决冲突，不参与自动召回。

规则：

- 完全相同的内容记录为 duplicate，不重复创建 active。
- 文本不同但无法确定替代关系时，保留旧 active，新内容标记 conflict。
- 只有明确表达“最终选择/决定采用”替代旧决策时，旧记忆才标记 superseded。
- 不自动删除任何历史记录。

## 6. 自动召回

每个新用户请求开始时执行：

```text
用户请求
  -> 提取中文字符 n-gram、英文 token、路径/命令/符号 token
  -> 查询 active 记忆
  -> 分层计分、去重、排序
  -> 写入 WorkingMemory
  -> 进入 ContextManager 和 Provider 输入
```

召回只读取 active 记忆。结果必须包含 `memory_id`、类型、文本、分数、命中词和来源条目。无命中时保持空结果，不使用上一轮召回结果，不添加默认记忆。

本方案不使用向量检索。词法检索需要支持中文、中英混合请求，以及路径、命令和函数名等 Coding Agent 特征。

## 7. CLI 手动 Dream

新增命令：

```powershell
jcode --dream
jcode --dream --cwd <workspace>
jcode --dream --config <global-config>
jcode --dream --model <model-profile>
```

约束：

- `--dream` 与普通 prompt 互斥。
- 使用当前配置和模型档案。
- 手动执行不受 `dream_min_sessions` 和 `dream_interval_hours` 门控。
- Dream 只能写 `.jcode/memory/`。
- Dream 不提供 Web API。
- Dream 不触发后台任务。
- Dream 失败返回非零退出码。

Dream 读取：

```text
.jcode/memory/logs/**
.jcode/memory/notes.jsonl
.jcode/memory/MEMORY.md
.jcode/memory/topics/*.md
```

如有来源引用，还可读取关联的 `session_id`、`run_id`、`turn_id`、变更文件、验证结果和 artifact 引用。

Dream 不得把 WorkingMemory 临时观察、完整文件正文、原始 shell 输出、未验证推测或敏感内容直接提升为长期记忆。

## 8. Dream 报告

每次手动 Dream 都写入：

```text
.jcode/memory/dream_reports/*.json
```

报告至少包含：

```json
{
  "status": "finished|no_changes|failed",
  "trigger": "manual_cli",
  "input": {
    "daily_log_entries": 0,
    "candidate_count": 0,
    "active_memory_count": 0
  },
  "changes": {
    "added": [],
    "updated": [],
    "superseded": [],
    "conflicts": [],
    "filtered_sensitive": 0
  },
  "changed_files": [],
  "dream_session_id": "",
  "provider": "",
  "model_profile": "",
  "updated_at": ""
}
```

首版可以只通过文件前后快照记录变化，但不能只记录“文件发生变化”，必须提供整理输入和变更类别。

## 9. 失败语义

### Daily Log 写入失败

本轮运行结果不回滚；记录 `memory_write_failed`；不生成 active 记忆；错误必须进入 report/trace。

### 候选解析失败

保留 Daily Log 原始条目；不生成 candidate；记录 `candidate_extraction_failed`；不影响本轮最终回答。

### 敏感内容命中

不写入 candidate 或 Durable Memory；记录 `memory_filtered_sensitive`。不保存敏感原文。

### 自动召回失败

当前请求继续执行，但不注入召回结果；记录 `memory_retrieval_failed`；不使用上一轮结果。

### Durable Memory 写入失败

本轮任务保持原有完成状态；report/trace 标记长期记忆未确认写入；不读取半成品，不擅自重试或自动修复。

### Dream 失败

CLI 返回非零退出码，保留失败报告，记录 `provider_failed`、`dream_run_failed`、`memory_write_failed` 或 `write_scope_mismatch` 等明确原因。

## 10. 文件级实施顺序

### 阶段一：结构和纯规则

- `src/memory/journal.py`：结构化 Daily Log。
- `src/memory/durable.py`：MemoryRecord、状态、去重和冲突接口。
- `src/memory/consolidation.py`：候选提取和确定性准入。
- `src/memory/retrieval.py`：词法 token 提取和 MemoryHit。

先完成纯函数和模块级测试，不接入 Agent 主流程。

### 阶段二：自动沉淀和召回

- `src/memory/working.py`：结构化召回结果和渲染。
- `src/runtime/agent.py`：请求开始时召回，运行结束时写 Daily Log 和准入结果。
- `src/evidence/summaries.py`：记录 retrieval、candidate 和 promotion 审计。

### 阶段三：CLI Dream

- `src/app/cli.py`：新增 `--dream`，与普通 prompt 互斥。
- `src/runtime/agent.py`：传递 `manual_cli` 触发来源。
- `src/memory/consolidation.py`：补充 Dream 输入统计、变更分类和失败报告。

Web 相关文件不修改。

### 阶段四：闭环评测

加入以下正例：

- 用户偏好沉淀、下一轮召回并影响输出。
- 项目约定沉淀、下一轮代码任务遵守约定。
- 关键设计决策沉淀、下一轮设计继续采用。
- Dream 整理重复和冲突后，后续只召回 active 记忆。

加入以下负例：

- 一次性要求不进入长期记忆。
- 模型推测不进入长期记忆。
- 敏感文本不落盘。
- 重复内容不产生重复 active 记忆。
- 冲突内容不静默覆盖旧记忆。
- 无命中时不残留上一轮召回。
- Dream 越界写入、Provider 失败和 memory 写入失败均可观察。

## 11. 完成定义

满足以下条件才算完成最小闭环：

1. 每个新请求自动检索 active 记忆。
2. 召回结果进入 WorkingMemory 和 Provider 输入。
3. 每轮完成后写结构化 Daily Log。
4. 只有明确表达生成 candidate。
5. candidate 可以晋升为三类 active 记忆。
6. 重复、冲突、敏感和写入失败都有明确状态。
7. 下一轮能够召回上一轮晋升的记忆。
8. `jcode --dream` 能手动整理记忆。
9. Dream 只能修改 `.jcode/memory/`。
10. Dream 有独立报告和失败语义。
11. Web 端行为保持不变。
12. 正例和负例都能自动执行并验证。
