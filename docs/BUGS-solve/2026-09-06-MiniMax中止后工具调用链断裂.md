# 解决方案讨论：MiniMax 中止后工具调用链断裂

对应 Bug：`docs/BUGS-after9.6/2026-09-06-MiniMax中止后工具调用链断裂.md`

## 目标

满足以下约束：

1. abort 后当前 run 必须以明确的 `aborted` 终态结束。
2. 后续 run 不能回放未闭合的 Responses 工具调用链。
3. 不伪造工具执行成功结果，不把“未执行”误记为真实工具输出。
4. 保留审计信息，能看出哪个调用因 abort 被丢弃。
5. 对正常完成、工具失败和跨 run 历史不产生额外行为变化。

## 方案比较

### 方案 A：abort 时只删除孤立 `tool_call`

在 `_finish_run(..., ABORTED)` 前，从 session history 删除当前 run 中没有对应 `tool_result` 的 `tool_call`，并清理 `provider_continuation` 中对应的 `function_call`。

优点：实现直接，MiniMax 下一次请求不会收到非法调用。

缺点：删除会损失“模型曾请求但未执行”的审计事实；如果只删除 history 而漏清 continuation，仍可能失败；并发 abort 时需要保证收口原子性。

### 方案 B：保留调用，补写取消状态的结果项

为每个因 abort 未执行的调用追加结构化的取消结果，例如 `tool_result` 的 metadata 标记 `tool_status=cancelled`，Provider 回放时编译成匹配的 `function_call_output`。

优点：调用链完整，审计信息最完整。

缺点：`function_call_output` 会被 MiniMax 解释为工具已经返回结果；如果输出协议没有明确支持“取消”，可能让模型误以为工具执行过。还需要确认所有 Provider 对取消结果的语义兼容性。

### 方案 C：Provider 输入编译前过滤未闭合调用，并记录丢弃事件（推荐）

在通用 Responses 输入编译层构造调用配对索引：只保留有匹配 `function_call_output` 的 `function_call`；对没有结果的调用不发送给 Provider，同时在本地记录 `orphan_tool_call_dropped`，包含 `run_id`、`call_id`、工具名和来源 run。

同时在 abort 收口阶段清理当前 run 的 `provider_continuation`，避免当前 run 的 checkpoint 恢复再次携带孤立项。通用 history 原文仍保留，便于审计；Provider 输入是经过一致性校验后的投影。

优点：不会伪造工具结果；能同时防住历史和 continuation 两条路径；校验集中在协议边界，所有 Responses Provider 都受益；保留原始审计。

缺点：需要定义“丢弃调用”的事件记录和测试；如果孤立调用本身包含下一轮任务的关键意图，模型不会看到该调用，但这是 abort 后未执行动作的正确语义。

## 最终确定方案

采用原生工具调用状态机，并对每一个工具调用补齐成对的 Responses 结果项。

### 调用状态

```text
pending -> running -> completed | failed | interrupted
pending -> cancelled
```

- `cancelled`：用户 abort 时调用尚未开始，明确未执行。
- `interrupted`：用户 abort 在调用执行期间发生，无论底层工具是否能立即停下，都不得视为完成。
- `completed`、`failed`：维持真实工具返回结果。

### 固定回传文本

尚未执行的调用必须回传：

```text
[JCode tool execution cancelled]
status: cancelled
reason: user_abort
message: 该工具调用因用户中止当前运行而未实际执行；不得将其视为已完成。
```

执行期间被中止的调用必须回传：

```text
[JCode tool execution interrupted]
status: interrupted
reason: user_abort
message: 该工具执行期间被用户终止，可能已经产生文件、命令、进程或其他运行时副作用；必须先检查工作区和运行状态，不得将其视为完成。
```

这两段完整文本会进入下一次 run 的模型上下文，并作为相同 `call_id` 的 `function_call_output` 与原调用配对。

### 1. 任务状态持久化

`TaskState.native_tool_calls` 以 `call_id` 为键持久化名称、参数、状态和更新时间。history、continuation、checkpoint、trace 都使用同一个调用标识。

### 2. abort 收口

- 模型返回批量调用后，所有调用先登记为 `pending`。
- abort 后，当前批次未开始调用写入 `cancelled` 结果。
- 正在运行的调用返回后写入 `interrupted` 结果。
- `run_shell` 使用可轮询的子进程执行方式，abort 时终止进程树。
- Web run 保持 `aborting`，同一 session 禁止启动新 run，直至运行线程结束。

### 3. 保留审计，不伪造成功

新增结构化 trace 事件：

```json
{
  "event": "tool_cancelled",
  "run_id": "run-...",
  "call_id": "call-...",
  "name": "read_file",
  "reason": "user_abort"
}
```

session history 中原始 `tool_call` 和明确的取消/中断结果都保留。不得写入看似成功的工具输出。

## 时序

```text
收到模型 function_call
  -> 记录原始 tool_call
  -> abort 置位
  -> 未执行调用标记为 orphan/cancelled（仅审计）
  -> 清理 task continuation
  -> run 以 aborted 结束
  -> 下一 run 编译 history
  -> 配对校验过滤 orphan
  -> MiniMax 收到合法 Responses input
```

## 测试清单

1. 模型返回一个工具调用后立即 abort：首个 run 为 `aborted`，不产生伪造 `tool_result`。
2. abort 后启动第二个 MiniMax Responses run：每个工具调用都有配对结果，不返回 2013。
3. 多个并行工具调用只执行前一部分后 abort：已执行、取消和中断调用均有配对结果。
4. 正常工具调用链：`function_call` 与 `function_call_output` 完整回放，行为不变。
5. continuation 与通用 history 使用相同 `call_id`，并持久化相同状态。
6. 非 Responses Provider 的现有请求编译和历史回放测试保持通过。

## 解决计划

### 阶段一：先建立可观测基线

1. 固定本次真实 session 作为故障样本，保存孤立 `call_ed56f21c74f54ba6ba2d17` 的证据。
2. 为新的 abort 路径构造工具调用批次，验证所有调用均生成配对结果。
3. 明确测试断言：不得调用真实 MiniMax 网络接口，使用持久化 history 和 continuation 检查项配对关系即可。

交付物：一个稳定复现 abort 调用批次的测试，以及能检查 `call_id` 状态的断言。

### 阶段二：实现状态机与成对结果

1. 在 `TaskState` 增加按 `call_id` 管理的调用状态。
2. 在 Agent 工具批次中为 `cancelled`、`interrupted` 调用追加固定 `function_call_output`。
3. 保持正常配对调用、reasoning、普通 user/assistant 消息的顺序和内容不变。

### 阶段三：补齐 abort 收口与 shell 中断

1. 修改 `src/runtime/agent.py`，处理批量调用中间的 abort。
2. 修改 `run_shell`，使用可终止进程树的执行方式。
3. 保证 `_finish_run()` 仍只执行一次，避免 Web 层 `aborting -> aborted` 与 runtime 收口产生重复事件。

### 阶段四：回归验证与发布门槛

1. 运行 request 编译器、continuation、agent abort、Web abort 相关现有测试。
2. 新增四类测试：单工具中断、多个并行调用部分执行、正常调用链不变、shell 中断。
3. 使用本次真实 session 的调用序列做离线验证，确认新的 abort 路径不会再留下孤立项。
4. 对 `minimax-m3` 和 `minimax-m2.7` 各执行一次真实接口冒烟测试；测试凭据只从环境变量读取，不写入日志和 fixture。
5. 检查 trace、session、checkpoint 三者的终态一致性：run 为 `aborted`，无伪造工具成功结果，存在取消或中断诊断事件。

## 实施顺序与回滚点

推荐顺序为“阶段一 -> 阶段二 -> 阶段三 -> 阶段四”。阶段二修复新 abort 链路。每个阶段独立提交，确保协议恢复和 shell 中断的回归可以独立定位。

## 完成判定

只有同时满足以下条件才算修复完成：

- abort 后 session history 保留审计事实，且每个 Provider 工具调用都有配对结果。
- 第二个 MiniMax run 不再因 2013 `invalid_prompt` 失败。
- 当前 run 的 continuation 和 checkpoint 持久化工具状态及配对结果。
- 没有伪造成功的工具执行结果，正常调用链和其他 Provider 测试不回归。

## 风险与取舍

该方案选择“未执行或中断动作以明确失败语义进入下一次模型上下文”。这既满足 MiniMax 的调用配对协议，也让后续模型不会误以为旧动作已完成。原始 history 和 trace 继续保留，因此不会牺牲故障审计能力。

## 本次实施结果

- 已实现 `TaskState.native_tool_calls` 状态持久化。
- 已实现 abort 后 `cancelled` 和 `interrupted` 的成对历史与 continuation 输出。
- 已实现 `run_shell` 的 abort 轮询与进程树终止。
- Web 在 `aborting` 状态显示“正在终止工具，请稍等。”并禁用消息输入与发送按钮。
- 本次未增强中断/失败后的工作区副作用识别；中断结果仅保守提醒后续 Agent 主动核验。
