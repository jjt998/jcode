# 恢复上下文完整变更路径导致后续 run 爆量

## 冻结方案

恢复差异只保留两个视图：

1. 本地完整变更路径 `changed_paths`。
2. Provider 可见的最小路径投影。

完整 `changed_paths` 继续用于工作区变化判断、旧读取证据 stale 标记、continuation 兼容性判断和现有运行审计，不进入 `WorkingMemory.render()`。

Provider 可见路径定义为：

```text
visible_changed_paths = changed_paths ∩ (历史 read_file 路径 ∪ 当前 hot 文件路径)
```

模型上下文只遵循以下规则：

- `visible_changed_paths` 非空时，展示这些完整路径；
- 存在未进入 `visible_changed_paths` 的其他变化时，只追加一句“工作区发生了变化。”；
- 只有其他变化时，只展示这句话；
- 没有变化时，不展示工作区变化信息。

历史 `read_file` 路径指实际产生文件证据的读取路径。`search` 扫描到的全部来源文件不自动视为模型侧已读路径，避免一次大范围搜索重新生成大列表。

`JCodeAgent._begin_run()` 必须继续使用完整 `changed_paths` 调用 `_mark_stale_file_evidence()`，然后只把最小 Provider 投影写入 `working_memory.resume_context`。

## 已删除的非必要机制

- 目录级统计和文件数量汇总；
- 代表路径采样；
- 变更类型统计；
- 完整路径 artifact 引用；
- 分页或按前缀查询工具；
- 本方案专用的内容哈希；
- 固定忽略 `node_modules` 或缓存目录的规则；
- 第二套 stale 数据结构。

## 验收

- `node_modules` 大规模变更时，Provider 只收到一句“工作区发生了变化。”。
- 已读或 hot 文件变化时，Provider 收到对应完整路径，并可要求重新读取。
- 已读文件被删除时，仍能展示该历史路径。
- 本地 stale 标记仍接收所有变更路径，热文件 freshness 语义不变。
- `search` 扫描大量文件时，不会把全部扫描来源注入 Provider 输入。
- 恢复上下文大小不随未读依赖文件数量线性增长。
